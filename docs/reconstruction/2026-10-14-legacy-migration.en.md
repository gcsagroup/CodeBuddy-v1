# Offline legacy data migration

Sources are the current files in `D:\CodeBuddy-v1`; see `source-baseline.json`. No branches, commits or pushes were created. The original project and user profile are read only. Implementation lives in `runtime/legacy-migration.mjs` and `runtime/profile-lock.mjs`; the CLI is `scripts/migrate-legacy-profile.mjs`.

## Use and integration

Start with the read-only inventory: `node scripts/migrate-legacy-profile.mjs --source <absolute-old-profile> --target <absolute-new-backend>`. Writing additionally requires `--apply --offline` and a stopped target runtime. Migration and the server share the SQLite exclusive transaction returned by `acquireProfileLock(dataDir)`. Process exit releases it automatically. Migration also checks live PIDs in old launch receipts, covering preview processes predating the lock. The offline flag never bypasses a live process or lock.

`inspectLegacyProfile` reports counts and compatibility boundaries without message bodies or configuration values. `migrateLegacyProfile` uses Node's SQLite backup API and quick_check for an independent consistent snapshot. The source database and WAL are opened read only. State JSON receives only original-UI-visible user/code_pro metadata, marked `readonlyHistory:true` with `legacyHistory:{archiveId,sessionId}`. Messages remain in `legacy/<archiveId>/sessions.db`. `loadLegacyConversation(dataDir,reference)` reads one selected conversation using existing history validation and UI projection. Hidden/child sessions remain archived but are omitted from the original UI list. No legacy execution or permissions resume.

Configuration fills missing entries while preserving current model defaults, providers and credentials. Compatible custom provider definitions are imported; legacy keyring credentials require re-entry. Existing literal custom headers use the new credential protection mechanism. Newly imported MCP entries are disabled. Unknown old builtins are explicitly reported. Existing ScheduleService creates imported schedules paused and untested, with no running flags, old execution session or automatic replay.

Original memory files remain archived. Old project identifiers use Blake3; the new implementation uses Harness storage domains. Unconfirmed project identity is never guessed. Supply `--project-map <JSON-file>` containing `{ "old-32-character-identity": "absolute-project-directory" }` to import through ProjectMemory and official driver.memory. Active/candidate/disabled state, expiry and confidence are retained. Old user-scope memories remain separately reported for review instead of broadening project scope. Stable IDs make reruns idempotent. Interrupted multi-module migrations can resume, with unhandled entries explicitly reported; no cross-file atomic rollback is claimed.
