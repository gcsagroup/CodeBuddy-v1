# CodePro 核心架构设计优化方案

## 一、工作区选择与根目录处理

### 1.1 现状

当前 CodePro 对磁盘根目录（如 `D:\`、`E:\`）采用硬性禁止策略。`projectWorkspace.ts` 中 `isFilesystemRoot()` 检测到根目录后，state 设为 `filesystem-root`，`WorkspaceConfirmationCard.tsx` 中 `canConfirm()` 直接禁用确认按钮，用户无法继续。

### 1.2 行业参考

| 产品 | 方式 | 核心思路 |
|---|---|---|
| Codex | 不禁止，用 `--cd` 指定目录，sandbox 默认只允许写 workspace | 沙箱圈定范围，越界走 approval |
| Claude Code | 允许启动，OS 沙箱默认只能写 cwd；`rm -rf /` 仍会提示 | 沙箱 + 危险操作兜底 |
| Trae | IDE 打开任何文件夹都行 | 用户主动选择，沙箱可选开启 |
| Hermes | 默认 local backend，可选 Docker/SSH/Modal 等隔离后端 | 多种 backend 按需选择 |

### 1.3 优化方案

**第一阶段（当前可做）：警告态 + 新建项目引导**

把 `filesystem-root` 从禁用态改成警告态，提供三个操作：

| 操作 | 说明 |
|---|---|
| 选择项目文件夹 | 打开文件浏览器，选择 D 盘下现有项目 |
| 在 D:\ 新建项目 | 自动生成 `D:\my-project`，用户确认后创建 |
| 取消 | 返回 |

不使用"使用 D:\ 作为工作区"选项，因为会导致 `.codepro` 散落在根目录、TaskDAG scope 全盘化、证据收集爆炸等问题。

**第二阶段（有条件后）：权限模式 + 运行时拦截**

参考 Claude Code 的 permission mode 设计，把"在哪工作"和"能做什么"分开，引入运行时文件操作拦截。

## 二、安全沙箱与边界控制

### 2.1 现状

CodePro 当前有三层边界控制，但只有第一层是硬拦截：

| 层级 | 机制 | 位置 | 性质 |
|---|---|---|---|
| 规划时验证 | TaskDAG read_scope/write_scope 验证 | task_dag.rs | 硬拦截 |
| 工具权限分级 | ReadOnly/WorkspaceWrite/ExternalWrite/HighRisk/Forbidden | permission_inspector.rs | 软拦截（用户可同意） |
| Prompt 约束 | 系统提示词注入边界描述 | task_scheduler.rs | 无拦截（依赖模型遵守） |

**核心漏洞**：没有运行时文件级拦截。Agent 可以执行 `echo "data" > D:\other_project\file.txt`，只要权限分级允许。

### 2.2 行业参考

| 产品 | 沙箱方式 | 技术 | 越界处理 |
|---|---|---|---|
| Claude Code | OS 级沙箱，默认 cwd 读写 | macOS Seatbelt / Linux bubblewrap | OS 直接拦截，通知用户 |
| Hermes | 六种 terminal backend | Local/Docker/SSH/Modal/Daytona/Singularity | 隔离由 backend 执行环境提供 |
| Trae | 可选沙箱，默认关闭 | sandbox-exec / bubblewrap | 拦截 + 跳过/运行/加白名单三选项 |

Hermes SECURITY.md 核心表述：

> The only security boundary against an adversarial LLM is the operating system. Nothing inside the agent process constitutes containment.

### 2.3 优化方案

**短期：文件工具层运行时检查**

在 `file_read`、`file_write`、`file_edit`、`shell` 工具执行前，检查目标路径是否在 `write_scope` / `read_scope` 内。越界时直接拒绝，不依赖用户判断。

**中期：OS 级沙箱**

参考 Claude Code 和 Trae 的沙箱实现，在 OS 层面强制限制文件访问范围。

**长期：多 backend 支持**

像 Hermes 一样，支持本地、Docker、SSH、云端等多种执行后端，让用户按安全需求选择。

## 三、多模态视觉子 Agent 设计

### 3.1 问题

CodePro 如果用户默认使用 `kimi-k2.7-code` 或 `deepseek-v4-flash` 作为主模型，这些是纯文本模型，不支持视觉输入。当 Agent 需要读取图片、截图、扫描件 PDF 时，模型无法处理。

### 3.2 行业参考

| 产品 | 处理方式 |
|---|---|
| Claude Code | 默认模型 Claude 原生多模态，无需额外处理 |
| Codex | 默认模型 GPT-4o 原生多模态，无需额外处理 |
| Trae | 如果模型不支持多模态，不发送图片 |

CodePro 的特殊性在于强制使用代码专用模型，所以必须自行解决多模态问题。

### 3.3 方案：工具化视觉子 Agent

**核心原则**：主 agent 决定读什么，工具负责"怎么读"。不搞预处理层（会全盘扫描浪费 token），而是把视觉分析能力封装成工具函数。

#### 架构

```
主 agent 调用 read_file / read_document 工具
    ↓
工具检测文件类型
    ↓
  ┌─────────────┬─────────────┐
  ▼             ▼             ▼
文本文件      图片/视频    扫描件PDF
  │             │             │
  │        主模型支持         │
  │        多模态？           │
  │        │        │         │
  │      是        否         │
  │        │        │         │
  ▼        ▼        ▼         ▼
直接返回   base64  视觉子Agent  视觉子Agent
文本内容  返回     分析→文字    分析→文字
```

#### 视觉子 Agent 实现

封装为函数，不是完整子 agent 生命周期。接收图片 + 任务上下文，调用多模态模型（如 `qwen2.5-vl:7b`），返回结构化文字。

```text
你是视觉分析助手。当前主 agent 正在执行任务：
「{task_context}」

请分析以下文件（{path}，{mime}），回答：
1. 文件内容是什么
2. 与当前任务相关的内容
3. 如果有文字，精确转录关键文字

用中文回答，简洁。
```

#### 改造现有工具

- `document.rs`：`read_document` 函数对图片/视频/扫描件 PDF 扩展名，走视觉子 Agent
- `image.rs`：`read_image` 工具检查模型能力，不支持时走视觉子 Agent

#### 模型选择

| 模型 | 大小 | 特点 |
|---|---|---|
| `qwen2.5-vl:7b` | ~5GB | 中文友好，OCR 强 |
| `llava:13b` | ~8GB | 通用视觉理解，成熟稳定 |
| `minicpm-v:8b` | ~5GB | 轻量，速度快 |

#### 实施路径

1. `ModelRouterConfig` 加 `vision_model` 字段
2. `document.rs` 和 `image.rs` 加文件类型检测 + 视觉子 Agent 调用
3. 视觉子 Agent 不可用时返回明确错误，让主 agent 知道需要手动处理
4. 可选：缓存同一文件的视觉分析结果

## 四、测试与验收流程

### 4.1 完整流程

```
修复/开发
    ↓
编译检查（cargo build）
    ↓
定向测试（cargo test -p <crate>）
    ↓
真实桌面验收（启动 CodeBuddy，鼠标键盘走用户场景）
    ↓
截图记录（关键步骤截图并脱敏保存）
    ↓
Reviewer agent 自动化验收
    ↓
写报告
```

### 4.2 验收分工

| 层级 | 执行者 | 验证内容 |
|---|---|---|
| 单元/集成测试 | cargo test | 代码逻辑正确性 |
| Reviewer agent | 子 agent | 代码是否满足 acceptance_criteria、是否越界、是否符合规范 |
| 真实桌面验收 | 人工（鼠标键盘） | UI 流程、用户交互、截图、实际体验 |

Reviewer agent 是自动化回归检查，不能替代真实桌面验收。每次改完一个小功能，先走真实桌面，再让 Reviewer 跑自动化检查。

## 五、核心原则

1. 不因工作区范围过大而阻止用户开始任务；先提供目录选择能力，在实际需要写入时再进行授权
2. 安全边界必须在 OS 或运行时层面强制执行，不能仅依赖 prompt 约束
3. 主 agent 决定读什么，工具负责"怎么读"；视觉分析按需触发，不搞全盘预处理
4. 每次修复完成后，先真实桌面验收，再走 Reviewer 自动化检查
