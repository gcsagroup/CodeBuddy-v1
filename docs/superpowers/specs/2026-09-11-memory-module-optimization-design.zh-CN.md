# CodeBuddy 记忆模块优化设计

日期：2026-09-11。复核：2026-09-12。状态：已确认，作为基础版本与后续演进的实现基线。

[繁體中文（默认版本）](2026-09-11-memory-module-optimization-design.md) · [English](2026-09-11-memory-module-optimization-design.en.md)

## 1. 结论

CodeBuddy 应将“固定规则、项目记忆、用户习惯、对话历史”拆成四个逻辑层，而不是继续把它们视为同一种记忆。

- `AGENTS.md` 只存放用户或团队明确确认、需要稳定执行的规则。
- AI 推断的用户习惯保存在用户记忆中，默认不能直接改写 `AGENTS.md`。
- 项目事实与工作经验保存在项目记忆中，必须保持项目隔离和来源信息。
- 完整对话继续保存在 session 数据库，不能复制成大量长期记忆。
- 取消“记忆总条数／总文件大小达到上限后拒绝写入”的产品机制，改为无损归档、按需检索和可观测的磁盘保护。
- 保留单条长度、查询响应、主动注入上下文和安全扫描上限；这些是运行安全边界，不是记忆容量上限。

直接回答“用户习惯是否也写入 `AGENTS.md`”：**不写入**。AI 学到的习惯先进入独立、可审核的用户记忆；只有用户主动点击“转为固定规则”并确认差异后，才写入全局规则文件。

## 2. 背景与现状

当前实现已经具备项目 identity 隔离、跨会话持久化、TTL、CRUD、搜索、分页、导出、备份恢复、active/archive 分层，以及 `project_rule`、`preference`、`verified_fact` 等类型。设置页也已提供 Project Memory 和个性化记忆开关。

当前主要问题：

1. 规则、事实和偏好共享同一记忆通道，权威性不够清楚。
2. AI 推断偏好与用户明确规则的 UI 和数据语义没有充分分开。
3. active 500 条、1 MiB soft／2 MiB hard 等限制容易被理解为“总记忆容量”，并可能让正常写入因容量被拒绝。
4. 自动注入以近期项目为主，相关性、来源和命中原因仍需增强。
5. JSON active/archive 适合当前规模，但长期累积后，全文搜索、更新和一致性成本会增加。

## 3. 参考设计与取舍

### Codex

Codex 将持久指令与生成记忆分开：全局／项目指令使用分层 `AGENTS.md`，历史对话提取内容保存在独立的本地记忆存储。必须遵守的规则应放在 `AGENTS.md` 或版本控制文档中；记忆只是辅助回顾信息。Codex 的项目指令还有主动加载大小边界，因此 `AGENTS.md` 不是记忆数据库。

采用：规则和记忆分层、全局与项目范围、记忆生成和记忆使用分开控制。
不采用：让 AI 静默生成或覆盖项目规则。

参考：[Codex AGENTS.md](https://learn.chatgpt.com/zh-Hans/docs/agent-configuration/agents-md)；[Codex 记忆](https://learn.chatgpt.com/zh-Hans/docs/customization/memories)

### Claude Code、Hermes、Pi 与其他 Agent

可观察到的成熟方案普遍使用“人工维护的指令文件 + 按需加载的历史／记忆 + 有界的当前上下文”。Hermes 类方案重视 session 搜索与全文索引；Pi 类方案保留完整 session、分支与压缩；Claude Code 将人工记忆文件和自动记忆分开。共同点不是无限塞入提示词，而是允许持久存储增长，同时让每次召回保持有界。

采用：持久存储与提示词预算分离、可追溯检索、完整 session 与摘要分离。
暂不采用：第一阶段引入向量数据库、云同步或复杂知识图谱；它们会延长交付时间，而且不能先解决规则污染和跨项目泄漏。

## 4. 目标与非目标

### 目标

- 用户可以在设置中直接管理全局规则；项目规则由系统按工作目录自动识别。
- AI 可以学习低风险、稳定的使用习惯，但这些习惯可查看、删除、停用和升级为固定规则。
- 记忆总量不会因为固定条数或固定总文件大小而停止增长。
- 每次模型调用只注入少量、相关、可解释的内容。
- 不同项目、用户和工作区之间不能互相泄漏。
- 所有写入和召回都能回答“谁写的、为什么写、何时写、来自哪里”。

### 非目标

- 不把全部聊天内容自动转成长记忆。
- 不让 AI 自动修改已经提交的团队规则。
- 第一版不提供跨设备云同步、不使用向量数据库、不建立知识图谱。
- 不通过删除旧记忆管理一般容量。

## 5. 分层架构

### 5.1 对话历史

- 存储：现有 `sessions/sessions.db`。
- 内容：完整消息、工具调用和会话状态。
- 用途：继续原对话、审计和生成候选记忆。
- 不会在每次新对话中完整加载。

### 5.2 项目规则

- 存储：项目根目录或就近目录的 `AGENTS.md`／`AGENTS.override.md`。
- 内容：构建命令、测试要求、代码规范、安全限制和团队流程。
- 写入：用户直接编辑；AI 只能生成草稿或建议差异，必须由用户确认。
- 特性：权威、可版本控制、按目录范围覆盖。

### 5.3 用户全局规则与习惯

- 明确规则：存储在用户电脑的 `.CodeBuddy/AGENTS.md`，由“行为与回答”设置页的多行输入框管理；第一次保存时创建文件。
- 兼容性：旧版 `profiles/<profile>/AGENTS.md` 仅在根目录文件不存在时作为读取回退，不再作为新写入位置。
- AI 习惯：保存在 `profiles/<profile>/memory/user/`，使用结构化记录，不直接写入全局 `AGENTS.md`。
- AI 习惯可以由用户点击“转为固定规则”，预览后加入全局规则。
- 加载顺序：先加载全局规则，再从项目根目录到当前工作目录逐层加载就近规则；同一目录中 `AGENTS.override.md` 优先于 `AGENTS.md`。更近的项目规则只覆盖冲突内容，变更从新会话开始生效。

### 5.4 项目记忆

- 存储：`profiles/<profile>/memory/projects/<project-id>/`。
- 内容：经验、已验证事实、架构决策和近期工作摘要。
- 项目 identity 必须使用规范化路径和稳定 ID；界面显示当前所属项目，避免误删。
- 项目移动／重命名时提供明确的重新绑定或复制流程，不能悄悄合并。

## 6. 设置页设计

记忆设置页分成三个区域：

1. **CodeBuddy 说明**：位于“行为与回答”，提供多行输入框、明确保存按钮、外部修改冲突保护和实际文件位置；写入 `.CodeBuddy/AGENTS.md`，适用于全部新会话。
2. **项目规则自动识别**：设置页不提供手动选择文件夹的卡片。打开项目时从项目根目录到当前工作目录逐层加载规则；工具读写更深层目录时再加载该目录链上的就近规则。系统只读取并注入规则，不复制到记忆数据库，也不自动创建或改写项目文件。
3. **AI 学到的习惯**：卡片列表显示内容、来源、置信度、创建时间和最后命中时间；提供保留、编辑、删除、停用和“转为固定规则”。

保留两个独立开关：

- **使用记忆**：是否在后续对话中检索和注入现有记忆。
- **允许生成新记忆**：是否允许当前对话成为 AI 习惯或项目记忆的来源。

关闭任何开关都不删除数据。删除和清空必须是独立、需要确认的操作。

## 7. 数据模型

每条结构化记忆至少包含：

```text
id, scope, kind, subject, content,
source, source_ref, reason, confidence,
created_at, updated_at, last_used_at,
expires_at, status, schema_version
```

- `scope`：`user` 或 `project`。
- `kind`：`preference`、`verified_fact`、`decision`、`work_summary`。
- `source`：`user_explicit`、`user_approved`、`ai_inferred`、`project_verified`。
- `status`：`candidate`、`active`、`disabled`、`expired`。
- `confidence` 只用于 AI 推断，不能覆盖用户明确规则。
- `source_ref` 对已验证项目事实为必填，而且只能指向当前项目内的安全相对路径。

`project_rule` 不再作为普通记忆类型新增；现有 `project_rule` 在迁移时转成候选规则，由用户决定写入 `AGENTS.md` 或降级为普通项目记忆。

## 8. 写入策略

1. 用户直接在设置中输入的规则，点击保存后写入对应规则文件。
2. 用户在对话中明确说“记住”时，写入 `user_explicit` 或 `user_approved` 记忆。
3. AI 自动学习只接受稳定、低风险的交互习惯，例如语言、回复长度和常用工具；初期写入 `candidate`，由用户确认后转成 `active`。
4. 密码、API key、token、身份证号、支付信息、私密通信内容和一次性任务细节不能成为长期记忆。
5. 相同 scope + kind + subject 使用更新或版本化，不能生成无限重复项。
6. AI 不能将推断内容写入 `AGENTS.md`；只能创建可审核的提升建议。

## 9. 检索与上下文预算

用户可配置层内的优先顺序：

```text
当前对话明确要求
→ 就近项目 AGENTS.override.md / AGENTS.md
→ 用户全局规则
→ 已确认且与任务相关的用户习惯
→ 项目记忆
→ 历史工作摘要
```

系统和开发者策略始终高于以上所有层。

主动注入保持有界，建议第一版总预算为 6,000 字符：规则优先，剩余空间再分配给用户习惯和项目记忆。候选、停用、过期或来源失效的项目不主动注入。

相关性分数由范围匹配、关键词／FTS 命中、记忆类型、用户确认、来源可信度、近期使用和重复惩罚组成。返回时提供简短命中原因；如果没有相关项目，不应为了填满预算而注入内容。

## 10. 取消容量上限的精确定义

应该移除：

- active 500 条作为总容量门槛的产品语义。
- 1 MiB soft／2 MiB hard 导致正常记忆写入失败的总文件限制。
- 任何因“太旧”或“超额”而静默删除用户数据的行为。

应该保留：

- 单条内容、subject、reason 和来源路径长度限制。
- 每次提示词注入、搜索响应、分页大小和工具输出限制。
- 文件损坏、路径穿越、符号链接、秘密和指令注入检查。

磁盘空间不足或数据库不可写时，系统应该拒绝本次写入并显示可操作错误，不能删除已有数据。设置页显示磁盘使用量，但不使用固定配额阻止正常积累。

## 11. 存储演进

### 第一阶段：快速交付

沿用现有文件格式和 ACP 合约，完成规则／记忆分层、设置 UI、候选习惯、独立的 use/generate 开关，以及取消总容量拒绝。active/archive 改成召回层级，不再代表用户容量。

### 第二阶段：数据量增长后

将结构化记忆迁移到 SQLite + FTS5；完整 session 数据库保持独立。通过 schema version、备份、校验、原子切换完成一次性复制迁移，原文件在用户确认前保留。只有固定评测证明 FTS5 无法满足中文和语义召回时，才引入向量检索。

## 12. API 与错误处理

沿用现有搜索、记住、忘记、清空、统计和导出能力，新增或调整：

- 读写全局规则，并从当前工作目录链自动发现只读项目规则。
- 列出候选习惯、批准、拒绝、停用和提升为固定规则。
- 分开设置 `use_memory` 和 `generate_memory`。
- 搜索结果返回 scope、source、confidence、source_ref 和 match_reason。

所有 mutation 使用稳定 request ID 和原子写入。写入失败保留原数据；UI 显示真实后端状态，不能用乐观状态掩盖失败。规则文件存在外部修改时，保存必须检测版本冲突并要求重新加载或比较，不能覆盖他人修改。

## 13. 测试与验收

### 后端

- 规则、用户习惯、项目记忆和 session 不能互相混写。
- AI 推断不能直接修改 `AGENTS.md`。
- use/generate 开关互相独立，关闭不能删除数据。
- 超过旧 500 条和 2 MiB 后仍能写入、搜索和重启恢复。
- 提示词和工具响应仍符合各自预算。
- 不同项目、重命名、过期、并发写入、损坏恢复和低磁盘空间行为可以复现。

### 桌面 UI

- 组件测试覆盖全局说明、保存失败回滚、外部修改冲突，以及手动项目文件夹入口已移除。
- 只有用户明确点击保存才创建全局 `AGENTS.md`；项目 `AGENTS.md` 只自动识别，不修改。
- 候选习惯的批准、拒绝、删除和提升流程。
- 两个开关的四种组合与重启持久化。

### 真实用户流程

从修改后的后端启动 Electron，通过真实窗口、鼠标和键盘完成：设置全局规则、在新对话中验证已有项目规则被自动识别、生成候选习惯、批准后跨项目召回、拒绝后不再召回、重启后状态一致。另用两个项目验证隔离，并检查实际文件、数据库和日志。

## 14. 成功标准

- 100% 的固定规则都有明确的用户写入或批准事件。
- AI 推断习惯直接写入 `AGENTS.md` 的次数为 0。
- 超过旧容量门槛后不丢数据、不停止正常写入。
- 跨项目错误召回为 0；敏感信息持久化为 0。
- 固定评测集上的相关记忆命中率提高，无关主动注入率下降。
- 所有召回项目都能显示来源和命中原因。

## 15. 交付顺序与预估

为了缩短交付时间，基础版本只实现最小闭环：

1. 全局规则输入框、项目 `AGENTS.md` 自动识别、外部修改冲突保护：0.5–1 个工作日。
2. 沿用现有结构化项目记忆，取消总条数/总文件大小拒绝，并保留单条与上下文安全预算：0.5–1 个工作日。
3. 两个记忆开关、后端回归、UI 测试和真实 Electron 关键流程验收：1 个工作日。

单人基础版本预计 **2–3 个工作日**。AI 自动推断习惯、候选批准流程和 SQLite + FTS5 是后续独立里程碑，不阻塞基础版本；用户明确说“记住”的内容仍可进入现有结构化记忆。实施必须在当前脏工作区中遵守文件所有权并逐阶段验收。
