### 当前机制的价值与实际缺口

有价值的检查包括：旧版本不可冒充当前要求；无真实回执不能自报成功；文件证据要对应当前版本；Unknown 不因新的无关工具成功清零；用户停止和服务中断不能成为 Completed。

但它不是全面业务验收。`minimum_completion_evidence_satisfied` 对 change 类任务允许有真实工作区写入、没有验证 observation 的情况通过最低层；明确执行义务与要求覆盖仍在后续校验。它不是“任何改动必跑完整测试”。反过来，模型自选的验证、便利步骤和历史动作可能引入额外交付阻塞。判断检查是否适用，要回到原目标与当前合同，不从最终文案反推。

10/6 三个反例说明不能用同一种宽松/严格政策解决：

- 修车工具确有程序、界面和数据检查；一次无管理句柄启动 Unknown 无法原身份对账，快捷方式写入又缺文件版本。不能说只是文案问题，也不能说所有已完成业务都不存在。
- 库存限定修复有实际成果，但模型多次填错 revision/修订关系。inspect 已提供合法 replaced 路径，不能把它称为 Host 没有任何通路。
- 订单页面有原始浏览器后态，但混合文件/桌面 target 导致 coverage 拒绝；最终改成 workspace_change 后登记成功，浏览器确认没有独立保留为受检义务。不是缺少所有证据，也不是可宣布门槛安全。

当前还有两种不同的循环控制：工具失败按参数指纹累计，恢复重建会清空；部分观察调用因旧工具名排除范围不全而可重置当前计数或算新 distinct success，影响有限预算延长。完成拒绝则比较宿主事实指纹与规范化 gaps，coverage 改参数本身不会必然重置。不能把两者混成“任意换参数就能无限重试”。

此外，证据存储提交/验证失败在 `propose_main_agent_finish` 里同样变成 rejected gap 返回。这里是宿主内部事实链失败，不等于用户业务缺项；即使解释更清楚，也不能要求模型重做业务来修存储。

## 2. Claude：模型可以结束，可配置检查可以要求继续，但必须能停止

[Claude Agent SDK 的公开 loop 文档](https://code.claude.com/docs/en/agent-sdk/agent-loop) 描述：模型不再请求工具时正常结束，ResultMessage 区分正常结束、执行错误及轮次/预算耗尽。SDK 的 success 是执行协议结果，不是独立证明生成程序全部正确。并非每次默认有独立验收员。

[Claude Hooks 文档](https://code.claude.com/docs/en/hooks) 提供可配置 Stop / TaskCompleted 检查：阻止结束时把原因反馈给模型；普通反馈也可让模型继续，不必展示成 hook error。Stop 有循环保护，但工具调用会重置连续计数，不能称为整个任务绝对最多八次。可选 prompt Stop 判断条件不可达时能允许停止；模型不可达判断不证明成功，也不替代效果对账。API 错误走 StopFailure，不用正常完成检查硬逼模型继续。

值得借鉴：检查给明确可处理反馈；正常反馈、错误和不可继续分开；有真实停止出口。不能据此主张所有任务加一个新模型裁判或照搬提示词验收。

## 3. Codex：普通一轮结束与显式持续 Goal 分开

[App Server 公开协议](https://learn.chatgpt.com/docs/app-server) 将 turn 状态、工具 item 状态、正文增量和错误分开；turn/completed 事件里的状态仍可能是 failed 或 interrupted。普通回合停止不等于开发成果已验收。

[Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex) 描述显式持续目标：目标和证据留在当前 thread，在空闲、安全边界检查是否继续；预算耗尽应交代进展和阻塞，不是标完成。模型有证据才能提出目标完成，用户/系统控制其他相应生命周期。它是显式 Goal 模式，不是所有普通聊天默认永远续执行。

[OpenAI Agents API 的恢复指南](https://developers.openai.com/api/docs/guides/agents-api/errors) 另说明：失败或断流后先查保存结果与已发生动作，有限重试，只继续未完成工作。它不证明 Codex 桌面的每个内部恢复分支都这样实现。

值得借鉴：持续授权与一轮结束分清；工作保留在可追踪身份中；有界继续且不重复未知副作用。不能把 goal complete 或 turn completed 当成外部业务零缺陷认证。

## 4. WorkBuddy：可验证的是交付体验，不是私有验收算法

[官方任务管理文档](https://www.workbuddy.cn/docs/workbuddy/Task-Management) 公开进行中、已完成、失败、待处理等状态，并允许在失败或完成后继续同一任务；没有公开决定完成的内部算法、强制证据门槛或防重复效果机制。

[官方任务对话文档](https://www.workbuddy.cn/docs/workbuddy/Conversation) 描述阶段说明、摘要、可展开中间步骤及产物/浏览器面板。它支持体验层的借鉴，不能证明内部事实链正确。

值得借鉴：成果已到哪、用户如何使用更清楚；不能照搬其未知内部完成策略，更不能因用户看不见内部拒绝就断定没有拒绝。

## 5. 准则建议：既不做少，也不做多

这是架构审查准则，不是新增 runtime 状态机、语言分类器、Prompt 清单或冻结基线修订。

1. **把结束回答、完成委托、确认效果分开。** 模型负责结合目标与事实提出语义完成；Host 管引用、版本、权限、派发、效果和终态；UI 只呈现。无需制造第二份业务判断。
2. **验收针对本次有边界的委托，而不是“无穷尽完善”。** 模型先说明合理范围和假设。缺失选择会实质改变成果时再澄清；不能所有请求都强迫用户填表。初版、原型、生产就绪不可互相偷换。
3. **既不悄悄减少必须交付项，也不把自选步骤升级为新硬要求。** 原目标的浏览器确认不能靠改 effect 躲掉；Agent 自选快捷方式或额外探测也不能无条件绑架核心交付。涉及安全未结效果必须另外保留并判断影响，不能仅口头称无关。
4. **必要验证是证据，不是仪式。** 关键要求应有与其对应的行为事实：幂等看重复请求；持久化看重开后的记录；发消息看相应层级的发送/送达事实。语法通过、exit 0、文件 hash 不等于这些行为正确。检查强度与用户要求及风险相称，不默认全量测试或无限探索所有边界。
5. **拒绝理由要区分性质与责任。** 业务漏做应提醒模型补；参数错误应给可修改字段和真实索引；证据已过期回原 owner 重新验证；宿主存储/关联坏了由宿主处理；服务不可用用有界恢复；安全 Unknown 保留原效果身份、对账而非重做。
6. **提醒必须有可执行出口。** 有新事实或新方案时允许合理继续；同一缺口没有新信息且无支持能力时准确交接，不反复打印失败。换参数或成功调用数量本身不是业务进展；也不能因此把所有新方案提前禁止。
7. **辅助失败、核心未完成与危险未知不能一锅煮。** 成品核心已核实，自动打开不是用户必需项，且原事实能支持失败不影响使用与安全时，可以交付成果并解释入口问题。若用户要求店员双击即可使用、失败涉及唯一入口，它就是核心缺口；模型自选的方法也可能承担用户必需结果，不能按动作名称定级。核心功能未核实则明确范围；可能发出/删除/覆盖的 Unknown 不可略过或自动重放。是否整体 Completed 仍需既有 owner 按真实依赖和安全边界判断，不由 UI 扫描文字裁决。
8. **公开正文不等待全部核验，但完整成功的展示须与事实相符。** 保留原正文流式输出；核验期间由真实状态说明仍在核验，不把模型文字封成已验收成品。短暂且已恢复的内部错误放详情；影响交付、安全、授权或需用户选择的问题必须明示。不能删已显示正文伪装未发生。
9. **失败也是一个可用的交付。** 说清已完成、未完成、已知原因/未知原因、已有改动及可用范围、谁能补什么、哪些操作不能重复；保留继续所需身份。不要只给内部审计号、万能“请重试”，也不要承诺没有实现的恢复能力。
10. **检验机制看对抗场景。** 同样要拦住漏做与假证据，也要放过合法证据纠正、合理替代方案；无句柄 Unknown 要诚实停，同目标修改不能缩水；额外便利步骤失败不能自动扩大业务目标。

## 6. 最小对抗验收，不只检查最终绿色状态

| 场景 | 需要证明的行为 | 不可接受的捷径 |
| --- | --- | --- |
| 漏了用户明确要求的数据保留 | 给准确缺项和可用验证能力，模型自行选择补足 | 只写文件/语法通过就宣布全部完成 |
| 实际已满足，但引用版本或参数错误 | 纠正引用后正常收口，不强制重做实现 | 放松版本核验，或再次写一遍当作证明 |
| 成果可用，非必需自动打开失败，原事实支持不影响使用与安全 | 明确核心成果和入口限制，已有结果不作废；若是唯一必需入口则仍按缺项处理 | 按动作名认定非关键，全部标失败，或隐藏可能产生的现实效果 |
| 原动作可能已执行但没结果 | 保留身份，对账或准确交接，不盲重放 | 换工具/换文案就发第二次 |
| 宿主证据保存故障 | 归属内部故障，保留实际成果和诊断 | 要模型重做业务或让用户填内部参数 |
| 验收提案把浏览器义务改成文件义务 | 保留原必需语义和合法修订/拆分路径 | 只因为新 schema 合法就默许减少交付 |
| 开放任务已达合理范围 | 告知本次范围、实际验证与延期项并结束 | 无限加功能、不断找非关键问题；或将原型说成生产就绪 |

本轮没有运行这组新验收；它们是待验证条件，不是 PASS。当前判断不支持删除完成机制，也不支持继续给模型堆大量内部手续。应先查验收义务来源、自动事实关联和失败恢复能力，再决定最小落点；不在此报告预定新 owner。
