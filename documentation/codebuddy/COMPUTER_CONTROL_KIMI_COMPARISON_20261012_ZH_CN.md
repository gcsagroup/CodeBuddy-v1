# Kimi K3 电脑控制对比验收与推荐

日期：2026-10-12（Asia/Shanghai）

## 结论

推荐当前继续使用 **Kimi K3 主 Agent + 现有 qwen_computer 控制器**，主 Agent 优先看图，辅助视觉也配置 Kimi K3，按需调用。Windows-MCP v0.8.8 暂保留为隔离候选，先补接入适配，再决定是否替换。

这里的“现有控制器”是项目已经接入的 qwen_computer MCP，并非恢复过去已移除的自研/组合版。两个方案都通过 MCP 提供工具，比较对象是实现及宿主接入质量。

## 真实验收结果

耗时为导出会话首末消息的秒级跨度，包含模型与工具往返；中止项只代表观测到的运行时段，不是完成耗时。单次探索样本，不是稳定性百分比或统计基准。

|---|---|---|
| 计算器 (63+19)×4 | 通过；93 秒，12 次调用，结果 328 | 经纠错通过；156 秒，26 次调用，结果 328 |
| 微信隐藏到托盘后的恢复与发送 | 通过；89 秒，13 次调用，2 次工具错误后恢复 | 未完成；观测 256 秒，12 次调用，3 次错误，后续工具长时间无进展后停止 |
| 微信已打开时发送 | 未另起重复场景 | 通过；103 秒，8 次调用，1 次错误后恢复 |
| 豆包保留草稿→新聊天→发送→读回复→回原草稿 | 通过；231 秒，15 次调用，0 次工具错误 | 未完成；观测 111 秒，14 次调用，9 次错误，持续 CONTROL_UNAVAILABLE 后停止 |

## 问题及归因

### 1. 宿主对外接控制器的串行调度有缺口（已证实）

agent.rs 的桌面串行分组只匹配 qwen_computer__；desktop_tool_stream.rs 对其余工具采用并发合流。候选计算器第一批 7 次 Click 在约 104 毫秒内启动，完成顺序不同；随后画面出现错误表达式 6+39，Kimi 发现后清空重算。这会抵消候选单次点击较快的优势。调用审计见 kimi-windows-click-order.json。

这属于 CodeBuddy 接入侧问题，不应全部归因 Windows-MCP 上游，也不能只靠提示词要求“别并发”作为长期修复。

### 2. 候选控制状态异常（现象确定，全部根因尚未确定）

23:10–23:11 的 session 20261012_14 出现 unavailable→user→ready；用户明确确认无人操作、无其他控制任务。该轮不得归为人工干扰。

旧候选会话曾保留控制器实例，这是生命周期混杂因素；之后逐会话移除，保证单候选实例的豆包测试仍复现 unavailable，因此多实例并非唯一解释。

前期直接测试日志记录过 AI control indicator 未确认状态切换的异常。它能解释该次异常，但本轮每次 unavailable 尚未取得相同栈，不能全部归为同一根因。模型把 unavailable 描述为“另一方占用”也超出了原始证据。

### 3. 轻量截图与完整树查询存在成本/语义取舍

此前直接工具微测中，候选热态点击加裁剪截图约 0.76–0.78 秒，现有带观察的动作约 1.86–1.93 秒，返回工作量不同，不能作等价倍速承诺。候选完整 Snapshot 曾耗时 27–29 秒。

安装源码还显示，关闭 UI 树采集时会把窗口集合设为空、活动窗口设为 None；若直接输出“No windows found”，模型容易把未采集误解为没有窗口。此类状态需区分。

### 4. 当前方案也有优化空间

现有微信出现两次定位错误后恢复，豆包第一次新对话点击未生效，重新聚焦后完成。大 UI 树、反复截图、长历史和模型往返都有成本。豆包累计输入 token 845545、输出 9606 是多次请求累计量，含重复上下文；不等于单次上下文长度或计费金额。

## 推荐实施次序

1. 当前使用现有 qwen 控制器；Kimi 主 Agent 看图，遇到实际不确定再请求 Kimi 辅助视觉，保持截图和目标窗口绑定。
2. 如继续接入候选，先复用宿主现有桌面调度机制，通过明确的桌面能力/共享输入资源归类来串行执行；不要伪装工具名称获取可信权限。
3. 管理控制器会话生命周期，保证桌面输入单一所有者；停止/切换后正常释放，保留人工接管保护。
4. 定位 indicator/control state 异常；精简不必要全桌面树查询，区分未采集与不存在，限制无进展重试。
5. 完成适配后再进行相同初始条件、多轮交替顺序测试：计算器、隐藏窗口恢复、中文输入、微信唯一发送、豆包草稿保护、遮挡与失败恢复。依据完整任务时间和结果选型。

本轮交付为配置调整、真实对比和方案；上述产品修复尚未实施。当前证据支持“保留现有实现、吸收候选优点”，不足以宣布候选直接替换后更快更稳定。
