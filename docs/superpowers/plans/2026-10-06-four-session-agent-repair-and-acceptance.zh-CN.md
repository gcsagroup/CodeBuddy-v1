## 第一阶段 辨别性验证

库存使用既有 requirement reducer/runtime 测试目标和临时存储，模拟当前 revision 2 的未知 effect：正确 replaced 应提交下一版本；错误 retained、旧版本、静默删除应拒绝且不修改原状态；修正后应可恢复。检查事件重放，不只检查 helper 返回 true。不得修改真实会话数据库、真实订单或伪造 E2E 成功。

本验证证明宿主协议行为，不证明 LLM 一定会正确使用。若正确提案失败，先定位实际失败 owner，再调整该项计划，不预设引擎必有缺陷。

CU 复测前先读取当前自动化能力，确保没有审批遮挡、没有观察者抢焦点。使用隔离网页和假数据，取证以被动截图/录屏及原回执为主。自动化不可用时记 BLOCKED 或 NOT_RUN；不换桌面实例、不注入 DOM、不让脚本代替真实点击冒充验收。

## 第二阶段 搜索工具供给纵向修复

当前事实 owner 是 `AnalysisTools`：当轮 catalog 与 selected 产生 provider 工具定义、扩展说明和只读检查输入。权限仍由原检查和派发边界执行；会话仍由 SessionManager 保存。

比较两条路径：每轮暴露全部只读工具简单，但破坏既有按需加载和上下文预算；新增持久工具状态则增加另一份真相。优先使用会话内成功加载的结构化调用记录，按本轮真实 catalog 重新校验，恢复最近有效选择，不建立持久配置或将历史批准当作当轮授权。

路由说明只引用本轮已供给工具。尚未加载但仍在当前只读 catalog 的调用，不执行，并返回可以重新加载的能力事实；已移除或不存在的工具不复活。真正权限禁止仍保持禁止，不混同缺少定义。模型决定接下来是否加载、改查询或交接。

修复验收同时覆盖：

- 同会话首轮加载搜索、下一轮继续使用，provider surface 和执行检查一致。
- 主动切换已加载工具后，提示不继续宣称旧工具当前可调用；缺定义有准确恢复信息。
- 扩展删除、工具改成非只读、失败加载、伪造成功文本不恢复工具或权限。
- 未选择的工具不实际派发；写文件或不安全 Shell 不因本修复变成允许。
- 搜索服务真实限流仍是工具失败；工具定义可用不等于检索成功，不靠文本关键词修上游 success 包装。
