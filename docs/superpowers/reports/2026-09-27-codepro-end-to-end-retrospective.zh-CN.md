# CodeBuddy 多轮教务 E2E 全链路复盘与推进依据

日期：2026-09-27。性质：会话、运行日志、当前源码、职责地图及设计记录的交叉审查；不是产品验收报告。

## 1. 结论：方向有进步，但完整体验仍未闭环

现在的问题不是“前端全做好了，后端突然坏了”，也不是“模型不会做项目”。七次记录暴露的是几组互相叠加、部分长期未闭合的问题：

1. **做事和解释没有可靠地同行。** 模型有时没调用公开说明工具；有时已经生成了普通说明，却被完成门槛前的正文缓冲路径挡住。没有说明不能一概归因于模型。
2. **执行事实更严格了，但安全收尾和恢复能力没有同步完整。** 拒绝把未知操作当成功是对的；让模型反复提交同一完成提案、用户反复面对内部手续，不是完整的解决方案。
3. **界面更克制了，但删掉重复内容时，也删掉了必要的当前反馈。** 计划变窄、操作可展开、真实增删行数是进步；长时间没有活动行、计划没有进行中、结束时仍无明确交接，会抵消这些收益。
4. **验证过程序与交付可用产品仍是两件事。** 测试脚本通过、网页返回 200、模型说“已完成”，分别只覆盖局部事实；旧项目的监听端口、当前文件版本和服务归属必须一起核对。
5. **工作方式偏向完成切片，缺少共同放行条件。** 历史实施记录已经写出不少正确原则，但后续改动常只验证单层。漂亮界面、编译成功、旧切片测试通过，都不能替代连续用户旅程。

因此，下一批应围绕一个目标收口：**用户发出需求后，能持续知道目前在做什么；异常时知道保留了什么、为什么停、谁来处理；完成时拿到与当前项目一致的真实入口。** 不以日志更少、卡片更多、测试数量更多作为目标。

这不是建议降低完成标准，也不是新增一个替用户猜结果的“总状态”。需要把现有事实接好、解释好，并补足确实缺失的能力。

## 4. 最新失败的拆解：不能用一个解释覆盖五个现象

### 4.1 开场和阶段说明：既有模型未遵循，也有宿主丢弃

确认：最新会话没有成功的 `publish_progress`。现有指令要求先介绍目标和第一步，模型没有遵循。依赖它主动调用特殊工具，无法保证有开场。

但更重要的是，22:57:20–22:57:22 的请求日志记录了约 50 个普通文本分片，说明 Python/Flask 等环境已确认、工作区为空、准备采用 Flask + SQLite；随后才是 `call_h49x5oqc` 的计划更新。这段说明没有进入用户导出的对话。

源码对应：`agents/agent.rs` 在 `uses_main_agent_completion()` 的路径上，把没有伴随完整工具请求的 Text 分片从用户事件中滤掉；文本进入 `last_assistant_text`。同一次模型响应随后调用工具时，不走无工具的最终答复出口；下一次请求开始清空该缓冲。于是正常工具前说明也可能消失。

原意是阻止未验收最终答复抢跑，实际范围覆盖了正常工作说明。这是**完成门槛与公开交流混用一条文本通道**的问题，不是改提示词或打字动画能解决的。

约束：不能直接取消所有正文过滤；只读分析、精确答复、simple-change 和最终完成门槛各有语义。需要分别处理，并保证 UI 和持久化收到同一份公开说明。

### 4.2 `app.py` 一瞬间出现：缺少中途可见数据，根因还未定位到最上游

确认：该请求耗时 93,247 ms，记录的首次有效内容时间为 93,170 ms；解析后日志到末尾才出现完整写入预览和正式 ToolRequest，实际文件写入只用了约 32 ms。输出约 6,098 tokens。

因此，前端“逐字显示”不能凭空恢复这 93 秒中的真实代码分片。当前 OpenAI-compatible 路径确实请求 `stream: true`，解析器也有增量工具参数预览与节流；这些代码存在不代表这一轮上游真的逐段提供了数据。

未知：服务端聚合、代理缓冲、模型接口行为、解析器事件形态之间，哪一层造成延迟。现有 TTFT 排除了部分通知，不是网络首字节时间。下一步应只记录请求 ID、时间、事件种类和字节/分片计数，对照网络到达、解析输出、ACP 发送、UI 接收四个点；不额外记录密钥或完整业务正文。

UX 仍有独立缺口：`BaseChat.tsx` 的会话布局仅在等待用户或压缩时显示兜底活动提示。没有工具预览的 Thinking/Streaming 阶段可能没有任何当前活动行。需要补回诚实的“正在生成/等待模型响应”状态，而不是假装正在写文件。

### 4.3 计划没有进行中：不是少画一个转圈

`todo_write` 当前接受并整段覆盖 Markdown 文本；模型指令模板和 `CodeProPlan` 渲染只表达 `[ ]`、`[x]`。最新第二份计划就是“两项完成、五项待办”，没有进行中事实。把第一个未勾选项自动转成 loading，会造假，暂停时还可能一直转。

默认折叠则是单独的展示选择：原生 `details` 未设置展开，和用户最新“默认展开”的要求不一致，可独立修正。

后续需明确：这是**模型维护的用户工作清单**，不是另建一套调度 DAG。进行中文案可以用 `activeForm` 类表达，但暂停/错误时必须停止动态提示；历史计划保留在原轮次，新计划不能覆盖旧轮结果。若扩展状态/ID/持久化结构，先列兼容和归属方案，不能仅因截图需要就加一套权威状态。

### 5.1 后台进程：旧保守门槛有理由，新能力有进步，历史仍不能擦除

| 工具有没有执行、改了什么 | 执行器真实回执和审计 | 用人话解释、展开回执 | 启动生命周期与旧未知操作对账能力不足 |
| 当前在生成什么 | Provider 实际分片、工具输入预览 | 显示草稿/生成状态 | 上游观测缺口，预览与执行必须区分 |
| 工作清单进行到哪 | 模型维护的清单，受当前运行状态约束展示 | 展示待办、进行中、完成及修改历史 | 当前没有明确进行中表达；不是控制面的完成事实 |
| 运行是否暂停/完成 | Runtime、收敛门槛及结构化终态 | 清楚说明影响与下一步 | 事实严谨但交接内容不足；错误保存不统一 |
| 产物现在能否使用 | 当前文件、匹配版本的检查、所属服务/就绪回执 | 展示真实链接/动作和局限 | 不能把过去的 200 或测试通过变成永久可用 |

公开交流是展示，不授予权限、不登记虚构证据、不终结任务。不能因为担心模型说错话，就丢弃所有正常解释；也不能因为用户想顺畅，就把所有正常解释当成已验证成果。

**职责清晰不等于所有事实都要模型再填一遍。** 模型应负责解释业务覆盖；宿主掌握的调用 ID、生命周期、版本校验应由宿主可靠绑定。减少重复搬运需要有边界的方案，不能另造第二个证据库。

## 7. 哪些做得好，必须保留

- 输入预览与正式可执行工具请求分开，稳定 call ID 关联；不完整 JSON 只供展示。方向正确，不能为了动态感提前执行。
- 增删行数来自真实写入前后和读回确认；未知/过大时不伪造 diff。比按生成 token 或请求文本估算更可信。
- 操作详情折叠、局部滚动、降低 token 数字权重、正文与工具记录分层，确实接近用户“默认看解释，需要才看代码”的目标。
- 当前动作放在末尾、已结束的操作按阶段归档，保持阅读顺序。这是有意义的信息组织，不应回退成满屏终端日志。
- 模式切换复用 ACP，等待后端确认而非 UI 乐观扩大权限；“仅聊天”与权限档位分隔；明确智能模式不等于 Codex 独立审核。这些取舍负责且必要。
- 未知副作用不由模型一句话抹除；暂停后阻止新的未经允许执行；当前补充受管理进程，是改善真正安全能力而非改绿状态。
- 设计记录已经反复强调真实打开入口、保留部分成果、区分编译和 E2E。问题在落实和共同验收，不是完全没有产品意识。

## 8. 因小失大与顾此失彼：应承认的取舍失衡

| 局部目标 | 带来的实际代价 | 应有修正 |
| --- | --- | --- |
| 防止未经验证的最终成功答复 | 普通阶段说明也可能被吞 | 分离公开工作说明与最终交付出口，保留最终门槛 |
| 不再重复展示加载状态 | 没有工具预览时用户完全无感 | 仅在没有真实当前活动时显示轻量兜底 |
| 不猜计划进行中 | 用户始终只见待办/完成 | 补明确展示契约，暂停停止动效，不猜任务 |
| 精简工具噪音 | 成功藏起来、失败长期裸露 | 同时展示当前影响和有证据的恢复关系 |
| 用模型让工具标题更自然 | 与主执行抢额度、重试叠加 | 已知动作确定性表达；非关键增强可取消、可降级 |
| 更严格证据门槛 | 模型反复办内部手续 | 一次具体拒绝对应可执行修复或正常暂停出口 |
| 每次满足一个视觉反馈 | 字号、卡片、固定计划多次摆动，跨层缺口被延后 | 先以完整旅程验收，再在同一信息层级里微调 |
| 尽快提供候选让用户 E2E | 用户成为跨层回归的主要发现者 | 交接前核对关键事件链和候选身份；不拿编译替代 |

我此前实施中的主要偏差：容易把“让用户看懂”拆成新增组件、文案、收缩规则，以这些局部完成作为进展；虽然多次声明 E2E 未做，声明边界本身并不能抵消产品链仍断开的事实。应先解决说明到达、当前活动、暂停交接、真实入口这几条主线。

## 9. UX 的判断不是死板模板，但需要稳定底线

用户想知道每个有意义的步骤，不是每一个内部调用。阅读体验应当像同一个人持续把事情讲清楚，而不是多个子系统分别宣布状态。

- **开场**：立即有已接收/正在准备的诚实状态；有模型说明后讲清第一步。不能在尚无证据时自动写“环境已确认”。
- **过程**：自然语言把相关读文件、修改、运行串起来。正在做的在底部，同一条从生成/执行变为真实回执；历史归档不制造大幅跳动。
- **长等待**：没有新字也不等于死机。显示真正所在阶段和等待，不需要假打字、虚构百分比或一秒一条旁白。
- **计划**：默认可见的窄列表，一次展开就够；当前项有明确状态才动；旧计划不会覆盖新轮任务。计划完成不等于产品验收。
- **出错**：先回答影响和接下来谁处理。技术诊断仍可见，但不用用户把多条红字自己对账。未经验证不能称“已恢复”。
- **暂停**：转圈停止，列出保留的实际成果与具体缺口；因服务限流暂停与因副作用未知暂停，行动建议不同。
- **交付**：已完成什么、检查覆盖什么、当前是否运行、实际入口、剩余局限集中出现。服务停着就不能给无效“打开”；“启动并打开”必须真正负责启动、就绪和失败反馈。
- **尺度**：主说明、操作标题、次要命令、技术详情区分层次，不全部同比缩小。已有 9.6px 浮层辅助文案有可读性风险，不能为了再紧凑继续缩；实际视觉与键盘/屏幕阅读器表现还需产品验证。
- **思考**：可以展示 Provider 明确提供的可展示摘要/内容，但不能把内部路由 JSON 或隐藏推理改名“深度思考”就当作必要公开说明。

例如最新失败应表达：后端文件已保存，页面、数据和验证尚未完成；模型服务暂时限流，本轮暂停；后续继续应从现有文件检查和未完成工作接上。不能声称“核心功能已完成”，也不能只说“任务未完成，请重试”而不交代已保存的东西。这里是建议文案的事实边界，不是新增的当前产品能力。

## 10. 成熟项目对照：借职责和事件设计，不照抄外观或整个框架

本次 OpenAI 部分使用 OpenAI Docs 技能核对官方文档；其他参考也是官方公开文档。WorkBuddy 截图及用户转述可作为交互需求，不作为已由本次审查验证的私有源码事实。此前社区评论是定性启发，不是代表性用户统计。

| 公开设计 | 对 CodeBuddy 有价值的部分 | 不采用 / 不据此推断 |
| --- | --- | --- |
| [Codex App Server](https://learn.chatgpt.com/docs/app-server)：turn 生命周期、同 ID 的 item started/completed、文本 delta、计划更新；agentMessage 可带 commentary/final_answer 阶段 | 交流阶段、操作生命周期、任务终态分开；计划是独立展示输入 | 不照搬整套协议；不认为有 phase 就能证明业务完成；不假设所有模型提供 phase |
| [Claude Agent SDK streaming](https://code.claude.com/docs/en/agent-sdk/streaming-output)：完整消息与启用 partial messages 后的增量事件区分 | 把流式作为明确的接口能力，最终完整消息仍需处理 | 不从“客户端支持流式”推导“LAN 模型这一轮必然逐 token 返回” |
| [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)：恢复可能重新执行节点，副作用需幂等或拆分 | 恢复边界清晰、避免重复副作用、持久状态与线程身份一致 | 不因支持 resume 就直接重放失败 shell；不因此替换整个执行引擎 |
| [Cline task management](https://docs.cline.bot/core-workflows/task-management)：本地任务历史与恢复时的上下文/文件状态检查 | “继续”是接续已有工作，不只是再发一句话 | 不宣称 CodeBuddy 已有完全等价的文件 checkpoint/回滚能力 |

选择原则：优先复用项目已有 Runtime、工具回执、ACP、Todo、会话存储；缺口在适配与责任分层时修这一层。只有现有机制确实无法承担职责，才提出替换。没有证据支持现在整体换成另一套 Agent 框架。

## 11. 计划与交付方式自身也需要修正

- R3 计划仍保留 `FROZEN_FOR_REVIEW` 历史标记，而实施记录说明其后获得批准并推进。不能仅看标题认定从未批准，也不应为本次复盘偷偷改冻结基线。今后在实施记录给出清晰的版本/批准/候选索引。
- `CURRENT.md` 指针早于多份后续实施文档；事实地图同时包含目标 owner 与迁移断点；阅读者容易把目标设计当现状。应有一份当前推进索引，但不要再复制一份状态库。
- 9/25 对话体验设计已经指出普通正文过滤；后续以 `publish_progress` 规避但没有闭合普通说明路径。说明问题不是“第一次发现”，是已知风险未成为验收阻塞。
- 历史报告列出 typecheck、fmt、构建成功并明确 E2E 未执行，证据表述是好的；缺少的是跨层问题尚未闭合时，候选仍被用户感觉为“已经修好了”的交接校准。
- 当前开发后端新鲜度检查只枚举 `goose`/`goose-cli` 等路径，未覆盖 `goose-provider-types`、`goose-providers`。这是静态构建风险，不证明最新一定用旧二进制；后续应在既有脚本中补依赖源码覆盖，再确认实际进程的二进制身份。

## 12. 下一批修复顺序与边界

优先级按用户影响，而不是文件大小。以下状态均为待实施/待验收，不能把本页当已完成清单。

### 批次 A：先让执行过程不失联、失败不失忆

1. **普通说明和最终答复分流。** 先修工具前已经生成的说明丢失，并保证发送与保存一致。保守方案是在实际工具请求到来时释放之前的说明：不需要猜语义，但此前等待仍不是实时流式。长期方案是明确公开 commentary 与 final 的展示契约：不改变完成权威，但涉及公共消息协议时需先确认兼容范围。不能用一个补丁假称两者都已解决。
2. **兜底活动提示。** 只消费现有 ChatState/活跃操作，无工具预览时显示生成/等待状态；有真实操作时避免重复。停止、审批、重连、压缩各有真实出口。
3. **可选模型增强降级。** 核对工具标题和链摘要所有入口，已知 CodePro 动作不用额外模型请求；非关键请求收到限流/取消不继续与主请求竞争。保留其他会话行为，不修改用户全局 provider 配置。
4. **Provider 错误一致交接。** 本地化用户说明，结构化错误仍归原 owner，保存与 UI 一致；429、不完整响应、取消不可混成一种继续建议。重试不重放已完成写入。
5. **构建身份保障。** 补既有新鲜度检查遗漏；不换编译入口、环境或依赖。源码身份、实际加载二进制和验证范围一起交接。

放行条件：正常工具前说明能看到且重载还在；长生成期间不是空白；失败后停止状态明确、导出包含原因；没有新增假完成或越权。未取得这些证据前，不以修好图标/字号作为本批完成。

### 批次 B：计划表达和阶段阅读连续

- 默认展开、单层窄列表可先按明确用户要求调整。
- 比较在现有文本清单中增加明确进行中表达，与增加可选结构化清单条目的成本；前者兼容更轻但 ID/修订关系弱，后者清晰但涉及协议/旧数据兼容。选定前不写第二套计划存储。
- 进行中只由明确输入产生，执行暂停约束动效；完成清单与 RunCompleted 解耦。
- 内部 strategy 通知、旧式图标与普通操作视觉统一；不让内部“已确定策略”冒充用户进展。正常失败和已验证恢复的区分需要关联事实，不能纯靠配色。

放行条件：第一次展开不是二次套娃；多轮计划不互相覆盖；当前执行、暂停、完成均与真实状态一致；阅读位置稳定。

### 批次 C：交付与恢复收口

- 验证 managed process 从启动、归属、就绪到保留/停止的真实链路；端口占用选择空闲端口，不杀未知服务。
- 测试验证对应当前产物和业务要求；测试脚本不能吞异常后以 exit 0 伪装成功，旧检查不能覆盖后续变更。
- 覆盖拒绝必须指向可处理的缺口；同一缺口没有新证据时走明确暂停交接，不继续循环提案。
- 修正恢复入口错误归因；用户续接时先核对原运行、文件和副作用，不机械重跑。
- 交付摘要使用现有权威事实，能打开才给打开；需要启动则由实际动作承担启动和失败反馈。仅链接到文件不等同运行网站。

放行条件：能完整开发并使用一次；也能在中途可恢复失败后接上；不可恢复/未知副作用时安全停下、已有成果清楚，不靠用户证明命令成功。

### 授权和止损边界

用户已经允许按复盘继续修复：已有机制内的消息保存、展示回归、装饰性负载控制、新鲜度漏项可在确认调用链后推进。新增公共消息阶段、结构化计划持久化、证据对账协议、独立审批者或权限变化，应另列方案和迁移边界取得确认；本页不等于这些变更均已批准。

不在本批顺手修生成的 `edu_sys4`，不更换模型/依赖，不整体重写引擎。运行级未知不能降格成可忽略 UI 问题；图标、字号等非阻塞调整不能反过来抢占主链修复。旧数据无法安全恢复时如实保留，不追求所有历史状态“变绿”。

## 13. 最小互补验收集：先证实主线，再扩大

沿用用户此前“不运行测试、由用户 E2E”的约定，本页只设计验收，没有执行。后续若用户授权 Agent 自动验证，再按受影响链路选择；不默认运行全套或再次消耗业务模型。

| 场景 | 必须核对的结果 | 专门防什么回归 |
| --- | --- | --- |
| 普通正文随后工具；以及无工具最终答复 | 前者公开且保存；后者仍经完成门槛 | 为修沉默放开假完成，或继续吞说明 |
| 90 秒生成：真实参数增量 / 上游整块返回两种 | 增量真实更新；无增量也有诚实等待；只有回执才已写入 | 假流式、错误写入时态、死屏 |
| 主请求 429，旁路增强同时存在 | 关键执行暂停，旁路可降级；原因保存；不重复写入 | 重试风暴、英文裸错、导出失忆 |
| 计划更新、多轮、暂停和继续 | 明确进行中才 loading；暂停停止；历史不覆盖 | 前端猜状态、单个固定计划吞多轮上下文 |
| 旧项目占默认端口，新项目启动 | 拒绝冒认；使用自身进程和匹配路由验证 | 对旧应用 HTTP 200 验收 |
| 已知普通命令失败后恢复；后台未知无法对账 | 前者不永久阻塞；后者不洗白且可正常交接 | 所有错误都 unknown，或所有 unknown 都忽略 |
| “继续”遇到模型超时/无效 JSON | 告知内部恢复失败，原任务和已做副作用不变 | 系统错误伪装用户歧义 |
| 完整教务需求到首次使用 | 明确功能范围、真实检查、运行状态、入口及缺项 | 只交付文件数和日志，不交付可用结果 |

这些不是要求模型背诵固定句式。验收的是事实一致性与用户是否能自然理解，不是是否命中预设中文关键词。

## 14. 多轮自查后的修正与剩余未知

第一轮：按七份导出识别反复出现的问题簇。第二轮：对照 CLI/请求日志和消息过滤、执行器、恢复、UI 调用链，检验因果。第三轮：对照职责和成熟产品设计，检查建议是否又制造新权威或靠动画掩盖缺口。

已纠正的判断：

- “模型完全没说话”不成立：最新有一段普通说明被缓冲路径丢弃；开场没按要求发布则仍是另一个事实。
- “前端没流式”不足以解释整段生成：解析后日志也没有中途写入分片。网络层根因未确认。
- “标题润色导致限流”证据不足：确认竞争和重试叠加，不确认首次限流的因果。
- “后台 unknown 就是误判”不成立：输出管道结束超时有真实生命周期风险，不能把长文本截断与它混淆。
- “后续 HTTP 200 已解决旧 unknown”不成立：业务可达性和原操作收口不同，且存在验错项目风险。
- “计划打勾太快就是伪造执行”证据不足：环境检查有真实回执；问题是缺少解释、设计决策缺可见过程，不能据速度本身判假。
