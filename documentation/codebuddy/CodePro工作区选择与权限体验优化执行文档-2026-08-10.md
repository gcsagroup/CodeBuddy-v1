# CodePro 工作区选择与权限体验优化执行文档

> **For agentic workers:** 实施本计划时，必须逐任务执行、逐任务测试、逐任务审查。不得跳过失败测试进入下一任务；不得自行创建分支或 worktree。涉及 UI 的任务必须在自动化测试通过后，用真实 Windows 桌面、鼠标和键盘完成用户验收。

**状态：** 已提议，等待产品确认后实施  
**日期：** 2026-08-10  
**适用项目：** `D:\CodeBuddy`
**目标：** 消除磁盘根目录场景下“只能取消、无法继续”的交互死路，同时避免把整个磁盘默认授予 Agent 作为可写项目。

**架构原则：** 工作区回答“在哪里工作”，权限模式回答“允许做什么”，两者在数据和执行层保持独立。MVP 只解决安全进入真实项目目录的闭环；整盘只读、渐进授权和 OS 级沙箱按验证结果分阶段交付。

**技术栈：** Electron 41、React 19、TypeScript 5.9、Vitest 4、Playwright 1.58、Rust/goose Agent Core。

## 1. 给项目经理的一页结论

### 1.1 当前问题

当用户当前目录为 `D:\` 等磁盘或共享根目录时，CodePro 显示“不能直接使用磁盘或共享根目录”，同时禁用“确认并开始”。界面没有“选择已有项目”或“新建项目”的操作，用户只能取消。

这不是安全限制本身的问题，而是产品只阻止风险，没有提供继续完成目标的安全路径。

### 1.2 MVP 决策

MVP 不直接开放整个 `D:\` 作为可写项目，而是在根目录确认卡中提供：

1. **选择已有项目文件夹**：打开系统目录选择器，选择后重新检查并确认。
2. **新建项目文件夹**：打开支持创建目录的系统选择器，默认从当前磁盘开始。
3. **返回修改需求**：保留用户输入，不清空草稿。

根目录卡片不再出现一个永远不可点击的“确认并开始”。

### 1.3 不进入本次 MVP 的内容

- 不把 `D:\` 默认设为可写项目根目录。
- 不承诺“只读整个磁盘”，直到所有文件工具、Shell、MCP 和 Provider 的只读边界完成真实验证。
- 不新增一套与现有 `GooseMode`、`PermissionInspector`、工具审批 UI 重复的权限系统。
- 不在 MVP 中建设完整 OS 级沙箱。
- 不修改 TaskDAG 的并行调度和证据模型，除非测试证明现有相对 scope 在新流程中失效。

### 1.4 交付判断

完成后，用户即使从 `D:\` 发起任务，也能在一次引导内进入已有项目或创建项目，不再被迫取消；Agent 最终仍只在用户确认的项目目录内开始执行。

## 2. 已验证事实与尚待验证事项

### 2.1 已验证的仓库事实

| 事实 | 代码依据 | 结论 |
|---|---|---|
| `filesystem-root` 不能确认 | `ui/desktop/src/components/codepro/WorkspaceConfirmationCard.tsx` 的 `canConfirm` | 当前禁用是显式产品行为，不是偶发错误 |
| 根目录卡片只有取消和禁用确认 | 同一组件 | 当前流程确实形成死路 |
| 项目目录在确认后才创建 | `ui/desktop/src/codepro/projectWorkspace.ts`、`startCodeProSession.ts` | 可继续保持“先确认、后写入” |
| 已有原生目录选择 IPC | `ui/desktop/src/main.ts` 的 `directory-chooser`、`preload.ts` 的 `directoryChooser` | MVP 应复用现成能力，不重复开发文件选择器 |
| 已有运行时工具审批 | `crates/goose/src/permission/permission_inspector.rs` | 不应声称 CodePro 完全没有运行时权限机制 |
| 已有权限等级 | `AlwaysAllow / AskBefore / NeverAllow` | 可复用现有授权语义 |
| 已有权限分类 | `ReadOnly / WorkspaceWrite / ExternalWrite / HighRisk / Forbidden` | 后续渐进授权应扩展现有分类，不另建平行体系 |
| TaskDAG 使用工作区相对 scope | `planner_agent.rs`、`coordinator/validation.rs` | 工作区为根目录会增加风险，但不会自动把所有 scope 变成 `D:\` |

### 2.2 尚待验证，禁止当成事实写入完成报告

- `chat` 或其他现有模式是否能保证所有 CodePro 工具严格只读。
- Shell 子进程在 Windows 上是否受到与内置文件工具一致的路径边界约束。
- 外部 MCP 工具是否都提供可信、不可伪造的权限分类。
- 根目录下的 glob、grep、索引和 Git 探测是否有统一的深度、数量和时间上限。
- CodePro 当前是否具有覆盖所有执行路径的 OS 级文件系统沙箱。

以上事项必须通过代码追踪、自动化测试和真实桌面实验验证，不能仅根据类型名、文案或模型提示推断。

## 3. 外部产品参考与取舍

### 3.1 Codex

公开文档显示，Codex CLI 将启动目录视为项目，也允许使用 `--cd` 指定目录；默认通过沙箱限制写入工作区，越界行为进入审批。CodePro 采用“明确工作目录 + 边界内顺畅执行”的原则，但不推断 Codex 对 Windows 磁盘根目录的具体 UI 行为。

参考：

- https://learn.chatgpt.com/docs/projects
- https://learn.chatgpt.com/docs/agent-approvals-security
- https://learn.chatgpt.com/docs/sandboxing

### 3.2 Claude Code

Claude Code 将工作目录和权限模式分开，支持 Manual、Accept edits、Plan、Auto 等模式，也允许增加额外目录。CodePro 采用“目录与权限正交”的模型；MVP 不照搬全部权限模式，也不新增与现有 goose 权限系统重复的实现。

参考：

- https://code.claude.com/docs/en/permissions
- https://code.claude.com/docs/en/desktop

### 3.3 Hermes Agent

Hermes Desktop 支持指定初始工作目录并限制仓库扫描根目录；Hermes 的安全文档还区分安全写入根和敏感路径保护。CodePro 采用“扫描范围、写入范围、敏感路径保护分别治理”的思想，但 MVP 只交付工作区选择闭环。

参考：

- https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/desktop.md
- https://hermes-agent.nousresearch.com/docs/user-guide/security/

### 3.4 CodePro 的采用与拒绝

| 项目 | 采用 | 拒绝或延期原因 |
|---|---|---|
| 工作目录和权限模式分离 | 采用 | 降低概念混淆，便于后续扩展 |
| 根目录场景提供可继续路径 | 采用 | 当前流程损害核心体验 |
| 复用系统目录选择器 | 采用 | 成熟、可访问、维护成本低 |
| 默认开放整盘写入 | 拒绝 | 项目身份、性能和误操作边界过大 |
| 新建一套权限引擎 | 拒绝 | 现有 `PermissionInspector` 已具备基础能力 |
| MVP 同时建设 OS 沙箱 | 延期 | 需要独立威胁模型和跨平台验证 |

## 4. 产品交互设计

### 4.1 普通项目目录

普通目录、缺失的具体项目目录和现有 Git 仓库继续沿用当前确认流程：

```text
确认项目工作目录
D:\CodeBuddy
已存在且包含文件 · 检测到 Git 仓库

[返回修改] [确认并开始]
```

### 4.2 磁盘或共享根目录

根目录使用专用引导，不显示禁用的“确认并开始”：

```text
请选择具体项目目录

当前位于 D:\。为避免扫描或修改无关文件，CodePro 需要先进入一个具体项目文件夹。

[选择已有项目文件夹]
[新建项目文件夹]
[返回修改]
```

交互要求：

- “选择已有项目文件夹”打开系统目录选择器。
- “新建项目文件夹”也使用系统原生目录创建能力，不自研文件管理器。
- 用户取消系统选择器后仍停留在当前引导卡，需求草稿保持不变。
- 用户选中另一个磁盘根目录时，继续显示根目录引导，不进入循环报错。
- 用户选中文件而不是目录时，显示可理解错误并允许重新选择。
- 用户选中具体目录后，必须重新调用 `inspectCodeProWorkspace`，不得绕过规范化、junction 解析、可用性检查和 Git 检测。
- 只有重新检查后的 `missing / empty-directory / non-empty-directory` 才能进入现有确认流程。

### 4.3 文案规范

中文：

- 标题：`请选择具体项目目录`
- 说明：`当前位于 {root}。为避免扫描或修改无关文件，CodePro 需要先进入一个具体项目文件夹。`
- 主操作：`选择已有项目文件夹`
- 次操作：`新建项目文件夹`
- 返回：`返回修改`
- 选择器取消后不显示错误。
- 检查失败：`无法使用所选目录，请重新选择。`

英文：

- Title: `Choose a project folder`
- Description: `CodePro is currently at {root}. Choose a specific project folder to avoid scanning or changing unrelated files.`
- Primary: `Choose existing project`
- Secondary: `Create project folder`
- Back: `Back to request`
- Error: `The selected folder cannot be used. Choose another folder.`

### 4.4 可访问性

- 操作必须使用真实 `button`，不能用可点击 `div`。
- 根目录卡首次出现时，焦点落到“选择已有项目文件夹”。
- 原生选择器关闭后，焦点返回触发按钮。
- 加载期间按钮禁用并显示可读状态，防止重复打开选择器。
- 错误使用 `role="alert"`。
- 状态不能只依赖颜色表达。

## 5. 数据和接口设计

### 5.1 保持不变

- `CodeProWorkspaceInspection.state` 继续保留 `filesystem-root`。
- `startCodeProSession` 继续只接受 `missing / empty-directory / non-empty-directory`。
- `confirmCodeProWorkspace` 继续在主进程中重新验证状态和规范化身份。
- 项目仍在确认成功后才持久绑定。

### 5.2 UI 新增接口

`WorkspaceConfirmationCard` 增加根目录操作回调：

```ts
interface WorkspaceConfirmationCardProps {
  candidates: CodeProWorkspaceInspection[];
  confirming: boolean;
  choosingDirectory: boolean;
  error: string | null;
  onConfirm: (candidate: CodeProWorkspaceInspection) => void;
  onChooseDirectory: (root: CodeProWorkspaceInspection) => void;
  onCreateDirectory: (root: CodeProWorkspaceInspection) => void;
  onCancel: () => void;
}
```

回调只发出用户意图，不直接创建会话。

### 5.3 目录选择 IPC 调整

复用现有 `directory-chooser`，允许传入默认路径：

```ts
directoryChooser: (defaultPath?: string) => Promise<Electron.OpenDialogReturnValue>;
```

主进程必须校验 `defaultPath` 是非空字符串后才传入 Electron；无效值回退到 `os.homedir()`。选择器继续使用：

```ts
properties: ['openDirectory', 'createDirectory']
```

不得接受 Renderer 自行传入任意 Electron dialog 配置。

### 5.4 选择后的统一流程

```text
用户点击选择或新建
  → 打开原生目录选择器
  → 用户取消：保持根目录引导
  → 用户选中路径：inspectCodeProWorkspace(prompt="", selectedWorkingDir=path)
  → 仍是根目录：继续显示引导
  → 是具体目录：显示现有确认详情
  → 用户确认：confirmCodeProWorkspace
  → findOrCreateCodeProProject
  → createSession
```

选择器结果永远不能直接传给 `createSession`。

10. 确认项目并开始，验证会话实际绑定所选目录。
11. 重启应用或新建会话，验证最近目录和项目身份没有产生重复项目。
12. 检查控制台与主进程日志，无新增未处理异常。

- [ ] **Step 4：记录证据**

交付报告必须包含：

- 实际运行的命令。
- 自动化测试通过、失败和跳过数量。
- 真实验收所选目录。
- 取消、重选、确认和重启后的可见结果。
- 截图路径和日志结论。
- 已知无关失败及其证据。

当前任务产生的新回归未解释前，不得进入下一功能。

---

## 7. 第二阶段：只读根目录验证，不与 MVP 混合交付

第二阶段先做技术验证，再决定是否向用户展示“仅浏览 D:\”。验证任务必须覆盖：

1. 内置文件读取、搜索和列表工具。
2. 内置文件写入、补丁和删除工具。
3. Shell/PowerShell 子进程。
4. Codex、Claude Code 及其他 Provider 适配器。
5. MCP 工具和动态扩展。
6. junction、symlink、UNC 路径和大小写归一化。
7. 搜索深度、结果条数、耗时和取消能力。

通过标准：

- 所有写入尝试都被宿主可靠拒绝或要求明确授权。
- 不能通过 Shell、重解析点或外部 MCP 绕过。
- 全盘读取不会因默认递归搜索导致界面长时间无响应。
- UI 能清楚显示当前是只读模式，并允许用户改选具体项目。

任何一项未通过，都不得把“仅浏览整盘”标记为可交付功能。

---

## 8. 第三阶段：高级整盘工作区与 OS 级隔离

只有在独立威胁模型评审通过后，才考虑“使用 D:\ 作为工作区”。最低要求：

- OS 级文件系统边界覆盖 Shell 及其子进程。
- 明确的允许写入路径和永久禁止路径。
- 敏感目录、凭据和系统元数据不可通过用户普通授权解锁。
- 删除、批量移动、覆盖、外部发布保持高风险审批。
- 扫描策略与写入策略分离。
- 授权状态具有会话/任务作用域、失效机制和可审计记录。
- 管理员可以禁用高级整盘模式。

该阶段应单独编写 ADR 和实施计划，不得直接扩展本 MVP 文档中的 UI 回调完成。

## 9. 验收标准

### 9.1 MVP 必须满足

- [ ] 根目录场景不存在无后续路径的禁用主按钮。
- [ ] 用户能选择已有项目目录。
- [ ] 用户能通过原生目录选择器创建项目目录。
- [ ] 取消选择不丢失需求草稿。
- [ ] 新路径经过完整 inspection 和 confirmation。
- [ ] 普通项目目录行为无回归。
- [ ] 多候选目录选择行为无回归。
- [ ] junction/规范化身份行为无回归。
- [ ] 项目持久绑定不产生重复 Project。
- [ ] 聚焦测试、完整桌面测试、类型、lint、格式检查通过。
- [ ] 真实 Windows 鼠标键盘验收通过。

### 9.2 MVP 明确不宣称

- 不宣称整个磁盘已经安全可写。
- 不宣称已有权限模式等同于 OS 沙箱。
- 不宣称所有外部 MCP 都受相同路径策略保护。
- 不宣称根目录全盘扫描性能已经解决。

## 10. 风险与回滚

| 风险 | 控制措施 |
|---|---|
| 选择器返回根目录导致循环 | 重新 inspection，并继续显示根目录引导 |
| 用户取消后输入丢失 | `pendingStart.initialMessage` 在取消 dialog 时不变 |
| 选择结果绕过安全确认 | 强制经过 inspection → confirmation → project binding |
| 异步重复点击打开多个 dialog | 使用 `choosingDirectory` 锁定操作 |
| 普通目录流程回归 | 保留现有普通目录单元测试和 E2E |
| 新建项目产生目录垃圾 | 只由用户在原生选择器中明确创建，不静默生成时间戳目录 |

回滚只需恢复根目录卡片旧分支和新增回调，不涉及项目数据迁移。已经由用户明确创建的目录属于用户数据，回滚时不得自动删除。
