# SecVibe 接入 CodeBuddy 的技术调研报告

日期：2026-10-23（北京时间）  
对象：https://secvibe.gcsa.com/  
本地架构核查：`D:\CodeBuddy-v1`，`main`，`09b0219`，含既有未提交修改。  
状态：公开资料调研与接入建议；尚未接入、调用审计接口或验证检测效果。

## 1. 结论

建议给 CodeBuddy 增加一个外部安全审查能力：Agent 完成代码修改和功能测试后，将本次变更及必要上下文交给 SecVibe 审查；收到漏洞位置、证据和修复建议后，由 CodeBuddy 修复、跑测试并再次审查，最终交付代码及安全检查报告。

**本次需求是把安全审查接入开发流程。CodeBuddy 继续使用 DeepSeek Harness 负责执行、调度、权限、恢复及任务完成，SecVibe 负责提供安全审查结果。**

架构上存在可复用的接入点；当前主要前提尚未确定：SecVibe 是否向第三方提供受支持的审计 API/MCP、结果格式及使用许可。官网有完整安全 Agent 产品，不等于已确认存在开放审计 API。应先向供应方取得接口资料，再做小规模闭环验证。

## 2. 一次实际使用会是什么样

以“开发登录接口”为例：

1. CodeBuddy 生成接口并运行功能测试。
2. 对获准审查的文件生成固定快照，附带相关调用、配置和依赖信息。
3. 调用安全审查工具，检查可能的注入、鉴权遗漏或凭据泄露等风险。
4. 若返回某文件某行存在风险，界面展示证据、严重程度与建议；Agent 在现有权限范围内修复。
5. 再跑功能测试与安全复检，报告修复项、未解决项及检查范围。

这与“让主模型自己说代码安全”有区别：最终展示应以外部审查工具的真实回执为依据。零条告警只代表本次范围内未检出问题，并非绝对安全保证。

## 4. 建议的接入方案

```text
用户请求 / 已启用的项目审查策略
                 ↓
CodeBuddy · DeepSeek Harness
                 ↓  原生工具发现、权限与执行
SecVibe 审查工具（必要的轻量适配）
                 ↓
供应方官方 MCP 或审计 API
                 ↓
结构化结果 + 报告 + 源码快照标识
                 ↓
Harness 驱动修复 → 功能测试 → 复检 → 向用户交付
```

接入顺序：

| 供应方提供的能力 | 建议 | 条件 |
| --- | --- | --- |
| 官方 MCP 服务 | 优先复用现有 Harness MCP 桥接 | 验证工具输入输出、身份认证及异步能力 |
| 稳定审计 HTTP API | 薄适配为 Harness 工具；供应方如有官方 SDK 优先复用 | 有接口版本、认证、状态和结构化结果约定 |
| 仅非交互 CLI | 作为候选备用路径，在隔离工作目录执行 | 实测参数、退出码、结构化输出、取消与许可；确认实际数据流向 |
| 只有交互式聊天产品 | 可作为人工审查入口 | 暂不承诺自动审查与自动修复闭环 |

成熟机制依据：MCP 定义了工具发现、调用、结构化返回值与输出 schema，可用于审查能力接入；这不是 SecVibe 已实现 MCP 的证据。[MCP 官方工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

不把整个 SecVibe/Pi 运行时嵌入 CodeBuddy，也不在适配层另造 Agent 调度器。即使供应方内部使用 Agent，它对 CodeBuddy 仍是边界明确的外部审查任务。

## 5. 当前项目可复用的部分

| 现有文件 | 已有职责 | 接入时如何使用 |
| --- | --- | --- |
| `runtime/harness/profile.mjs`、`runtime/harness/index.mjs` | Harness 插件组合、Agent 与工具执行 | 保留权威归属，通过现有工具机制调用审查 |
| `runtime/harness/mcp-bridge.mjs` | MCP 连接、工具注册和调用适配 | 官方 MCP 可直接优先对接 |
| `runtime/harness/mcp-tasks.mjs` | 协商后的 MCP Tasks 支持 | 仅在对方声明且实际支持时使用异步任务 |
| `runtime/mcp-settings.mjs` | 当前默认 MCP 同步调用超时 300 秒 | 非异步服务按实际时长与配置处理，超时不得报告审查通过 |
| `runtime/harness/tool-discovery.mjs` | 工具按需加载 | 不将全部扫描规则和工具定义注入每轮上下文 |
| `runtime/secrets.mjs`、`runtime/settings.mjs` | 凭据和设置边界 | 复用已有凭据存储，密钥不进入提示词或普通日志 |

首版可用现有工具调用记录、报告文件和聊天展示。专用漏洞面板属于后续可选工作，不作为首次接通的前提。异步服务任务状态只是外部作业状态，不接管 Harness 的任务完成判定。

## 6. 审查输入、结果及可靠性要求

以下是拟议的适配需求，并非 SecVibe 官方 API 字段或接口地址：

- **输入**：项目标识、请求 ID、基线 revision、本次未提交改动及新文件的内容哈希、获准文件清单、关联代码上下文、所选检查类别。
- **结果**：审查 ID、运行状态、检查范围与覆盖缺口、报告位置、耗时和费用信息（如供应方支持）。
- **问题项**：稳定问题标识、相对路径/行号、规则或 CWE、严重程度、证据、修复建议；置信度仅在来源有定义时保留。
- **版本绑定**：报告绑定实际扫描的快照。审查过程中代码改变，报告应标明过期；修复后针对新快照复查，不沿用旧结论。
- **失败区分**：鉴权失败、限流、超时、服务故障、取消、部分完成与成功无告警分别展示，空列表不能掩盖失败或缺失覆盖。
- **长任务**：复用已有 Tasks/服务任务 ID 做进度查询与取消。重试遵守供应方幂等约定，避免重复上传、扫描和计费；长扫描不靠无限延长同步连接解决。
- **上下文**：默认审查本次变更及必要的关联上下文。只传 diff 可能漏掉跨文件问题；供应方若仅支持整仓输入，应先重新确认数据范围与成本。
- **自动修复**：Agent 消费结构化发现并通过原有工具修改；保留误报复核与停止条件。外部报告中的文本不获得新的执行权限。

自动触发可放在代码修改与基础测试之后。若要求“未通过安全审查就不交付”的硬门槛，需要单独明确项目策略，并接入现有 Harness 生命周期；仅写一条提示词不能保证每次必查。本轮不更改公共协议或任务完成语义。

## 7. 首版范围与数据边界

建议先选一类已确认可调用的代码审计，再根据供应方实际能力加入依赖风险和密钥检查。起步采用用户主动调用；通过验收后再为指定项目启用自动审查与受控修复。

源码外发需明确接收方、范围、保存期限、是否用于训练及删除方式。默认排除构建缓存、无关目录、真实凭据和越界软链接；密钥检测使用合成样本验收。若远端服务需要含真实秘密的内容，先确定相应数据策略。本地 CLI 仍可能调用云模型，“本地运行”本身不证明源码不出设备。

本次读取的 Cloud 隐私协议（页面注明更新于 2026-09-26）说明：项目内容在云端处理；相关上下文可能交给所选模型提供方；会话与项目一般保留至删除或账户移除，部分备份/安全记录可能继续保留有限时间。这是官方条款说明，尚未独立验证实际处理；商业审计 API 的具体条款仍需确认。[来源](https://secvibe.gcsa.com/privacy/zh-CN/)

商业接入、CLI 再分发、规则复用和品牌使用条件均待对方确认。只读网页调研并不包含上传公司私有代码或接受付费条款。

## 8. 验收与实施顺序

| 阶段 | 工作与交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 接口确认 | 官方接口说明、测试凭据配置方法、样例结果、费用与数据条款 | 明确可调用合同和获准数据范围 |
| 最小验证 | 隔离样例项目：一次审查、一次可验证修复、一次复检 | 取得真实服务回执，并与源文件版本对应 |
| 产品接入 | 工具按需加载、设置凭据、报告与错误展示、任务取消 | 自动化测试通过，再在 Electron 中完整走通 |
| 稳定性 | 多文件变更、较大项目、限流/断线、取消恢复、重复调用 | 不误报通过、不重复修复或扫描，不破坏原功能 |
| 项目策略 | 明确自动触发范围、修复预算、人工复核和交付条件 | 策略经确认后启用 |

验收样本同时包含已知漏洞、已修复版本及无漏洞对照；至少检查路径/行号、证据、误报处理、服务错误不冒充成功、旧报告失效、跨文件上下文和修复后的功能回归。统计检测命中、误报、扫描时长及费用，并记录实际检查范围。具体排期应在获得可用接口并完成最小验证后给出。

## 9. 发给 SecVibe 方的问题清单

1. 是否提供供第三方产品使用的代码安全审查 HTTP API、MCP 或非交互 CLI？请提供官方版本化文档和最小调用示例。
2. 审查凭据如何申请？模型 API Key 和产品审查凭据是否独立？是否有测试额度及限流说明？
3. 输入支持文件、diff、压缩包还是仓库？是否支持未提交及新增文件？语言、文件大小和项目规模限制是什么？
4. 能否提供包含文件位置、证据和严重程度的 JSON/SARIF 或其他结构化结果样本？如何表示部分覆盖与执行失败？
5. 长扫描如何提交、查询、取消、恢复及去重？是否真正支持 MCP Tasks？
6. 源码、依赖信息和密钥样本发往哪些服务，保存多久，是否用于训练？是否支持私有化部署？
7. 计费、商业嵌入、CLI 再分发、规则使用、版本兼容和技术支持条件是什么？

## 10. 可直接转发给经理

> 我理解的目标是为 CodeBuddy 增加安全审查闭环：Agent 写完代码并完成基础测试后，调用 SecVibe 检查本次变更，把漏洞位置、证据和建议返回，再由 Agent 修复、测试和复检。CodeBuddy 继续由 Harness 主导，SecVibe 作为审查工具接入。我已核实它有安全审计产品与 CLI 发布，但尚未确认稳定的第三方审计 API；设置里的模型 API Key 也不等于审计接口。下一步需要对方提供 API/MCP 文档、测试凭据申请方式、结构化结果样例和源码数据条款，先跑通隔离样例，再纳入产品自动流程。
