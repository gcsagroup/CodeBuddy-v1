# 项目分析报告技术证据引用修复设计

## 背景

普通“项目分析报告”由 `codepro_report.rs` 独立渲染，不经过 LLM 辅助终态报告管线。当前清洗器为了避免在正文暴露完整路径和命令，会把匹配到的技术证据值替换成 `【详见技术证据】`。该占位符会直接显示给用户，破坏报告的自然语言体验。

## 目标

- 项目分析报告正文不再出现 `【详见技术证据】`。
- 正文继续保留发现或建议的语义，不因隐藏路径、命令而删除整句话。
- 完整路径和命令仍只显示在宿主生成的折叠技术证据中。
- 不修改 LLM 辅助终态报告、结果聚合器或其他报告类型。

## 方案

在 `sanitize_analysis_text` 的宿主清洗阶段，根据证据类型使用自然语言指代替换完整技术值：

- `路径`证据替换为“相关文件”；
- `命令`证据替换为“相应检查”；
- 其他证据类型替换为“相关证据”。

清洗结束前再将输入文本中已有的精确占位符 `【详见技术证据】` 归一化为“相关证据”。这既修复宿主当前主动生成的占位符，也防止模型原文携带同一占位符穿透。

折叠技术证据继续使用原始 `AnalysisReportEvidence`，因此不会丢失完整路径、命令、失败标记或去重与数量上限行为。

## Codex 对照

本次对照范围是当前 Codex 桌面端的可观察交互，不推测其私有内部实现。可观察基准是：面向用户的结果使用自然语言说明结论和限制，命令、路径等执行细节保留在工具活动或技术上下文中，而不是在正文显示未解析的占位符。

CodeBuddy 采用这一用户体验原则：正文使用“相关文件”“相应检查”等可直接阅读的指代，原始证据继续由宿主放入折叠技术证据。CodeBuddy 不照搬 Codex 的具体报告结构，因为普通项目分析报告已有固定四章节合同，本次只修复证据引用措辞。

当前环境抓取 Codex 官方手册时返回 HTTP 403，官方开发者文档 MCP 也无法在本会话注册。因此以上仅作为明确标注的产品行为对照，不作为 Codex 内部架构事实；实施不依赖未经验证的内部机制。

## 数据流

1. Agent 生成四段项目分析正文。
2. 宿主收集路径和命令证据。
3. `sanitize_analysis_text` 将正文中的完整技术值替换成按类型选择的自然语言指代。
4. `render_analysis_report` 使用清洗后的正文生成四个固定章节。
5. 宿主将未经改写的完整证据追加到折叠技术证据区。

## 边界与错误处理

- 空证据值继续忽略。
- 多个证据值按长度降序替换，避免短路径先替换而破坏长命令匹配。
- 未知或本地化后的证据类型使用“相关证据”，不暴露原值。
- 不尝试用正则猜测未被宿主记录的路径或命令；本次只修复已有证据替换产生的占位符。

## 测试与验收

先添加失败回归测试，证明当前实现会泄漏占位符。测试至少验证：

1. 正文中的路径被改写为“相关文件”，且不包含完整路径或占位符。
2. 正文中的命令被改写为“相应检查”，且不包含完整命令或占位符。
3. Agent 原文自带的 `【详见技术证据】` 被改写为“相关证据”。
4. 折叠技术证据仍包含原始路径和命令。

实施后运行目标单元测试、`goose` Rust 全量库测试，并在桌面应用中执行一次普通项目分析流程，确认用户可见正文和折叠证据符合设计。

## 非目标

- 不引入新的 LLM 调用。
- 不改变终态报告 schema、事实模型或 fallback 模板。
- 不处理未进入 `AnalysisReportEvidence` 的任意敏感文本识别。
- 不重构项目分析报告的章节结构。
