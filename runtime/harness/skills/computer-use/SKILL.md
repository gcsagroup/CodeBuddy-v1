# Computer use / 电脑控制 / 電腦控制

Use the configured desktop MCP to operate Windows or macOS applications. This guide is instructions, not a grant of permission or proof that the controller is connected.

On macOS, local FORMS means the FluidUse CoreML field matcher built into `get_app_state(form_entities=...)`. It is ready through that tool; using it requires no workspace file search, source inspection or shell command.

## Discover before acting

1. Loading this skill reveals the connected entry tools and current availability. Use those schemas directly. Only discover additional tools through `search_mcp_tools` by exact `names`; do not search again for tools already loaded.
2. If the tools are absent or disconnected, explain that specific limitation and how to enable the computer-control extension for this chat. Do not treat a missing schema as proof that an application is absent. Do not silently replace unavailable or rejected desktop input with shell UI automation.
3. `mcp__qwen_computer__list_apps` lists visible windows, not installed applications. Select the exact returned window identifier. Do not invent an English application name when the returned name is localized; keep separate windows and popovers distinct.
4. Observe that exact window with `mcp__qwen_computer__get_app_state` before any click, key or text input. Use the current control evidence; request a full visual observation when the controls cannot answer the question. Never start with `press_key` or assume that the previously frontmost app still has focus.

`window_title` declares an immutable exact-caption restriction; it is NOT a search query or a description of the task. Normally begin with `list_apps({"window_title":""})`, select a returned window identifier using the requested app/document and current observations, then inspect that exact window before input. Descriptions such as a current customer form, an invoice to edit, or a named open file do not supply the application's complete caption: do not invent, translate or shorten a caption from them. Use a nonempty `window_title` only when the user explicitly requires that exact window caption. An empty caption restriction does not authorize unrelated windows or writing before target verification.

The host retains that declaration for this turn. For an explicitly required caption, refresh the list once with the SAME title if absent; if still absent or ambiguous, leave all candidates untouched and report the unresolved target. Do not replace a rejected restriction, delegate, or change tools to circumvent it. With a descriptive target, inspect plausible returned windows and resolve from their actual content; if multiple windows remain indistinguishable, ask which one instead of guessing. Verify the result in the same matched window. The controller handles caption changes produced by successful actions in the same verified Windows window; do not broaden the original title yourself.

## Observe, act, verify

When the user names an open file, for example “记事本里已打开的《交班表.txt》”, the name between book-title marks identifies the file. Call `list_apps({"window_title":""})` and use the returned window selector. For a desktop editing task, verify the requested change in the editor and its saved state there.

Windows defaults to a control-first observation, including button-based apps such as Calculator. Read its displayed values and action targets directly; no writable field is required. Request `view="full"` only when current controls cannot resolve the task's visual details. After each action in the same Windows window, the receipt returns to control-first mode even if the preceding observation explicitly used full. The original frame remains available in the tool receipt. UIA ToggleState On, Off or Indeterminate gives the current checkbox state; when absent, the state is unknown. Field views also include current document values, buttons, selection and focus; use that existing evidence before requesting another image interpretation.

For Windows forms request `get_app_state(view="fields")`. Read labels and current values directly. Use each current field token with `set_value` only for an authorized whole-field replacement. On legacy forms without tokens the same observation can include the full control tree, native edit indices, exact values and keyboard focus. Match the edit to its label in that tree, click its index and check keyboard focus in the returned state before typing. Each action returns fresh evidence; verify all requested postconditions there. Request `view="full"` for pixels only if the control data leaves a target, state, or explicitly requested visual detail unresolved.

For macOS form edits, including a single PDF field, inspect the actual controls and obtain local FORMS matching before the first write. Pass exact replacement values as `form_entities` entries `{label,value}`. FORMS recognizes a narrow English vocabulary: for Chinese or unsupported labels, use optional `form_labels` on a subsequent observation of the SAME exact window selector. Translate only clearly resolved target fields: `fields:[{element_index:"18",label:"Company"},{element_index:"23",label:"Email"}]`, `entities:["Company","Email"]` in source-entity order, and an English scoring `title` such as `Customer Form`. Use `Email`, not `Work email`, for the resolved email target; preserve the work/billing distinction by selecting the correct observed index and leaving other fields unlisted. Never invent distinctions between two unlabeled email fields. Unlisted fields are skipped without scoring. Keep original labels and values in `form_entities`; do not translate or clear current values to force a recommendation. Raw English matching remains available without `form_labels`.

Local FORMS never writes. Its recommendation is not authorization, and its skip is not a prohibition on an explicitly requested, unambiguous replacement. Existing values can legitimately produce skip. Select the action from user scope and current control facts; verify changed and preserved fields from the action's readback. Stop before submission unless separately authorized. `unavailable`, `no_fields` and `no_mapped_fields` do not mean a successful match. A stale projection returns a fresh observation: resolve its current indices again before scoring; never reuse old translations blindly.

If entering an application's editing mode reveals form controls absent from the scored observation, request matching for that new state before filling. Do not describe toolbar-only recommendations as document-field matches. Report FORMS participation only for the actual control indices and recommendations returned; distinguish your own field selection from the local model's suggestion.

macOS also defaults to control-first `view="fields"`, using native element indices without Windows write tokens. Request `view="full"` only for unresolved visual targets or details. Action after-states return to controls, preserving readback while avoiding unnecessary auxiliary image calls.

For macOS whole-field replacement, use `set_value` on the current native editable field index. Native document fields such as Preview PDF fields do not require keyboard focus: omit `focus` for those fields. Web fields require verified focus; prefer `set_value(focus=true)` when the schema advertises it, instead of a separate click just to focus. This single-field operation focuses the bound field and rechecks its identity, actual focus, foreground and human takeover before writing. If the parameter is absent, web fields still require a separate click and focus readback. Preserve existing content and verify the actual after-state; API success alone is not proof of a changed value. A focus/permission rejection or pause is not permission to switch input methods. Each field is a separate decision; do not batch writes or reuse stale indices.

For a single text or numeric expression in an observed control that accepts text entry, use one `type_text` call for the complete literal once the input target is established. Inspect its returned state before any separate confirmation key. `press_key` takes one key or one simultaneous shortcut, never a sequence of characters or a list of shortcuts. When distinct fields or buttons require separate decisions, use their individual targets.

- Keep routine control turns short: use the returned evidence to choose the next action, without narrating the same plan before every tool call. When the requested result is already visible in the last action's after-state, finish with a brief factual result. Do not add a separate observation or re-audit the full history just to write the final reply. Preserve all target, focus and permission checks.

- Verify a GUI save from the current document values and the application's saved-state evidence (such as the unsaved marker clearing after Save). Mac PDF receipts may additionally include `pdf_document` / `PDF disk fields`, read directly from the local PDF identified by that window's AXDocument. Compare `status=read` exact disk fields with the requested changes and preserved UI fields; disk values can legitimately remain old before saving. Duplicate names stay separate by page/annotation, and null means unknown. After an authorized save, matching disk and UI values establish field persistence without another screenshot or shell read. Use the action's fresh receipt; re-observe only if a needed value remains unavailable or conflicting. This receipt never authorizes saving, submitting, or changing scope.
- Once those postconditions are established, finish. A missing filesystem path is not missing GUI evidence: do not recursively search the user profile or drives, discover file tools, or open another verification channel merely to corroborate a completed GUI save. Report a document path only if observed or supplied by the user; the chat's workspace is not the open document's location. Read disk contents through other tools only when the user explicitly requests it or a concrete missing/conflicting fact requires it. If the save state is unknown, say so instead of claiming persistence.

- For a known local folder or document, use `mcp__qwen_computer__open_path` when available, then observe the actual target. It uses the desktop runtime and default application. Launch acceptance is not proof that content is visible; if the returned window list has not caught up, observe/list once before deciding what is missing. Do not launch the same path repeatedly. When the document is already open, discover its window with list_apps and verify the document in that window. Only locate a file on disk when the task requires opening it from disk. A rejected window lookup cannot be resolved by searching disk. Do not inspect unrelated apps first.
- Do not start desktop applications with confined `pwsh`/`bash`, WMI, COM launch workarounds, or long sleeping background jobs. Shell child lifetimes and desktop permissions differ from user-owned application windows. A shell denial or an empty process list is not evidence that a GUI is still loading. If `open_path` is unavailable, use an observed desktop launcher or explain the missing capability; do not escalate shell permissions just to work around missing desktop tools.
- Reuse each action's returned screenshot and tree for the next decision. Do not insert `list_apps` plus `get_app_state` after every action. Observe again only for a changed/ambiguous target, stale state, missing evidence, or a specific unmet postcondition. Once the requested folder/document is visibly open, report concisely and stop; do not inspect the document's private contents unless requested.
- Escape or three consecutive input conflicts end computer control for this turn only. DESKTOP_STOPPED blocks further computer tools in this turn, while reasoning and independent non-desktop tools remain available. Do not end the task merely because computer control was interrupted. There is no resume button: do not invent one or ask the user to unlock control. Do not bypass the stop with scripts or replay uncertain actions.
- `DESKTOP_PAUSED` means desktop control is explicitly paused, not that the conversation was cancelled. Continue independent authorized work when useful; explain the blocked part only if it requires desktop control. There is no global unlock button. Do not use another input tool or shell to bypass the pause. The host waits queued calls without model polling. `DESKTOP_OBSERVATION_EXPIRED` after resume requires fresh observation, never replay of uncertain input.
- `DESKTOP_INPUT_CONFLICT` means input changed during or since the last observation. It is a temporary conflict, not a persistent pause: observe the target again, reconcile any partial action, and decide from the new evidence. Sustained input may block the observation too; report the conflict if it persists. Do not ask the user to unlock a pause that does not exist, and never blindly retry the previous action.
- `open_path` validates that the exact path exists before dispatch. Repeating filesystem existence checks does not verify its window. If a fresh window observation still cannot locate the target, use an observed desktop navigation control or report the verification gap; do not chain unrelated discovery and filesystem probes.

- Make one grounded input, inspect the returned after-state, then decide the next action. Use current element indices or window-local screenshot coordinates. A sparse accessibility tree is a reason to inspect the screenshot, not to guess a familiar layout.
- Use `type_text` for Unicode text and `press_key` for shortcuts. These tools target the current keyboard focus, not an element mentioned in your reasoning. Before typing or editing shortcuts such as Ctrl+A, inspect the latest after-state: if the intended editor is not focused, click that observed editor and verify focus in the returned state. An active window or a visible editable element alone does not establish input focus. Reuse that state without an extra observation call. On macOS cmd/super means Command; ctrl means Control. Use each tool's loaded schema.
- Windows foreground `type_text` supports single-line text. For multiline content, use `set_value` only if the observed editor supports it and complete replacement is intended; include any existing content that must be preserved. Otherwise use that editor's observed line-break controls. Do not assume Enter or Shift+Enter is harmless in a message composer.
- To bring an already observed window forward without changing its contents, use `perform_secondary_action` on its current root window element with its advertised `AXRaise` (macOS) or `Raise` action. Reuse the returned after-state. A new-conversation shortcut such as Cmd+N changes application state; never use it merely to activate a window or resume an existing draft.
- Activation denied is a foreground handoff, not a stale element retry. When the native tool reports that target activation was denied and no input was dispatched, ask the user to bring that exact window to the foreground. A fresh read of a background window does not resolve an OS activation refusal. Do not cycle through Raise, clicks, set_value, shortcuts, other windows, or shell diagnostics to force activation. Continue only after a fresh observation confirms the intended target is foreground; preserve existing field values and reconcile before writing.
- If the target is not running, use `open_path` for supported documents/folders or an observed desktop launcher. Launch success does not prove window readiness.
- Do not create AppleScript/System Events, PowerShell SendKeys, pyautogui or other shell scripts to replace these desktop input tools. In particular, do not bypass a focus, stale-observation, permission or user-takeover rejection with another input mechanism.
- After stale state, ambiguity or focus changes, enumerate and observe again. If the same failure persists with fresh evidence, report the exact blocker instead of repeatedly sending the same input or switching to blind scripts. Missing foreground identity does not prove the application is closed.
- Preserve user drafts. For messaging, verify the recipient and exact content before sending, obey the current authorization flow, and inspect the resulting conversation after sending. If submission is uncertain, observe first; do not resend.
- If the screenshot is unavailable to your model and the accessibility tree contains only window chrome, stop and report the visual configuration blocker. Shell screenshot files, opening QuickLook, image dimensions, and old clipboard contents do not let you read the missing screenshot. An empty composer alone does not prove submission, and an unchanged window is not evidence that a reply is loading.
- Tool exit code 0, input dispatch and an empty shell result are not completion evidence. Report only visible, verified results. Distinguish message submission in the app from delivery to the recipient. If verification is blocked, say what remains unverified; do not label the task completed.

## Communicate useful progress

During desktop work, group communication around the user's goal. Leave routine observations, clicks, typing, scrolling and checks in the tool record rather than narrating each action. This does not change the observe, act, verify workflow above.

When there is useful new information, briefly share a verified finding, a meaningful stage result, a change of approach or a concrete blocker in the user's language. Usually one or two sentences are enough to explain what changed and, when helpful, the next step. Combine related progress, avoid repeating plans or internal reasoning, and do not fill silence with generic reassurance or announce every retry.

Continue working after an update. Communication is not a prerequisite for the next action; wait only when user input is genuinely needed. There is no fixed time or tool-call schedule for updates.

Examples, only when supported by the actual task:
- Useful: "I checked all three applications. Two meet the technical requirements, but one cannot start in time; I am checking their project experience next."
- Useful blocker: "The file picker does not expose an actionable upload control. I am checking the page's upload button; the existing draft is preserved."
- Avoid: "Taking a screenshot. Clicking the application. Taking another screenshot. Opening the next file."
