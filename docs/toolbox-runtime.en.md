# Toolbox and conversation synchronization

Ordinary new conversations follow currently enabled toolbox capabilities. Saving skills, tools or MCP configuration during execution does not rebuild the running scope. Queued messages and subsequent turns read current configuration before execution. Each tool call also checks current disable/removal policy. Native Harness skill discovery and content versions own skill updates; editing instructions cannot erase text already present in model history.

The toolbox header and conversation cards consume one backend snapshot, distinguishing pending application, connected and failed states. Reading status never initializes connections. Visible views refresh every three seconds and on focus to observe edits from other windows. Retry retires only failed selected connections; healthy peers remain reusable. Forced reconnect is unavailable during execution.

Remote MCP uses official Harness `agent-preset-registry` leases per complete server configuration, including credentials, filters and timeouts, with at most 64 reusable configurations. Editing, failing or deleting one server does not restart peers. Native scopes project only each conversation's selected tools, resources and instructions without rebinding shared parents. Stdio remains isolated by session and working directory. Existing protocol, Tasks, Apps, receipt and approval adaptations remain; disconnect never automatically replays actions. Resource approval checks the projected definition while retaining source-generation identity, revoking old consent on reconnect.

Ambiguous legacy lists remain custom. Explicitly switching to follow uses only enabled global entries while retaining old names and encrypted definitions without executing them. Switching back restores the old selection subject to current global disable/removal policy. Without an old list, custom mode freezes the current effective selection. Retirement markers prevent resurrection from historical copies until explicit re-addition. Selection survives restart without rewriting messages, replaying actions or deleting user configuration.

The whole-group MCP cache entry point and independent card tool-count fetching/cache have been removed. Independent Rust MCP tools remain supported. Broken external dependencies such as Scrapling's Python environment require repairing that environment; synchronization and bounded diagnostics do not install dependencies.

References: the pinned MIT developer preview Harness 0.2.1-alpha.2 [preset registry](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/agent-preset-registry/README.md), [MCP lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/mcp.md), and [MCP tool-list change protocol](https://modelcontextprotocol.io/specification/2025-06-18/server/tools). Native leases/scopes are reused while preserving product adaptations; no second Agent core or dependency upgrade is introduced.

## First response and list loading (2026-11-06)

Desktop sessions enable `backgroundMcp`: native selected scopes are admitted before optional stdio and remote MCP handshakes complete in parallel. Ordinary replies no longer wait for the slowest optional connection. `connecting / ready / error` remain distinct from unapplied configuration. Legacy load-result notifications omit pending connections instead of reporting failure.

The existing bridge owns readiness promises, diagnostics and disposal. Discovery exposes pending server names; structured `servers` or exact tool names await only the selected connection. Waiting is cancellable and neither executes tools nor grants permissions. Native registrations, role filters, policy checks, approvals and receipts remain authoritative. Searches targeting a failed server include its diagnostic. Initial failures do not trigger repeated automatic launches; recovery after an established connection retains the existing lifecycle.

Warmup and sessions share the remote configuration identity; background scheduling is not a connection identity. Identical pending stdio connections survive reconfiguration. Removal, replacement and closure dispose scopes, so late results cannot resurrect removed selections. Active configuration changes still apply before the next turn; per-call disable/removal checks remain. No persisted-state migration, dependency installation or legacy Rust Agent restoration is required.

Connection logs measure initialize (including process startup/negotiation), tools/list and total time. In background mode session preparation logs measure scope admission, not completion of every handshake. Toolbox skills, extensions and usage load concurrently with partial inventory rendering. Each card group initially mounts 24 entries, appending near the scroll boundary with an accessible Load more fallback. Search and deep links use the complete catalog, and edits consume current snapshots. This change does not paginate the backend inventory API.
# Extension failures and preview identity (2026-11-07)

External-extension forms normalize an omitted timeout to the existing 300-second default so the displayed value and validation agree. Explicit invalid values remain invalid. Opening or testing a form does not persist configuration.

Failure notifications retain the latest result per extension. Changes to peers, ordering, selected chats, or partial snapshots do not reannounce unchanged failures. Confirmed recovery followed by failure, or changed diagnostics, re-arms the notification. This bounded, per-window cache affects presentation only; toolbox state, permissions and reconnect policy remain authoritative elsewhere.

The preview backend fingerprints runtime source at startup and exposes read-only runtime/status diagnostics. The desktop checks every 30 seconds and on focus, asking users to finish tasks before exiting and restarting after source changes. It never interrupts tasks automatically. This development fingerprint is not a package signature or complete build attestation; dependencies, tool binaries, tests and assets are excluded. The launcher reuses SQLite leases across preparation and execution, rejects duplicate launches and preserves the original receipt.
