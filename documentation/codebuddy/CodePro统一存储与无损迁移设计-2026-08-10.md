# CodePro 统一存储与无损迁移设计

**状态：** 已按外部审查修订，待用户确认书面版本  
**日期：** 2026-08-10  
**范围：** 统一本机用户数据根目录、迁移现有数据、为未来账号隔离预留稳定边界  
**不在范围：** 登录、云同步、账号界面、旧数据自动删除、安装程序和更新文件迁移

## 1. 结论

CodeBuddy 使用单一用户数据根目录：

```text
C:\Users\<用户名>\.CodeBuddy
```

本阶段只实现 `profiles\local` 本地档案。未来账号功能通过新增 `profiles\<account_id>` 扩展，不在本次实现登录、同步或账号业务逻辑。

统一 `.CodeBuddy` 是所有默认启动的主路径；即使检测到旧目录或旧数据冲突，应用也直接创建或使用统一目录，正常启动不得被旧数据阻断。旧数据迁移是用户显式发起的可选导入，采用“复制到暂存区、验证、原子切换、保留旧目录”的方式。导入完成后只写新目录，不长期双写；程序不自动删除旧数据。

## 2. 前提与事实

当前桌面版通过 `GOOSE_PATH_ROOT` 将大部分后端数据写入 `%APPDATA%\CodeBuddy\backend`，但 CodePro run 和项目记忆仍使用 `%LOCALAPPDATA%\CodeBuddy` 下的独立路径。未设置根路径时，goose 兼容路径还可能使用 `%LOCALAPPDATA%\Block\goose` 和用户主目录下的 `.agents`。

这造成以下问题：

- 备份、诊断和卸载残留需要检查多个目录。
- Electron 与 Rust 后端没有共享一个产品级路径契约。
- 后续账号隔离会再次触发迁移。
- 用户无法确认某一类数据的权威位置。

## 3. 对 Codex 的借鉴边界

OpenAI 官方文档明确说明 Codex 的用户级配置位于 `~/.codex/config.toml`，项目级覆盖位于受信任项目中的 `.codex/config.toml`。CodeBuddy 借鉴“单一用户根目录”和“用户级数据与项目级配置分离”的产品原则。

本设计不推断 Codex 未公开的会话数据库、缓存迁移或账号存储内部实现，也不照搬未经官方文档确认的清理规则。

参考：

- https://learn.chatgpt.com/docs/config-file/config-reference

## 4. 方案比较

### 4.1 一次性移动

启动时直接移动旧文件并立即改用新路径。实现较少，但中断、文件占用或同名冲突可能留下半迁移状态，拒绝采用。

### 4.2 默认新存储与显式无损导入（采用）

默认启动直接使用统一产品根目录，不自动扫描或迁移旧目录。只有用户显式选择导入旧数据后才进入版本化迁移状态：旧数据先复制到暂存区，完整验证后再原子切换。导入可重复执行，旧目录只读并保留。

### 4.3 仅统一界面

保留物理目录分散，只在设置页统一展示。风险低，但不能解决备份、残留和账号隔离，拒绝采用。

## 5. 权威目录结构

```text
.CodeBuddy\
├── version.json
├── config\
│   └── app.json               # 设备级界面和桌面行为
├── profiles\
│   └── local\
│       ├── profile.json
│       ├── config\            # Provider、模型、权限和档案偏好
│       ├── sessions\
│       ├── runs\
│       ├── memory\
│       ├── projects\          # 项目引用、项目来源配置和受控元数据
│       ├── audit\             # 工具审计和幂等记录
│       ├── models\            # 用户已下载的模型资产
│       ├── agents\
│       ├── skills\
│       ├── prompts\
│       ├── recipes\
│       ├── plugins.json       # 当前档案的启用和配置状态
│       ├── state\
│       │   └── electron\      # 档案级 Electron sessionData
│       └── cache\
│           ├── mcp\
│           └── model-metadata\
├── plugins\
│   └── packages\              # 设备上已安装的插件包
├── state\
│   └── electron-app\          # 窗口和无账号设备状态
├── cache\
│   └── app\                   # 与档案无关且可重建的应用缓存
├── logs\
└── migrations\
```

### 5.1 设备级数据

`config\app.json`、`plugins\packages`、`state\electron-app`、`cache\app` 和 `logs` 属于当前 Windows 用户和设备。它们保存语言、主题、窗口行为、更新偏好、插件安装包和不含账号身份的运行状态。配置文件不得保存 Token、密码或可直接使用的刷新凭据。

### 5.2 档案级数据

`config`、`sessions`、`runs`、`memory`、`projects`、`audit`、`models`、`agents`、`skills`、`prompts`、`recipes`、`plugins.json`、`state` 和 `cache` 属于档案。Provider、默认模型、权限策略、响应偏好、用户已下载模型、用户自定义 Agent/Skill/提示词/配方和插件启用状态不能跨档案共享。插件程序包可设备级复用，但其启用与配置必须按档案隔离。

Electron 41 的持久 session 按存储路径或 `persist:` partition 复用，因此账号 Cookie、Local Storage、IndexedDB 和相关缓存必须放在档案的 `state\electron`；设备级 `state\electron-app` 不得保存账号登录态。Electron 的 `sessionData` 物理目录同时承载持久存储和缓存，本设计只做档案级物理隔离，缓存与 Cookie 的清理边界通过 Electron 官方 API 的数据类型区分，不假设它们天然分目录。当前版本的档案固定为 `local`。

未来实现账号时，每个账号使用服务端稳定、不含邮箱或用户名的内部 ID 作为目录标识。账号切换不得共享会话、记忆、run 或项目绑定。本地档案不会自动并入账号档案，导入必须由用户明确选择。

`projects` 只保存 Project 的稳定 ID、规范化绝对路径、显示名称、最近打开时间、workspace 类型、项目来源配置和受控派生元数据。用户项目源码、Git 数据和 worktree 不复制到这里；同一规范化项目路径在一个档案内只能对应一个 Project。

### 5.3 不进入根目录的数据

- 安装程序、应用二进制、自动更新下载和 Windows 卸载信息。
- Token、密码和其他长期凭据；这些数据继续使用 Windows Credential Manager 或项目已有安全存储。
- 用户项目源码和 Git worktree；这里只保存项目引用和受控元数据。

## 6. 路径解析契约

新增产品级环境变量 `CODEBUDDY_HOME`。未设置时默认值为当前 Windows 用户主目录下的 `.CodeBuddy`。

`.CodeBuddy` 和 `CODEBUDDY_HOME` 是发布后保持兼容的存储标识。未来即使调整对外展示名称，也不得仅因品牌变化自动重命名用户数据目录。

路径解析必须满足：

- Electron 主进程和 Rust 后端得到完全一致的规范化绝对路径。
- Electron 必须在 `ready` 前把 `userData` 指向设备级 `state\electron-app`，把 `sessionData` 指向当前档案的 `state\electron`；不能在 session 创建后再修改路径。
- 应用启动后不得由功能模块自行拼接 `%APPDATA%`、`%LOCALAPPDATA%`、`.agents` 或 `Block\goose`。
- 业务模块只使用类型化的路径接口取得目录。
- 路径优先级固定为：有效的 `CODEBUDDY_HOME` > 有效的旧 `GOOSE_PATH_ROOT` > 默认 `.CodeBuddy`。只设置旧变量时将其作为兼容目标并记录一次弃用警告；两个变量同时存在且规范化路径不同时，以新变量为目标，将旧变量路径仅作为迁移来源，不进行双写。
- 空值、相对路径、不可创建路径和指向普通文件的路径必须返回明确错误。
- 测试可通过 `CODEBUDDY_HOME` 使用隔离目录，不接触真实用户数据。

## 7. 启动与迁移状态机

```text
应用启动
  -> 解析并验证 CODEBUDDY_HOME
  -> 默认创建或使用统一 .CodeBuddy 并启动
  -> 不扫描、不读取、不修改旧目录
用户显式选择“导入旧数据”
  -> 运行 typed preflight
     -> 无需导入：保持统一目录并继续
     -> 发现可导入旧数据：进入迁移
        -> 停止所有会写用户数据的后端启动
        -> 盘点来源并生成迁移计划
        -> 复制到 migrations\staging\<migration_id>
        -> 验证文件、JSON 和 SQLite
        -> 原子切换到正式目录
        -> 写入完成标记
        -> 使用统一目录启动
     -> 发现冲突：仅阻止本次导入，不覆盖来源，不影响以后正常启动
```

### 7.1 旧数据来源

迁移器必须显式识别：

- `%APPDATA%\CodeBuddy`
- `%LOCALAPPDATA%\CodeBuddy`
- `%LOCALAPPDATA%\Block\goose`
- `%USERPROFILE%\.agents`
- 用户显式设置的旧 `GOOSE_PATH_ROOT`

来源不存在时跳过。迁移器不得把源码仓库、用户项目或任意同名目录当成应用数据。

旧数据按语义映射，不整目录盲目复制。迁移实现前必须用盘点器确认来源存在和实际类型，默认映射为：

| 旧路径或类型 | 新位置或动作 |
|---|---|
| `%APPDATA%\CodeBuddy\settings.json` | `config\app.json`，只保留设备级字段 |
| `%APPDATA%\CodeBuddy\recent-dirs.json`、`window-state.json` | `state\electron-app` |
| `%APPDATA%\CodeBuddy\backend\config\config.yaml` | `profiles\local\config\config.yaml` |
| 旧 backend `permissions`、`custom_providers` | `profiles\local\config` 对应子目录 |
| 旧 backend `agents`、`prompts`、`recipes`、`skills` | `profiles\local` 对应用户内容目录 |
| 旧 backend Provider OAuth/token 缓存 | Provider 专用迁移器写入 Windows Credential Manager；现有格式必须保留文件时，进入受限 ACL 的 `profiles\local\state\providers`，不得进入普通配置或日志 |
| 旧 backend `tls` | 受限 ACL 的 `state\tls`；私钥不得出现在迁移报告 |
| `%APPDATA%\CodeBuddy\backend\data\sessions` | `profiles\local\sessions`，SQLite、WAL、SHM 作为一致单元处理 |
| 旧 backend `data\projects` | `profiles\local\projects\sources` |
| 旧 backend `data\codepro-control` | `profiles\local\runs\control-plane` |
| 旧 backend `data\tool-audit-v1`、`tool-audit-v2` 和幂等记录 | `profiles\local\audit`，保持现有 schema 和保留期限 |
| 旧 backend `data\apps`、`mcp-apps-cache` | `profiles\local\cache\mcp`；可验证为纯缓存时不迁移 |
| 旧 backend `data\models` | `profiles\local\models`，已下载模型完整迁移；只有能够明确识别并重新生成的索引/元数据进入 `cache\model-metadata` |
| `%LOCALAPPDATA%\CodeBuddy\codepro-runs` | `profiles\local\runs` |
| `%LOCALAPPDATA%\CodeBuddy\project-memory`（如果存在） | `profiles\local\memory` |
| `%USERPROFILE%\.agents\plugins` | `plugins\packages` |
| `%USERPROFILE%\.agents\agents` | `profiles\local\agents` |
| `%USERPROFILE%\.agents\skills` | `profiles\local\skills` |
| `%APPDATA%\CodeBuddy\Partitions\goose` 中的持久 Cookie、Local Storage、IndexedDB | `profiles\local\state\electron`，保持一个档案一个持久 session |
| Chromium `Cache`、`Code Cache`、`GPUCache`、shader cache | 不迁移，由档案级 Electron session 在 `profiles\local\state\electron` 中重建，并通过类型化 API 作为可回收缓存管理 |
| 旧 backend state 日志和 Electron 日志 | `logs\legacy\<source_id>`，不能覆盖当前日志 |
| `%LOCALAPPDATA%\CodeBuddy\bin`、`Update.exe`、更新包 | 不迁移，由安装和更新系统管理 |

`%LOCALAPPDATA%\Block\goose` 和用户指定的旧 `GOOSE_PATH_ROOT` 按相同的 `config`、`data`、`state`、`.agents` 子目录语义映射，不使用额外的猜测规则。

### 7.2 权威切换规则

- 完成标记写入前，旧目录仍是权威来源。
- 完成标记写入后，新目录是唯一写入位置。
- 不采用长期双写，避免两份数据逐渐分叉。
- 显式导入失败时不得覆盖来源或部分发布暂存内容；应用显示可操作错误，旧数据保持不变。失败只终止本次导入，不改变统一目录作为默认启动主路径。
- 迁移中断后根据迁移状态继续或安全重建暂存区，结果必须幂等。

`migrations\migration.json` 至少包含：迁移 ID、布局起止版本、目标根目录、规范化来源列表、来源指纹、当前状态、暂存目录、清单文件路径、开始/更新时间和脱敏错误。状态只允许：

```text
planned -> copying -> verifying -> ready_to_commit -> committed
                   \-> failed
```

逐文件清单使用独立的追加式 manifest，不把大量文件记录塞进单个 JSON。每一项记录来源标识、相对路径、类型、大小、内容摘要、目标相对路径和验证结果。恢复时先验证来源指纹；来源已经变化则停止并重新生成计划，不能继续使用旧清单。

### 7.3 冲突处理

如果多个来源映射到同一目标且内容不同，本次显式导入停止并生成冲突报告，不以时间戳猜测正确版本，不覆盖任何一方；该冲突不得阻止下一次正常启动统一目录。

无法识别但确定属于旧应用数据根的文件，复制到 `migrations\legacy-unclassified\<source_id>`。这类文件不自动进入业务模块，也不自动删除。

### 7.4 完整性验证

- SQLite：检查数据库、WAL 和 SHM 组合，执行 SQLite 完整性检查，并确认关键表可读。
- JSON/TOML/YAML：确认可解析；不认识的字段原样保留。
- 普通文件：比较相对路径、大小和内容摘要。
- 目录：比较应迁移文件数量和总字节数。
- 迁移前计算所需空间；空间不足时不开始复制。

## 8. 旧数据保留和清理

迁移成功后程序不修改或删除旧目录。设置页显示旧目录、占用和迁移完成时间，并在稳定运行至少 7 天后提供手动清理入口。

清理属于独立的高风险操作：必须再次扫描、展示精确目标、要求用户确认，并记录结果。本次迁移任务不实现自动删除。

## 9. 存储生命周期和容量保护

统一目录不等于统一删除策略。数据必须先分类为“可重建”“可自动过期”“用户历史”“运行中状态”和“凭据”，再应用对应规则。不能为了满足总容量上限删除会话、记忆、未完成 run、插件或凭据。

当前代码已经存在的保留策略必须复用并集中到统一存储服务，不重新实现一套相互冲突的清理器：

| 数据 | 默认策略 | 自动删除边界 |
|---|---|---|
| 已完成/失败/丢弃的 run | 保留 30 天；terminal run 总量软上限 2 GiB | 先删过期 terminal run，再按最旧 terminal run 收缩；当前和非终态 run 永不自动删除 |
| 工具审计和幂等记录 | 已完成记录保留 30 天；每 session/scope 最多 4,096 条 | 未解决记录永不因保留期限删除 |
| 项目记忆 | 每项目最多 500 条、单条 2,000 字符、单项目文件 2 MiB | 不按年龄自动删除用户记忆；提供项目级清理 |
| Rust 日志 | 保留 14 天 | 仅删除过期日志目录，不删除审计权威记录 |
| 启动诊断 | 最多 20 份 | 删除最旧诊断文件 |
| Electron/Chromium 缓存 | 每个档案 512 MiB 软预算 | 只清理 Electron 官方 API 定义的 cache 数据，不清 Cookie、Local Storage、IndexedDB 或凭据 |
| MCP 和可重建模型元数据缓存 | 合计 256 MiB 软预算，30 天未使用可回收 | 只删除能够重新生成的缓存条目，不包含已下载模型文件 |
| 用户已下载模型 | 默认保留，按档案展示占用 | 只能由用户选择具体模型后删除，不进入自动或一键清理 |
| 会话数据库 | 默认永久保留，用户可归档或删除 | 不按“最近 20 个”等数量静默删除；删除后执行受控 SQLite checkpoint/compact 才能实际回收空间 |
| 旧迁移来源 | 成功运行至少 7 天后提示 | 只能由用户确认后清理，永不自动删除 |

容量预算是软预算，不是对整个 `.CodeBuddy` 的单一硬上限。当前机器的应用数据约 630 MiB，其中约 493 MiB 是 Chromium 缓存，因此 500 MiB 总上限会把正常安装立即判定为超限，拒绝采用。

存储服务必须提供统一盘点结果：分类路径、总字节数、可回收字节数、不可自动删除原因、最旧/最新时间和清理策略。设置页按分类展示占用，允许用户清理缓存、过期 terminal run、旧日志和已明确选择的会话；“一键清理”不得包含记忆、非终态 run、凭据、插件包或旧迁移来源。

每次开始可能产生大量数据的 run、下载或迁移前检查目标卷可用空间。预留值取目标卷容量 5%，但最少 1 GiB、最多 5 GiB。低于预留值时先清理符合策略的可重建/过期数据；仍不足则拒绝新的大写入并显示所需空间、可回收空间和手动处理入口，不能继续写到磁盘耗尽，也不能擅自删除用户历史。

Electron 41 官方提供 `Session.getCacheSize()`、`clearCache()` 和按数据类型清理的 `clearData()`。实现必须明确限定为 cache 类型并做“Cookie/Local Storage 保持不变”的回归测试，不能用无参数的全量清理。

参考：

- https://www.electronjs.org/docs/latest/api/session
- https://www.electronjs.org/docs/latest/api/app

## 10. 安全与隐私

- 迁移日志不得记录 Token、请求正文、会话正文或记忆内容，只记录类型、路径标识、数量、大小、摘要和错误类别。
- 根目录及档案目录使用当前 Windows 用户可访问的权限，不扩大到其他用户。
- 迁移器拒绝通过 junction、符号链接或路径穿越写出 `.CodeBuddy` 暂存和目标边界。
- 冲突报告中的路径和内容摘要需要脱敏；不复制凭据到普通配置文件。
- 未来账号目录只能由经过验证的内部 ID 生成，不能直接使用邮箱、显示名称或外部输入作为路径。

## 11. 验收标准

### 11.1 路径单元测试

- 默认根、环境覆盖和所有子目录映射正确。
- Electron 与 Rust 的路径契约一致。
- 空路径、相对路径、非法路径、junction 和权限拒绝有确定行为。
- 新运行不再写入旧路径。

### 11.2 迁移测试

- 全新安装。
- 存在旧目录及真实冲突时，默认启动仍选择 `InitializeNew`，且不调用 preflight/migrate。
- 只有显式 opt-in/import 才运行 typed preflight；冲突 fail-closed 且来源字节不变。
- 只有 Roaming 数据。
- 只有 Local 数据。
- 多个旧来源同时存在。
- 迁移中途终止后重启。
- 同名不同内容冲突。
- SQLite 正常、损坏和带 WAL。
- 磁盘空间不足。
- 重复执行结果一致。
- 失败后旧数据内容和时间戳不变。

### 11.3 功能集成测试

迁移后验证设置、Provider 配置、会话、run、证据、撤销基线、项目记忆、插件、Agent、MCP 缓存、日志和审计记录仍能正确读写及重启恢复。

容量和清理测试必须覆盖：超过 run 软预算、过期/未过期 terminal run、当前及暂停 run、审计未解决记录、日志轮转、Electron cache 超限、Cookie/Local Storage 保持、低磁盘空间、会话归档/删除后的 SQLite 回收，以及清理任务中途终止后重试。每次测试同时断言不可自动删除的数据未变化。

### 11.4 真实桌面验收

先使用隔离的 `CODEBUDDY_HOME` 构建并启动真实桌面程序，通过真实鼠标和键盘完成：

```text
首次启动 -> 创建会话 -> 选择项目 -> 执行任务
-> 写入记忆 -> 关闭应用 -> 重新打开
-> 恢复会话和任务 -> 查看数据位置
```

隔离验收通过后才迁移当前机器真实数据。迁移后打开原有会话，执行真实任务，重启并恢复；检查所有新增写入只出现在 `.CodeBuddy`，旧目录内容和时间戳不变。保存迁移报告、测试输出和界面截图。

任何新增回归都必须先定位、修复并重新运行相关完整验收，不进入下一项开发。

## 12. 分阶段实施

1. 建立共享路径契约及自动化测试，不改变生产默认路径。
2. 让 run、memory、sessions、插件和 Agent 依次改用共享路径，每一步保持测试通过。
3. 实现版本化迁移器和故障注入测试。
4. 接入 Electron 早期启动流程及隔离桌面验收。
5. 使用隔离旧数据夹具执行显式可选导入和用户视角验收；不自动迁移当前机器真实数据。
6. 在统一路径验收通过后实现存储盘点、分类预算、缓存清理、低磁盘保护和设置页；完成自动化及真实桌面验收后，才能进入下一个无关功能。

## 13. 回滚

实现阶段不删除旧代码兼容入口和旧用户数据。候选版本验证失败时，停止候选进程，保留迁移报告，将启动配置指回已验证的旧版本；旧版本仍读取未被修改的旧目录。

在新目录产生用户写入后，不允许直接降级并假装两份数据一致。需要恢复时保留新目录，通过专用恢复或再次迁移处理，不能用文件覆盖回滚。

## 14. 完成定义

只有同时满足以下条件才算完成：

- 自动化测试覆盖路径、迁移、冲突、恢复和关键业务读写。
- Rust 和桌面相关构建、类型检查、格式、lint 与测试通过。
- 使用变更后的源码重建 Electron 和后端。
- 隔离桌面默认启动与显式可选导入流程均通过。
- 旧目录未被修改或删除，新写入只进入 `.CodeBuddy`。
- 存储占用可见，分类清理和低磁盘保护通过测试，受保护数据没有被自动删除。
- 迁移证据足以让用户独立复核。
- 用户检查通过前不提交、不推送；不创建分支。

## 15. 设计审查处理记录

2026-08-10 外部审查意见按当前代码和 Electron 41 官方文档逐项核实后处理如下：

- **采纳：** 设备级配置与档案级 Provider/模型/权限配置分离。
- **采纳：** Electron 持久 session 按档案隔离；缓存与 Cookie 通过类型化 API 区分清理。
- **采纳：** 精确列出旧目录到新目录的映射。
- **采纳：** 明确 `CODEBUDDY_HOME` 与 `GOOSE_PATH_ROOT` 的优先级和冲突行为。
- **采纳：** 明确 Project 目录只保存引用、来源配置和元数据。
- **采纳：** 用户 Agent、提示词和配方归档案；插件包设备复用、启用状态归档案。
- **采纳并修正：** 将容量管理纳入当前存储目标，但复用现有 run、审计、记忆和日志策略。
- **拒绝：** 只保留 20 个会话或 50 个 run；按数量删除会造成用户历史丢失，run 已有状态感知的 30 天/2 GiB 策略。
- **拒绝：** 500 MiB 总硬上限；当前正常数据已约 630 MiB，必须按类别管理可回收数据。
- **拒绝：** 因未来可能改品牌而改用 `.codepro`/`CODEPRO_HOME`；当前产品名是 CodeBuddy，发布后的存储标识应保持兼容稳定。
- **保留用户决策：** 默认根目录使用用户明确批准的 `%USERPROFILE%\.CodeBuddy`。这是有意采用的单一用户根目录，不声称它是 Windows 通用应用默认规范。
