# CodeBuddy Windows 日用 Beta 产品与架构设计

**状态：** Accepted  
**日期：** 2026-08-05  
**目标平台：** Windows  
**适用范围：** CodeBuddy 首个面向普通开发者的日用 Beta 及其后续演进边界

## 1. 摘要

CodeBuddy 的近期目标不是先完成完整企业 Agent 平台，而是交付一版普通开发者愿意每天使用的 Windows 代码 Agent。产品以 Codex 式任务线程和 Git worktree 隔离体验为参考，以多 Provider、稳定性优先的默认模型组合、宿主掌握真实证据和安全治理作为差异化。

Beta 首先服务现有项目中的代码分析、Bug 修复和中小功能开发。主 Agent 负责理解目标和动态决策，Rust 宿主负责工作区、权限、执行、证据、状态与恢复。Planner、Coder、Tester、Reviewer 从固定四角色流水线调整为按需能力；完整权威 Coordinator、全量事件溯源、多写入 Worker、企业平台、跨平台桌面、通用个人助理、完整浏览器/电脑自动化和大型项目生成均保留为 Beta 后路线，而非取消。

## 2. 背景与问题

CodeBuddy 已经具备多模型、任务 DAG、Coder/Tester/Reviewer、权限、审计、Git/GitHub、证据、取消和恢复等大量能力。当前架构正在从固定 Scheduler 主导的流水线迁移到主 Agent 语义决策与 Rust Control Plane 权威执行相结合的架构。

现阶段的主要风险不是缺少功能，而是：

- 用户日常任务闭环尚未成为唯一优先级；
- Planner 严格结构化输出仍可能成为执行前单点故障；
- 固定四角色和预编译 DAG 会增加简单任务的延迟、成本和失败面；
- 直接修改当前目录不能提供与 worktree 或 OS 沙箱等价的隔离；
- 完整事件存储、投影、Reducer 和权威 Coordinator 可能在产品价值验证前吸收过多开发资源；
- 自动化测试数量很多，但真实 Provider、安装态生命周期和真实用户任务指标不足；
- 历史路线、当前计划和 Git 实际状态需要收敛为单一事实源。

## 3. 产品目标

### 3.1 Beta 定位

CodeBuddy Beta 是面向 Windows 普通开发者的本地代码 Agent，通过隔离工作区安全完成现有项目中的分析、Bug 修复和中小功能开发，并提供可核验的 Diff、测试与恢复能力。

### 3.2 Beta 核心用户

- 在 Windows 上维护现有 Git 项目的普通开发者；
- 希望用自然语言完成分析、修复和中小改动，但仍要检查真实 Diff 和测试结果的用户；
- 不希望理解 Planner、DAG、模型路由和内部状态机的用户；
- 需要默认配置开箱即用，同时允许高级模型配置的用户。

### 3.3 Beta 核心场景

- 阅读、解释和分析现有项目；
- 复现并修复 Bug；
- 实现中小规模功能；
- 运行相关测试和质量检查；
- 查看 Diff、验证证据和未完成项；
- 将隔离任务合入本地项目，或安全放弃；
- 应用重启后恢复未完成任务。

### 3.4 成功原则

Beta 的第一优化目标是任务成功率和稳定性。成本和速度是次级指标，只有在不降低成功率时才通过更便宜模型、较少 Agent 或更短上下文优化。

## 4. Beta 范围与后续愿景

### 4.1 Beta 必须包含

- Windows 桌面安装、启动、升级、卸载和恢复闭环；
- Git 项目默认 worktree 隔离；
- 非 Git 项目快照保护和明确风险提示；
- 主 Agent 动态执行循环；
- 按需 Worker，默认单写入 Worker；
- 稳定性优先的推荐默认模型组合；
- 高级 Provider、模型和 fallback 设置；
- 宿主掌握的权限、审计、文件变化、命令和测试证据；
- 可查看、可合入、可继续和可放弃的任务结果；
- 有界取消、暂停、检查点和崩溃恢复。

### 4.2 Beta 后开发，不从愿景删除

- 完整企业管理平台；
- macOS/Linux 桌面版本；
- 通用个人助理和大量消息平台；
- 完整浏览器/电脑自动化；
- 默认多 Worker 并行写代码；
- 完整权威 Coordinator 与全量事件溯源能力；
- 从零自动生成大型完整项目。

这些能力不得成为首个日用 Beta 的发布阻塞项。Beta 后根据用户数据、风险和依赖顺序恢复开发。

## 5. 方案比较与决策

### 5.1 方案 A：Codex 式隔离任务工作台

每个开发请求形成独立任务；Git 项目默认使用 worktree；Agent 在隔离环境中理解、修改和验证；用户检查 Diff、测试和风险后决定合入、继续或放弃。

优点：

- 直接解决本地未提交修改与 Agent 写入冲突；
- 适合后台任务和后续并行能力；
- 用户心智模型清晰；
- 可渐进接入主 Agent、Worker 和 Coordinator。

代价：

- 需要实现 worktree 生命周期、交接、冲突和清理；
- 非 Git 项目仍需不同的保护模式；
- 合入增加一个用户确认步骤。

### 5.2 方案 B：优先完成完整 Control Plane

先完成版本协议、事件存储、投影、Reducer、RunEngine、Coordinator Shadow/Advisory/Authoritative 和桌面细粒度控制，再交付 Beta。

优点：架构完整，长期一致性和恢复模型清晰。

拒绝作为近期主路线的原因：产品价值尚未通过日用任务验证；双轨迁移周期长；会推迟真实用户反馈；存在为尚未发生的规模问题过度建设的风险。

### 5.3 方案 C：极简单 Agent 直接修改

暂停多 Agent 和新控制面，使用单 Agent 直接修改当前目录。

优点：最快形成演示版本。

拒绝原因：弱化现有证据、权限、恢复和多模型资产；无法提供足够的默认隔离；不适合作为可信日用工具。

### 5.4 决策

采用方案 A。保留 U-75/U-76 的协议和最小事件基础，但所有后续控制面能力必须服务于真实 Beta 纵向切片。完整权威 Coordinator 只有在 Shadow/Advisory 评测证明优于现有路径后才能成为默认执行中枢。

## 6. 架构原则

### 6.1 双层控制

系统采用“智能主 Agent + 确定性 Rust 宿主”：

```text
用户任务
  -> 主 Agent 理解目标并决定下一步
  -> Rust 宿主校验命令、权限、工作区和状态
  -> 工具、测试或可选 Worker 执行
  -> 宿主记录真实结果与证据
  -> 主 Agent 决定继续、修复、求助或结束
```

主 Agent拥有语义判断权，但没有权限批准权、权威状态写入权或成功事实定义权。Rust 宿主可以拒绝越权行动，但不替模型决定业务语义方案。

### 6.2 动态计划

- 简单任务不要求完整 DAG；
- 计划是可修订工作记忆，不是不可改变的预编译程序；
- Planner 输出异常时允许一次格式修复；
- 修复仍失败时降级为受限单任务主 Agent 模式，或明确向用户报告；
- 降级不得绕过权限、只读、工作区和证据边界。

### 6.3 按需 Worker

- Explorer 用于大型代码库的独立只读研究；
- Coder 用于边界明确的独立实现；
- Tester 用于独立上下文或长时间验证；
- Reviewer 用于高风险、大 Diff、发布任务或用户明确要求；
- 首版禁止 Worker 嵌套委派；
- 默认只允许一个写入 Worker；
- 并行写入必须使用独立 worktree 或宿主验证的互斥文件所有权。

### 6.4 宿主事实优先

- 文件变化来自工作区基线和实际文件系统，不来自 Worker 自述；
- 测试结果来自真实命令、退出码和有界输出；
- 权限拒绝不能通过换工具绕过；
- 不确定的外部副作用不能自动重试或声明成功；
- UI 状态来自后端权威状态，不能由前端动画推测。

## 7. 模块边界

### 7.1 Workspace

负责本地目录、worktree、非 Git 快照、冲突检测、合入和清理。不依赖模型，不生成用户结论。

### 7.2 Orchestration

负责主 Agent动态循环，接收宿主观察结果，提出继续、委派、暂停或结束候选。不能直接执行副作用或写入权威状态。

### 7.3 Workers

负责 Worker 注册、独立上下文、工具范围、取消令牌和结果合同。Worker 输出是候选证据，不是宿主事实。

### 7.4 Runtime / Control Plane

负责命令校验、权威状态、受管副作用、进程取消、幂等、检查点和恢复。不替主 Agent 做语义判断。

### 7.5 Evidence

负责真实文件变化、命令、测试、敏感数据和证据归属。必须覆盖内置工具、Shell、Python、MCP 和外部工具造成的间接写入。

### 7.6 Reporting

负责把内部 Run、Task、Agent 和证据投影为普通用户报告与技术报告。不得拥有执行能力。

任何模块若同时承担模型决策、权威状态写入、工具执行和用户报告中的两个以上职责，应重新评估并拆分。

## 8. 工作区模型

### 8.1 Git 项目默认模式

- 每个修改任务对应独立 worktree；
- 用户本地未提交修改不得被任务静默覆盖；
- 任务完成后可查看 Diff 和验证结果；
- 用户显式选择合入、继续或放弃；
- 合入冲突必须停止并解释；
- 放弃任务不得污染本地目录；
- 应用重启后能够重新关联任务与 worktree。

### 8.2 直接修改模式

直接修改当前目录作为高级显式选项保留。界面必须说明它可能与用户当前编辑冲突，不能把它包装成与 worktree 等价的安全模式。

### 8.3 非 Git 项目

使用宿主快照、路径约束、冲突检测和有界撤销包。界面明确标记“可恢复但未隔离”。自动化或不可信项目后续接入容器或远程沙箱。

## 9. 默认模型策略

- 普通用户默认只看到“推荐配置”；
- 默认组合以任务成功率和稳定性优先；
- 简单问答和只读检索可在评测不降级的前提下使用更快、更便宜的模型；
- 高级设置保留 Provider、角色模型和 fallback；
- 每个 Provider、模型和推理级别组合独立评测；
- 不通过结构化输出、工具调用、安全和证据门槛的组合不得进入默认配置；
- 不静默跨 Provider 发送用户数据；
- UI 和证据持续显示实际 Provider、模型和推理级别。

## 10. 用户体验

### 10.1 主流程

```text
选择项目
  -> 描述任务
  -> 系统判断只读或修改
  -> Git 修改任务创建 worktree
  -> 主 Agent 理解、修改和验证
  -> 必要时调用有限 Worker
  -> 展示结论、Diff、验证和未完成项
  -> 用户选择合入、继续或放弃
```

执行开始前只显示一句来自结构化策略的简短说明，不展示内部 Prompt 或完整 DAG。

### 10.2 运行中界面

聊天是主要交互面。输入区附近只显示紧凑状态，例如阶段、活跃 Agent 数、修改文件数和停止入口。命令、任务、证据与内部 Agent 状态默认折叠，用户主动展开后查看。

### 10.3 完成界面

完成卡片突出：

- 结论；
- 修改文件与 Diff；
- 验证结果；
- 下一步操作。

主要操作为合入本地项目、继续修改、放弃任务和查看技术证据。

### 10.4 用户状态

普通用户只看到：等待、工作中、需要你处理、已完成、未完成、已停止。内部细粒度状态不得原样作为普通用户错误提示。

## 11. 错误处理与恢复

- Planner 输出异常：修复一次，仍失败则安全降级；
- 工具参数错误：返回主 Agent修正，不自动扩大权限；
- 测试失败：区分代码缺陷、环境问题、错误命令和既有失败；
- 代码缺陷：回到修改循环，必要时调用 Coder；
- 环境问题：保留修改并说明缺少条件；
- 权限拒绝：等待用户决定，禁止换工具绕过；
- Worker 无进展：只停止该 Worker；
- 连续重复失败：暂停并保留成果，不伪装完成；
- 用户停止：停止新的模型调用，终止可管理进程，显示无法确认的外部操作；
- 应用崩溃或重启：从最后持久化检查点恢复；
- 结果不确定的外部写入：阻止自动重发并要求用户核实。

## 12. 完成定义

只有同时满足以下条件才显示“已完成”：

- 用户目标已经覆盖；
- 宿主确认预期文件变化；
- 必需验证实际执行并记录退出码；
- 没有未解决的阻断问题；
- 没有待确认的高风险或结果不确定操作；
- worktree 结果可查看、可合入或可放弃。

测试无法运行时只能显示“修改完成，验证未完成”。行动预算耗尽、环境缺失、用户停止和验证未完成不得伪装为项目成功或项目 Bug。

## 13. Beta 阶段

### 13.1 Beta 0：可信基线

目标：任何后续问题都能定位和回退。

- 完成或安全保存当前 U-76 切片；
- 修复 Planner 已知异常输出兼容问题并加入回归；
- 统一路线、完成状态和 Git 事实源；
- 产品代码没有来源不明变化；
- 完成 Rust、桌面端和安装包基线验证。

退出条件：主分支可构建，核心测试通过，每项新工作从明确提交开始。

### 13.2 Beta 1：隔离任务闭环

目标：安全完成一个真实修改任务。

- Git worktree 默认模式；
- Diff、测试和证据；
- 合入、继续、放弃和清理；
- 本地脏工作区保护；
- 非 Git 风险提示；
- 重启后任务/worktree 恢复。

### 13.3 Beta 2：动态主 Agent

目标：摆脱固定四角色必经流水线。

- 简单任务绕过完整 DAG；
- Planner 失败安全降级；
- 主 Agent根据真实结果继续；
- Worker 按需创建；
- Tester 失败可返回修复循环；
- Worker 失败不默认终止 Run；
- Coordinator 先以 Shadow/Advisory 参与。

### 13.4 Beta 3：稳定性与默认组合

目标：普通用户无需理解模型配置即可稳定使用。

- 版本化真实任务评测集；
- 默认模型组合资格；
- 崩溃、网络中断、模型失败和长任务验证；
- 安装、升级、卸载和数据保留验证；
- 成功率、延迟、Token、成本和人工介入记录。

建议工程门槛：

- 代表性任务首次执行成功率至少 80%；
- 允许一次自动修复后的成功率至少 90%；
- 错误修改或错误合入率低于 2%；
- 停止后不再产生新写入；
- 崩溃恢复成功率至少 95%；
- 安装、升级和卸载均有真实 Windows 证据。

样本不足时必须标记为未充分测量。这些数字是 Beta 工程门槛，不是市场承诺。

### 13.5 Beta 4：小范围日用测试

目标：验证开发者是否愿意持续使用。

观察每周完成任务数、接管或放弃比例、常见失败、Diff 查看比例、重复打开使用率和默认模型手动替换率。指标稳定后再扩大用户范围。

## 14. 测试体系

### 14.1 确定性合同测试

覆盖协议、状态、路径、worktree 所有权、权限、敏感路径、幂等、防重、Planner 解析与降级、完成判定和取消后禁止新副作用。每次相关提交运行。

### 14.2 真实仓库集成测试

固定夹具覆盖干净 Git、脏 Git、合入冲突、非 Git、间接写入、测试失败、缺少运行时、长命令、重启和检查点恢复。断言真实文件、进程和 Git 状态，不断言模型自述代替事实。

### 14.3 Provider/模型评测

同一任务集比较首次成功率、修复后成功率、结构化输出、工具调用、安全、错误完成声明、Token、费用和延迟。默认模型只能由这层评测产生。

### 14.4 安装态 Windows 验收

使用真实安装包验证首次安装、启动、打开项目、完成/合入/放弃、崩溃恢复、升级、卸载和连续运行。开发态 Electron 通过不能代替安装态验收。

## 15. 现有路线调整

- U-74F：已完成，只保留回归；
- U-75：保留，作为版本化协议基础；
- U-76：继续最小事件存储、投影和恢复基础，不在该阶段切换生产事实源；
- U-77：拆分，只先实现动态主 Agent 所需的最小 Runtime；
- U-78 Shadow：保留，用于与旧路径比较；
- U-79 Advisory：Beta 2 可启用，仅允许低风险建议；
- U-80 Authoritative：推迟到真实评测证明收益后；
- U-81：任务/worktree/合入 UI 提前到 Beta 1，多 Agent 细粒度控制推迟；
- U-82：安装态验证、Provider 评测和恢复验证提前到 Beta 0-3；
- U-60 及外围能力：保留设计，Beta 稳定后恢复。

## 16. Beta 后演进顺序

默认评估顺序为：

1. 权威 Coordinator 与完整事件溯源；
2. 多 Worker 并行写入与合并；
3. 浏览器和电脑自动化；
4. 从零生成大型项目；
5. 企业策略、组织管理和云执行；
6. macOS/Linux 桌面版本；
7. 通用个人助理与消息平台。

真实用户数据可以调整顺序，但后续能力不得破坏任务成功率、工作区隔离、停止语义和恢复门槛。

## 17. 单一事实源

- Git 提交和门禁记录决定当前完成状态；
- 旧阶段文档明确标记为历史资料；
- 同一能力只有一个当前计划；
- 未接入生产路径的能力不得写为用户可用；
- `PASS`、`BLOCKED`、`NOT_RUN`、`NOT_MEASURED` 严格区分；
- 文档中的测试数字必须能追溯到原始命令、提交和结果。

## 18. 影响与代价

正面影响：

- 更早形成可日用产品并获得真实反馈；
- worktree 降低覆盖和并行冲突风险；
- 主 Agent 提升失败恢复和动态调整能力；
- 保留 Rust 宿主的权限、证据和确定性优势；
- 多模型成为受评测的高级能力，而不是普通用户负担。

代价与风险：

- worktree 生命周期与交接需要新的桌面和 Git 集成；
- 新旧编排路径仍需一段受控共存期；
- 收缩 U-76/U-77 会要求重写部分既有路线文档；
- 推荐默认模型需要持续评测和维护；
- 非 Git 项目在引入 OS 级隔离前仍只能提供恢复保护；
- 推迟完整权威 Coordinator 会暂时保留部分旧 Scheduler 复杂度。

这些代价可接受，因为它们直接换取更早的真实日用验证，并降低在用户价值未证实前进行平台级重构的风险。
