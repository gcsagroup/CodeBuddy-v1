## 4. 视觉只读边界：不能只修下拉框

`crates/goose-provider-types/src/canonical/catalog.rs::get_provider_setup_category` 只精确匹配目录 ID。旧注册 ID `claude-code`、`codex`、`gemini-cli` 与新目录 Agent ID 不一致，查询可能返回 `None`；Inventory 会回落为普通 Model。

ACP 的视觉配置保存检查，以及 `crates/goose/src/agents/platform_extensions/computer/vision.rs::analyze_screenshot` 的调用前检查，也依赖这一分类，只拒绝显式 `Some(Agent)`。

因此这是共享分类事实的问题，不只是显示问题。视觉适配器传空工具列表，不足以证明一个自带执行循环的 CLI Provider 只读；旧 CLI 还会根据全局 GooseMode 使用自己的权限参数。

没有证据表明本次截图已导致越权动作：当前没有保存视觉路由，这次教务会话也没有相关视觉调用。这里记录的是需要阻断的静态风险，不是已发生的安全事故。

修复边界：由厂商元数据/分类的共同权威提供准确分类；UI、保存和运行前检查一致消费。不要分别堆 ID 字符串例外，也不要为了兼容放宽视觉只读约束。验证应以假 Provider 工厂证明拒绝发生在实例化/发送截图之前，不需要真实执行桌面输入。

## 5. “已确定执行策略”为什么仍显示

- 原始持久事件是 `strategy_selected`。
- `crates/goose/src/acp/server.rs::send_status_message_update` 将 ActivityEvent 转为 PublicProgress，丢失原始 `event_type/event_id`，`attempt_id` 为空。
- `ui/desktop/src/components/codepro/codeProActivityModel.ts::publicProgressEventType` 将 planning/completed 重新投影为 `plan_created`。
- `ProgressiveMessageList.tsx` 隐藏的是成功的 `strategy_selected/strategy_updated`，因此真实传输路径绕开了规则。

使用本次原始事件和当前转换逻辑的内存复现结果：原始事件会被隐藏；转换后变成 `plan_created`，不会隐藏。现有前端隐藏测试直接输入原始事件，所以单测通过也无法证明真实链路正确。

另一个风险：`acp/adapter/gooseSessionNotifications.ts::upsertPublicProgress` 以 run+attempt 作为更新键。同一 run 转换出的多个空 attempt 活动会命中同一行。不能用伪造 attempt ID 解决，也不能从中文标题反推事件类型。

修复边界：保留结构化事实身份，优先核查已有 status_message/ActivityEvent 通道能否完整承载；真实 worker PublicProgress 维持其真实 attempt 语义。验收覆盖服务端转换到 UI 的边界，而不只给组件喂理想输入。

## 6. 当前标题、文件生成与最终总结是三个环节

### 当前标题过早失效

`currentWorkStage.ts` 一旦发现最新工具不是 `publish_progress`，就返回空值；工具结束后也不会恢复之前阶段。这个规则避免旧 `data.js` 一直挂着，但同时把仍有参考价值的阶段全部丢掉。`BaseChat.tsx` 的活动工具结束后也没有具体动作可显示，于是 `LoadingGoose` 回到“CodePro 正在处理中”。

不能简单恢复旧逻辑，否则会重现“文件写完还说正在写”。应分别消费真实工具状态、参数生成预览、模型响应阶段；模型发布的阶段描述只作说明，不作为正在执行某文件操作的证据。没有具体动作事实时，应诚实展示等待模型响应，而不是编造“正在写某文件”。

### 文件生成缺少动态预览：尚未定责

本次 28 次写入审计耗时约 19–506 毫秒。18:59:51、19:00:19、19:00:29 分别出现几个完整写入；19:00:53 发布阶段后，19:01:46 集中出现 9 个完整写入。这些是完整工具调用/执行记录，不是网络分片到达时间。

现有链路已经包含参数生成时的 `tool_input_preview`、Agent 临时通知转发、ACP pending tool call 和 UI preview 适配。会话导出不完整保留这些临时预览，不能因为导出没有它们就判定服务未流式返回。

已有 `GOOSE_STREAM_TIMING=1` 观测，并在 INFO 的 `goose::stream_timing` 目标记录时序；本次候选未启用，默认 warn 日志也不提供这些记录。这是候选验证准备的缺口。

下一次只需一次受控短请求，按同一 request ID 对照网络 body chunk、解析输出、ACP 发送、UI 接收的时间及数量；不记录整段代码或凭据。先确定缺口在哪一段，再修，不通过人为延长“正在写入”制造流式假象。

### 最终总结一次性出现：存在宿主缓存

`agent.rs` 约 13620 行起先缓存独立正文，识别为继续工作时才释放 commentary；约 15056 行起在完成检查通过后构造完整文本消息发送。因此主链路的最终总结即使上游流式产生，也可能在 UI 一次出现。

这不能解释所有上游等待时间，却已经否定“只要修 SSE 就能解决最终总结突现”的假设。若要真正流式展示，需要明确尚未确认的正文与已通过完成检查的结果边界；不能取消完成门槛，也不能把整段结果切成小段伪装网络流式。
