# CodeBuddy 記憶模組最佳化設計

日期：2026-09-11。複核：2026-09-12。狀態：已確認，作為基礎版本與後續演進的實作基線。

[简体中文](2026-09-11-memory-module-optimization-design.zh-CN.md) · [English](2026-09-11-memory-module-optimization-design.en.md)

## 1. 結論

CodeBuddy 應將「固定規則、專案記憶、使用者習慣、對話歷史」拆成四個邏輯層，而不是繼續把它們視為同一種記憶。

- `AGENTS.md` 只存放使用者或團隊明確確認、需要穩定執行的規則。
- AI 推斷的使用者習慣保存在使用者記憶中，預設不能直接改寫 `AGENTS.md`。
- 專案事實與工作經驗保存在專案記憶中，必須維持專案隔離和來源資訊。
- 完整對話繼續保存在 session 資料庫，不能複製成大量長期記憶。
- 取消「記憶總筆數／總檔案大小達上限後拒絕寫入」的產品機制，改為無損歸檔、按需檢索和可觀測的磁碟保護。
- 保留單筆長度、查詢回應、主動注入上下文和安全掃描上限；這些是執行安全邊界，不是記憶容量上限。

直接回答「使用者習慣是否也寫入 `AGENTS.md`」：**不寫入**。AI 學到的習慣先進入獨立、可審核的使用者記憶；只有使用者主動點選「轉為固定規則」並確認差異後，才寫入全域規則檔案。

## 2. 背景與現況

目前實作已具備專案 identity 隔離、跨工作階段持久化、TTL、CRUD、搜尋、分頁、匯出、備份恢復、active/archive 分層，以及 `project_rule`、`preference`、`verified_fact` 等類型。設定頁也已提供 Project Memory 與個人化記憶開關。

目前主要問題：

1. 規則、事實和偏好共享同一記憶通道，權威性不夠清楚。
2. AI 推斷偏好與使用者明確規則的 UI 和資料語義不夠分離。
3. active 500 筆、1 MiB soft／2 MiB hard 等限制容易被理解為「總記憶容量」，並可能讓正常寫入因容量被拒絕。
4. 自動注入以近期項目為主，相關性、來源與命中原因仍需增強。
5. JSON active/archive 適合目前規模，但長期累積後，全文搜尋、更新和一致性成本會上升。

## 3. 參考設計與取捨

### Codex

Codex 將持久指令與生成記憶分開：全域／專案指令使用分層 `AGENTS.md`，歷史對話提取內容保存在獨立的本地記憶儲存。必須遵循的規則應放在 `AGENTS.md` 或版本控制文件中；記憶只作為輔助回顧資訊。Codex 的專案指令還有主動載入大小邊界，因此 `AGENTS.md` 不是記憶資料庫。

採用：規則和記憶分層、全域與專案範圍、記憶生成和記憶使用分開控制。
不採用：讓 AI 靜默產生或覆寫專案規則。

參考：[Codex AGENTS.md](https://learn.chatgpt.com/zh-Hant/docs/agent-configuration/agents-md)；[Codex 記憶](https://learn.chatgpt.com/zh-Hant/docs/customization/memories)

### Claude Code、Hermes、Pi 與其他 Agent

可觀察的成熟方案普遍使用「人工維護的指令檔 + 按需載入的歷史／記憶 + 有界的目前上下文」。Hermes 類方案重視 session 搜尋與全文索引；Pi 類方案保留完整 session、分支與壓縮；Claude Code 將人工記憶檔和自動記憶分開。共同點不是無限塞入提示詞，而是讓持久儲存可以增長、每次召回保持有界。

採用：持久儲存與提示詞預算分離、可追溯檢索、完整 session 與摘要分離。
暫不採用：第一階段引入向量資料庫、雲端同步或複雜知識圖譜；它們會延長交付時間，且不能先解決規則污染和跨專案洩漏。

## 4. 目標與非目標

### 目標

- 使用者能在設定中直接管理全域規則；專案規則由系統依工作目錄自動識別。
- AI 能學習低風險、穩定的使用習慣，但可查看、刪除、停用和升級為固定規則。
- 記憶總量不因固定筆數或固定總檔案大小而停止成長。
- 每次模型呼叫只注入少量、相關、可解釋的內容。
- 不同專案、使用者和工作區之間不可互相洩漏。
- 所有寫入和召回都能回答「誰寫的、為何寫、何時寫、從哪裡來」。

### 非目標

- 不把全部聊天內容自動轉成長期記憶。
- 不讓 AI 自動修改已提交的團隊規則。
- 第一版不提供跨裝置雲端同步、不上向量資料庫、不建立知識圖譜。
- 不以刪除舊記憶作為一般容量管理方式。

## 5. 分層架構

### 5.1 對話歷史

- 儲存：既有 `sessions/sessions.db`。
- 內容：完整訊息、工具呼叫和工作階段狀態。
- 用途：繼續原對話、稽核和生成候選記憶。
- 不會在每次新對話中完整載入。

### 5.2 專案規則

- 儲存：專案根目錄或就近目錄的 `AGENTS.md`／`AGENTS.override.md`。
- 內容：建置命令、測試要求、程式碼規範、安全限制和團隊工作流程。
- 寫入：使用者直接編輯；AI 只能產生草稿或建議差異，必須由使用者確認。
- 特性：權威、可版本控制、依目錄範圍覆蓋。

### 5.3 使用者全域規則與習慣

- 明確規則：儲存在使用者電腦的 `.CodeBuddy/AGENTS.md`，由「行為與回答」設定頁的多行輸入框管理；第一次儲存時建立檔案。
- 相容性：舊版 `profiles/<profile>/AGENTS.md` 僅作為根目錄檔案不存在時的讀取備援，不再作為新寫入位置。
- AI 習慣：保存在 `profiles/<profile>/memory/user/`，使用結構化記錄，不直接寫入全域 `AGENTS.md`。
- AI 習慣可以由使用者點擊「轉為固定規則」，經預覽後加入全域規則。
- 載入順序：先載入全域規則，再由專案根目錄到目前工作目錄逐層載入就近規則；同一目錄中 `AGENTS.override.md` 優先於 `AGENTS.md`。較近的專案規則只覆寫衝突內容，變更從新對話開始生效。

### 5.4 專案記憶

- 儲存：`profiles/<profile>/memory/projects/<project-id>/`。
- 內容：經驗、已驗證事實、架構決策和近期工作摘要。
- 專案 identity 必須使用規範化路徑和穩定 ID；介面顯示目前所屬專案，避免誤刪。
- 專案搬移／重新命名時提供明確的重新綁定或複製流程，不能偷偷合併。

## 6. 設定頁設計

記憶設定頁分為三個區塊：

1. **CodeBuddy 說明**：位於「行為與回答」，提供多行輸入框、明確儲存按鈕、外部修改衝突保護和實際檔案位置；寫入 `.CodeBuddy/AGENTS.md`，適用於全部新對話。
2. **專案規則自動識別**：設定頁不提供手動選擇資料夾的卡片。開啟專案時從專案根目錄到目前工作目錄逐層載入規則；工具讀寫更深層目錄時再載入該目錄鏈上的就近規則。系統只讀取並注入規則，不複製到記憶資料庫，也不自動建立或改寫專案檔案。
3. **AI 學到的習慣**：卡片列表顯示內容、來源、信心、建立時間和最後命中時間；提供保留、編輯、刪除、停用和「轉為固定規則」。

保留兩個獨立開關：

- **使用記憶**：是否在後續對話中檢索和注入現有記憶。
- **允許產生新記憶**：是否允許目前對話成為 AI 習慣或專案記憶的來源。

關閉任何開關都不刪除資料。刪除和清空必須是獨立、可確認的操作。

## 7. 資料模型

每條結構化記憶至少包含：

```text
id, scope, kind, subject, content,
source, source_ref, reason, confidence,
created_at, updated_at, last_used_at,
expires_at, status, schema_version
```

- `scope`：`user` 或 `project`。
- `kind`：`preference`、`verified_fact`、`decision`、`work_summary`。
- `source`：`user_explicit`、`user_approved`、`ai_inferred`、`project_verified`。
- `status`：`candidate`、`active`、`disabled`、`expired`。
- `confidence` 只用於 AI 推斷，不得覆蓋使用者明確規則。
- `source_ref` 對已驗證專案事實為必填，且只能指向目前專案內的安全相對路徑。

`project_rule` 不再作為一般記憶種類新增；現有 `project_rule` 在遷移時轉為候選規則，由使用者決定寫入 `AGENTS.md` 或降級為普通專案記憶。

## 8. 寫入策略

1. 使用者直接在設定輸入的規則，點擊儲存後寫入對應規則檔。
2. 使用者在對話中明確說「記住」時，寫入 `user_explicit` 或 `user_approved` 記憶。
3. AI 自動學習只接受穩定、低風險的互動習慣，例如語言、回覆長度和常用工具；初期寫入 `candidate`，由使用者確認後轉為 `active`。
4. 密碼、API key、token、身分證號、支付資訊、私密通訊內容和一次性任務細節不得成為長期記憶。
5. 相同 scope + kind + subject 使用更新或版本化，不產生無限重複項。
6. AI 不得將推斷內容寫入 `AGENTS.md`；只能建立可審核的提升建議。

## 9. 檢索與上下文預算

使用者可設定層內的優先順序：

```text
目前對話明確要求
→ 就近專案 AGENTS.override.md / AGENTS.md
→ 使用者全域規則
→ 已確認且與任務相關的使用者習慣
→ 專案記憶
→ 歷史工作摘要
```

系統和開發者政策始終高於以上所有層。

主動注入保持有界，建議第一版總預算 6,000 字元：規則優先，剩餘空間再分配給使用者習慣和專案記憶。候選、停用、過期或來源失效的項目不主動注入。

相關性分數由以下訊號組成：範圍匹配、關鍵字／FTS 命中、記憶種類、使用者確認、來源可信度、近期使用和重複懲罰。回傳時提供簡短的命中原因；若沒有相關項目，不應為了填滿預算而注入內容。

## 10. 取消容量上限的精確含義

應移除：

- active 500 筆作為總容量門檻的產品語義。
- 1 MiB soft／2 MiB hard 導致正常記憶寫入失敗的總檔案限制。
- 任何因「太舊」或「超額」而靜默刪除使用者資料的行為。

應保留：

- 單筆內容、subject、reason 和來源路徑長度限制。
- 每次提示詞注入、搜尋回應、分頁大小和工具輸出限制。
- 檔案損壞、路徑穿越、符號連結、秘密和指令注入檢查。

當磁碟空間不足或資料庫不可寫時，系統應拒絕該次寫入並顯示可操作錯誤，不能刪除既有資料。設定頁顯示磁碟使用量，但不以固定配額阻止正常累積。

## 11. 儲存演進

### 第一階段：快速交付

沿用現有檔案格式和 ACP 合約，完成規則／記憶分層、設定 UI、候選習慣、獨立的 use/generate 開關，以及取消總容量拒絕。active/archive 改為召回層級，不再代表使用者容量。

### 第二階段：資料量增長後

將結構化記憶遷移到 SQLite + FTS5；完整 session 資料庫保持獨立。以 schema version、備份、驗證、原子切換完成一次性複製遷移，原檔在使用者確認前保留。向量檢索只有在固定評測證明 FTS5 無法滿足中文和語意召回時才引入。

## 12. API 與錯誤處理

沿用既有搜尋、記住、忘記、清空、統計和匯出能力，新增或調整：

- 讀寫全域規則，並從目前工作目錄鏈自動發現唯讀專案規則。
- 列出候選習慣、批准、拒絕、停用和提升為固定規則。
- 分開設定 `use_memory` 與 `generate_memory`。
- 搜尋結果返回 scope、source、confidence、source_ref 和 match_reason。

所有 mutation 使用穩定 request ID 和原子寫入。寫入失敗保留原資料；UI 顯示實際後端狀態，不以樂觀狀態掩蓋失敗。規則檔有外部修改時，儲存必須偵測版本衝突並要求重新載入或比較，不能覆蓋他人修改。

## 13. 測試與驗收

### 後端

- 規則、使用者習慣、專案記憶和 session 互不混寫。
- AI 推斷不能直接修改 `AGENTS.md`。
- use/generate 開關互相獨立，關閉不刪除資料。
- 超過舊 500 筆和 2 MiB 後仍能寫入、搜尋和重啟恢復。
- 提示詞和工具回應仍符合各自預算。
- 不同專案、重新命名、過期、併發寫入、損壞恢復和低磁碟空間行為可重現。

### 桌面 UI

- 元件測試涵蓋全域說明、儲存失敗回滾、外部修改衝突，以及手動專案資料夾入口已移除。
- 只有使用者明確點擊儲存才建立全域 `AGENTS.md`；專案 `AGENTS.md` 只自動識別，不修改。
- 候選習慣的批准、拒絕、刪除和提升流程。
- 兩個開關的四種組合與重啟持久化。

### 真實使用者流程

從修改後的後端啟動 Electron，以真實視窗、滑鼠和鍵盤完成：設定全域規則、在新對話中驗證既有專案規則被自動識別、產生候選習慣、批准後跨專案召回、拒絕後不再召回、重啟後狀態一致。另用兩個專案驗證隔離，並檢查實際檔案、資料庫和日誌。

## 14. 成功標準

- 100% 的固定規則都有明確使用者寫入或批准事件。
- AI 推斷習慣直接寫入 `AGENTS.md` 的次數為 0。
- 超過舊容量門檻後不丟資料、不停止正常寫入。
- 跨專案錯誤召回為 0；敏感資訊持久化為 0。
- 固定評測集上的相關記憶命中率提升，無關主動注入率下降。
- 所有召回項目都能顯示來源和命中原因。

## 15. 交付順序與預估

為縮短交付時間，基本版本只實作最小閉環：

1. 全域規則輸入框、專案 `AGENTS.md` 自動識別、外部修改衝突保護：0.5–1 個工作日。
2. 沿用既有結構化專案記憶，取消總筆數/總檔案大小拒絕，並保留單筆與上下文安全預算：0.5–1 個工作日。
3. 兩個記憶開關、後端回歸、UI 測試和真實 Electron 關鍵流程驗收：1 個工作日。

單人基本版本預估 **2–3 個工作日**。AI 自動推斷習慣、候選批准流程和 SQLite + FTS5 是後續獨立里程碑，不阻塞基本版本；使用者明確說「記住」的內容仍可進入既有結構化記憶。實作必須在目前髒工作區中遵守檔案所有權並逐階段驗收。

## 16. 可執行的真實後端驗收案例

以下案例必須使用從目前原始碼建置的 CLI／桌面後端與獨立 `CODEBUDDY_HOME`；直接修改 JSON、mock ACP 或只通過元件測試不能替代後端驗收。每個案例記錄工作目錄、完整命令、退出碼、測試數量、後端二進位 SHA-256、儲存路徑和日誌路徑。未執行的案例標記 `NOT_RUN`。

基本版本必須通過 BE-01、BE-02、BE-03、BE-04、BE-05、BE-07 和 BE-08。BE-06 屬於後續「自動習慣候選」里程碑，不阻塞基本版本發布。

| 編號  | 前置條件與操作                                                                                      | 必須觀察到的結果                                                                                        |
| ----- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| BE-01 | 經真實 `project_memory_remember` 寫入超過舊 500 筆與 2 MiB 門檻的資料，重新啟動後繼續寫入。         | 所有寫入成功；active 熱資料可輪替到 archive，但總筆數不減少，且不再出現「容量已滿」拒絕。               |
| BE-02 | 對 BE-01 中已進入 archive 的唯一內容執行 `project_memory_search`，再重啟並重複查詢。                | 兩次都返回同一記憶、scope、source 與 evidence；archive 不會因重啟遺失。                                 |
| BE-03 | 經 ACP list/stats 查詢包含 active、archive、project 與 user scope 的資料集。                        | `usageBytes` 涵蓋全部持久化記憶；相容欄位的容量值為 0／無限制，UI 不把它判斷為已滿。                    |
| BE-04 | 在專案 A 寫入唯一記憶，使用專案 B 的工作目錄查詢與開啟新會話。                                      | B 無法搜尋或自動召回 A 的 project scope 記憶；user scope 只在明確啟用時跨專案可用。                     |

| BE-08 | 模擬單筆損壞、原子寫入中斷和可重現的低磁碟空間條件。                                                | 舊資料仍可恢復或隔離；錯誤明確指出儲存失敗，不把環境問題誤報為容量上限，也不破壞其他專案資料。          |
