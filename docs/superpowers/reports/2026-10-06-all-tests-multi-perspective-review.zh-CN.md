### 当前失败处理：已有停机出口，恢复和交接质量仍不齐

- `main_agent_contract.rs` 和 `agent.rs:9859` 提供 `report_blocked`。宿主校验 active run、非空和长度，再以 `completion_blocked` 暂停；不会因交接文字清掉 Unknown。用户说明要求具体成果、实际检查、剩余影响和安全下一步，但内容质量仍由模型负责，宿主不验证每句业务自述。
- `agent.rs:1520` 将交接说明明确归属于模型，并另列未确认动作数量。这保留真实边界，但常见“模型说已交付 / 宿主说未确认”的组合仍让用户难判断成果是否可用。不能隐藏后者，也不能让 UI重新猜谁对。
- `tool_task.rs:772–788` 只有部分绑定的 managed-process stop 可以回原 owner 查询结清；其他历史动作明确无支持的绑定对账入口。诚实交接有效，但不能把它说成恢复能力已完整成立。
- `tool_task.rs:1351–1427` 按工具名与参数指纹计相同调用失败，当前执行中第二次要求复盘、第三次进入收尾；恢复重建会清空失败计数，不能称为持久跨轮累计。`agent.rs:13755` 的收尾不再供给执行工具。另一方面，观察类排除使用有限旧工具名集合，不是统一只读权限事实；当前部分 qwen 观察调用的成功也可重置计数、进入 distinct_successes。Main Agent 的 Auto 执行到 Finalize 边界且 tracker 允许时，可据新 distinct success 延长预算，上限受配置与 180 轮限制。它不能证明用户验收项有新进展，仍可能延长低价值尝试，但不能称为无限循环。
- 完成提案以宿主事实指纹和规范化 gaps 识别重复拒绝，再要求交接。修改 coverage 参数本身不保证重置；只有改变被比较的事实或拒绝缺口才可能形成不同状态。有 Unknown 时指纹聚焦未结动作集合，不以无关探测成功结清。库存实际有合法修订路径而模型未用对；订单实际通过改窄义务收口。前者不能称为 Host 无解，后者也不能称为可靠完成。
- `codepro_terminal_report.rs:21` 对模型错误区分限流、认证、额度等，保留已记录文件并不宣称功能验收；旧未完成 renderer 也保留退出码与缺口。通用错误建议继续并不证明每个 Unknown 都有恢复入口。
- UI `turnTerminal.ts` 和 `chatSessionController.ts:589` 根据结构化 checkpoint/retry_strategy 控制继续、关联重放、验证重试，不是任意文字生成一个“继续”按钮；这些入口的跨停止、重载、未知效果行为没有在本批真实 E2E 完整验收。`SessionManager::finish_unified_turn` 只记录本轮 finished/paused，源码明确不认证整个用户目标，不能把它当 runtime Completed。

任务真的无法完成时，交接应回答：本次完成了什么；没完成什么；原因哪些已确认、哪些未知；已有改动是否保留及可用范围；继续需要谁补什么；哪些动作不能直接重做。它是表达准则，不是 Host 固定业务流程。认证/额度/授权问题才要求相应用户介入；内部证据存储或关联问题不能让用户去填内部参数或证明旧动作成功。

例如预约实现轮应表达“预约工具还没做出来，本轮没有生成新页面。模型响应流中断，具体原因尚未确认；之前查到的资料保留。恢复后继续实现剩余功能”，而不是只说“最后的交付确认没通过”，也不能承诺下一次一定成功。部分完成的任务则要保留已核实成果，不笼统宣布全部不可用。

### 与成熟公开做法的差距

这里只比较公开协议与恢复指南，不推断竞品私有实现或成功率：

1. [Codex App Server](https://learn.chatgpt.com/docs/app-server) 分开 turn 状态、item 生命周期、文字增量和错误；`turn/completed` 事件内仍可能是 failed/interrupted。可借鉴的是稳定身份和权威状态的呈现，不能把结束事件或模型 final 文本当业务成功。当前已有相应分层，但复查、任务进度和交接的呈现仍不够一致。
2. [OpenAI Agents API：Errors and recovery](https://developers.openai.com/api/docs/guides/agents-api/errors) 要求先查询结果与已发生动作，再有限重试；认证、无效输入与额度问题先修原因；断流本身不证明最终状态。它不是 Codex 桌面内部实现的保证。对照本项目，短板是原动作对账能力、失败生产者语义和部分继续建议尚未形成可验的闭环。
3. [Claude Agent SDK：Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop) 以结构化 result subtype 区分正常结束、执行错误、轮次/预算耗尽，保留 session 信息供后续处理，并区分模型 stop_reason 与执行结果。可借鉴清楚的终止原因及续接身份；SDK success 同样不能替代成品实际验收。

不需要照搬框架、新 DAG 或语言分类器。优先级仍是原验收义务不缩水、上下文来源不冲突、失败后可对账或准确停止，然后再优化交接与界面层级。这七题跨版本、任务类型与干扰条件不同，不能计算产品总体成功率；但足以确认 Host 有独立于模型能力的缺陷。

下一批连续用户过程至少覆盖：正常交付；已改文件后模型中断再继续；不可结清的原动作交接且不重放；参数错误可修正与确需用户处理的故障分别退出。每题核对界面解释、持久化事实与实际效果相符，不以按钮存在、工具 success 或文案漂亮作为 PASS。
