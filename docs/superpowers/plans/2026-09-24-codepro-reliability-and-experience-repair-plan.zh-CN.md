# CodeBuddy 连续开发、事实闭环与过程体验修复计划

日期：2026-09-24。版本：R3。状态：**FROZEN_FOR_REVIEW（修订冻结送审，实施待用户批准）**。

本文件冻结本批目标、问题范围、权责、实施顺序、验收与停止条件，不冻结具体 Rust 类型或局部实现算法。用户批准后可在该边界内连续实施，不逐个小步骤询问；当前仅完成计划，不代表修复、自动验证、构建或 E2E 已完成。

本次用户授权是落实剩余计划与验收边界，不视为产品实现或协议迁移的开工批准。R2 相对 R1 的差异见第 13 节，R3 对六项补充审查的采纳及限定见第 14 节；R1 可从提交 `25d4d48c1c2f90ef161f726bc1a76f013cd1ee5f` 恢复查阅。R2/R3 仍为同一计划的未提交修订，不另建并行有效计划。

## 1. 新起点与最终目标

**做一个内核工作方式和外表交互体验尽可能接近桌面版 Codex 的 CodeBuddy，不为差异化另起一套。**

这里的“接近”落实为正常开发闭环、低负担澄清、有界自主、连续恢复和简洁可信的过程展示，不声称复制不可见的私有实现。公开实现能复用时优先评估复用，其次才是适配；不以“必须自己实现”作为选择理由。现有 Main Agent 主循环是本批打通对象，不整套换引擎或扩成全功能桌面复刻。

目标不丢、受阻能停、恢复有据、交付可验、过程可懂，是实现上述产品目标的底线，不是另建一套特色架构的理由。

本批不是“把几个用例调绿”，也不是重建架构。需要同时实现以下结果：

1. 当前目标、项目对象、授权、执行和完成判断属于同一条可追踪的事实链；暂停后的聊天不能绕过已暂停的运行继续修改文件。
2. 正常开发能贯通“确认关键前提 → 读改 → 运行验证 → 根据结果调整 → 交付”，不把宿主内部故障转嫁为用户技术选择题。
3. 完成由当前要求匹配的实际效果支撑；无法继续时有真实、可行动的阻塞说明，既不假完成，也不无限复核。
4. 继续、补充、替换目标、撤回要求、取消、压缩后恢复各有正确含义；不把“继续”“2”变成脱离原任务的新目标。
5. 默认开发路径能展示阶段说明、轻量可折叠的实际操作和真实修改证据，实时与重载一致。

两条验收线分别记录：**执行正确性**与**开发/交互可用性**。任一未达标，都不能笼统宣称本批产品通过。

| 明确的小修复 | 直接探查并推进；低风险可逆的技术选择由 Agent 决定，必要时说明假设 | 为流程完整强制问卷、逐项审批实现细节 |

| 工具失败或环境受阻 | 把具体 observation 交回 Main Agent，自主诊断、换合法方案；确需用户行动时给一句可理解说明 | 让用户修宿主、反复说“请继续”，或通过换工具绕权限 |
| 任务进行与交付 | 正文讲发现和下一步，操作轻量折叠，结束展示真实修改与验证结果 | 工具卡片淹没正文、隐藏异常、把模型思考当进度或完成证据 |

ask_user 是需求澄清工具，不是问题本身；正式权限审批是另一条事实链。推荐选项不是已提交回答，自由文本回答也不是权限决议。不为“完整版”“全栈可运行”等示例词建立识别规则；验收还要用不同措辞和不同业务场景检查泛化。

**无人答复：** 可以合理、可逆默认的实现选择，优先说明假设后推进，不先发一张非必要问卷。问题未答时，不把推荐项当已选答案，不重复询问同一未变化的信息；在运行状态允许的前提下继续不依赖该答案的已授权工作。确实影响交付形态、范围或不可逆决定时不擅自默认；无可推进工作才进入明确等待。权限审批绝不能超时默认同意。

当前 ask_user 是同步等待、300 秒超时返回 unanswered；上述规则不能只补到超时后提示词就宣称等待期间可并行推进。优先用现有 Main Agent 决策/工具调度避免非关键问题阻断可做工作，并验收实际等待时序；若必须新增异步提问公共协议，按第 11 节单独送审，不在本批暗加一套调度机制。

## 2. 冻结边界：保留什么，不做什么

### 2.1 必须保留

- 动态 Main Agent 为默认工作入口；共享骨架和集成可由主 Agent 完成，有明确独立价值时才委派。
- 模型理解语义、提出计划/修订/覆盖提案；宿主维护来源、版本、授权和真实执行事实，验证确定性条件。
- 现有 Reducer 是唯一状态转换权威，RunEngine 提交，EventStore 留痕，Projection 供下游消费。
- 现有 requirement/evidence/权限/恢复机制继续作为唯一事实来源；Convergence 不变成第二个语义裁判。
- N01 的零改动完成、N03 的“诊断完成但项目仍失败”、真实记忆任务的记忆交付、人工取消的非失败语义。
- 用户后续有效选择可以撤回旧义务，例如“不 delegate 了”；不能永久强制已经撤销的独立审查。

### 2.2 本批明确不做

- 不恢复固定 Planner→Coder→Tester，不强制委派数量，不新增永久 Judge、核心状态系统、第二套 requirement/evidence store 或 completion evaluator。
- 不建设完整持久化 ActionAttempt 系统；使用既有调用身份、审计、状态与结果对账边界。若不足以安全实现，按第 11 节停下提出最小扩展，而不是偷偷新建。
- 不用命令名、中文固定短语或 substring 规则直接裁决意图、授权、否定范围、目标切换或完成。
- 不给记忆/Git/工具名加完成黑名单；不要求所有变更任务都必须测试退出码 0。
- 不把自主模式等同无限权限，不通过改执行器、委派、工具别名绕过拒绝。
- 不引入外部记忆模块，不整套迁移 Codex/LangGraph/OpenHands，不修 WorkBuddy 项目，不全面重做导航/主题/编辑器。
- 不新增自动撤销系统、总结 Agent 或后台猜测进度的状态机；无真实 diff 不伪造增删行和“撤销”。
- 不安装或更新依赖、清缓存、切换 toolchain/profile/features/target，不新建 worktree，不自动提交、推送或合并。

## 3. 事实权责与不变量

以下名称表达现有职责，不要求照此新增同名类型。实施前逐一映射到实际调用点；禁止多个消费者重新解释同一原文。

| 事实 | 唯一责任边界 | 消费者不得做的事 |
| --- | --- | --- |
| 当前用户要求与修订 | 现有语义提案及 requirement 提交边界；宿主绑定来源和 supersession，Reducer 提交 | 从 Planner/DAG、摘要或最终回复反推目标；修改历史 run_started.goal |
| 输入属于哪个工作 | 现有 ACP 输入/恢复解析与绑定边界 | 用短词表或 UI 当前选中项擅自创建/恢复 run |
| 授权与审批 | Authorization/Execution Policy，消费真实审批选择与有效范围 | 把 ask_user 回答、工具成功、角色或模型计划视为权限 |
| 能否派发动作 | 现有执行准入边界，消费最新已提交合同、权限与运行状态 | 只检查本地 token 就忽略 Paused/Cancelled 或已失效合同 |
| 工具结果与副作用 | 工具执行器、ToolAudit 及既有 evidence 归一化边界 | 无回执推定失败/无副作用；成功请求推定文件确有净改动 |
| 完成资格 | Main Agent 提案；现有 Convergence 核对引用、归属与硬条件 | 单个成功工具或最低门槛代替全部要求；复制整包证据视为逐项覆盖 |
| 状态转换 | Reducer，经 RunEngine 原子提交 | 兼容状态、todo、报告或 UI 单独写 Completed/恢复 |
| 展示 | ACP/消息适配与 UI 单向消费不同来源的事实 | 合并时补造生命周期、把公开进度转文件变更、隐藏未决审批/失败 |

冻结不变量：

- **I1** 当前要求必须可追溯至真实用户输入；宿主注入的复核、压缩摘要和工具结果不是新授权。
- **I2** 暂停/取消提交后，不再准入新的普通业务动作；已在途动作单独收尾，结果未知不盲目重放。
- **I3** 每个实际调用最多接受一个权威终结结果；协议重复不重复计数，不以 first-wins 掩盖重复生产源。
- **I4** 本任务允许只在获批范围和生命周期内复用；子权限不超过“当前父权限 ∩ 委托范围”。
- **I5** 证据必须匹配当前要求、目标资源与适用版本；工具成功、记忆写入、独立 demo 通过不自动证明原开发目标完成。
- **I6** CompleteRun 被拒绝必须给出真实 gap；无变化的 gap 不能触发无界复核或重复测试。
- **I7** 用户委托完成、项目健康、回合结束、压缩完成、进程停止是不同事实。
- **I8** 展示来自真实生产链；实时、历史与委派使用一致的身份和来源规则，但不强制变成同一种事件。

## 4. 开工前基线与必要快照（S0）

用户批准后，先做可恢复性准备，不先跑长 E2E。

1. 记录 Git 分支/HEAD、已有 diff、未跟踪源码清单及相关文件哈希，并保存相关未跟踪源码的实际内容，区分既有改动和本批增量；清单和哈希本身不能恢复文件。只归档相关源码，不打包凭据、整个用户目录或全部缓存。此快照不是提交，也不覆盖原文件。
2. 保存实际后端 SHA-256、前端产物/构建来源、启动命令和 profile 路径；无法追溯的历史产物明确标 unknown，不用日期推断同一构建。
3. 固定已有原始证据及哈希；保护 session DB、账本、Evidence artifact。需要 DB 副本时用一致性备份方式，不把运行中的单个数据库文件复制称为完整快照。
4. 确认当前修改者，按文件和状态链分工；一个共享边界只有一个写者。保留既有 dirty 工作，不清理、不重置。
5. 将 EDU 的“Paused cannot install a plan”定位到准确入口与状态序列；补查恢复绑定分支失效原因。现有证据足够的路径不重复采集。
6. 检查 README、涉及组件 AGENTS 和已有测试入口。已知编译/测试失败记录精确命令与诊断，不把旧报告当作当前基线；不为建基线全量跑测试。

产出：轻量 baseline manifest、相关补丁/文件快照索引、现象到调用链映射。无关文件和本地 profile 不加入提交。

## 5. 实施切片及出门条件

S1/S2/S3 为产品放行必需的 P0 链，顺序不表示后面的安全问题可以延期放行；S4 为本批必交的体验修复。每个切片先看完整入口和退出分支，再写最小机制修复与核心回归。不得因本地 helper 通过就提前宣布闭环。

**实施依赖不等于四座串行大工程。** 先闭合 S1 的准入/合法退出和 S2 最小的当前目标/完成真实性，再结合 S3 的受控执行与审批，尽早打通一次真实的“探查 → 修改 → 测试失败 → 观察 → 修复 → 复验”。它是首个联合里程碑，不必等通用需求抽象全部做完，也不得为了演示闭环放宽暂停、权限或完成门槛。随后补齐修订、重启、委派和展示路径；全部门禁通过后才进入集中 candidate 构建。

### S1：运行状态真正约束执行，同时交付合法受阻退出

**范围：** Main Agent 工具循环、委派返回、执行准入、现有暂停/取消/收口路径。

- 将最新权威状态与有效合同校验接到实际动作准入点；检查与准入要与状态更新有明确的顺序约束，仅每轮轮询一次不能解决并发竞态。
- 暂停后不再发起新业务写入/委派。已有调用根据结果完成审计；宿主必要的取消确认、结果采集和只读对账走明确收尾路径，不借其继续开发。
- 分开记录取消已请求、执行是否停止、效果是否已知。无法证明停止或结果时保留未决信息并阻止冲突重放，不承诺系统做不到的强杀或 exactly-once。
- 委派注册在 Paused 状态失败属于宿主状态冲突，不提示用户“补权限”；返回具体 run/task/blocker 与可行下一步。
- 完成拒绝返回非空、可追踪 gap；限制的是同一缺口无有效变化时反复提交相同完成提案/全目标复核，不是禁止模型基于已有回执发现新问题或提出新的合法行动。没有可推进的合法动作时正确暂停或等待，不再注入几十轮相同复核。
- 重复判定关注当前要求、缺口及其相关资源效果、验证、授权或子任务结果的有效变化；重复读取产生新的 audit ID、工具次数增加，不自动视为进展。原始调用仍完整留存，不为去重删审计，也不只用工作区哈希判断所有任务。
- 普通 action 的可恢复失败只影响该 action，不连坐取消无关只读调用；有新证据可换合理方案，但不得通过换工具绕权限。

**出门条件：** 复现 EDU 的暂停时序后无新业务写；在途/未知结果保留调用与任务身份、阻止冲突重放，不被误报为无副作用；拒绝完成不会变成无限 Running；正常可恢复工具错误仍允许模型继续。完整委派 outcome 与副作用对账在 S3 验收，不能在这里提前报通过。使用现有 Paused/阻塞事实表达，不为文案新增一个核心状态。

### S2：当前目标、输入恢复与完成证据贯通

**范围：** ACP 输入绑定、requirement revision、恢复上下文、现有完成提案/Convergence。

当前 `UserRequirement` 只有 ID、来源消息与执行义务，已有 revision 提交机制但缺少上述语义关联。S2 依赖第 9.1 节一并送审的最小合同扩展；不是承诺现有字段已经足够，也不以最终报告补洞。

- 新输入区分继续、补充、替换、撤回、回答当前问题；由现有语义解析 owner 提案，宿主绑定 source message、原 run/current requirement、选项身份及版本。只读探查和普通工具调整不需每次重新生成完整计划。
- “继续”先定位未完成工作并对账，满足恢复条件后才由 Reducer 恢复；有必要创建新 run 时必须显式链接来源与仍有效的要求，不能只注册字面“继续”。
- A→B 保留历史 goal，提交有效要求的修订/替代关系；撤销委派只撤销相关义务，不顺带撤销原集成目标。数字答复绑定尚有效的问题与选项，失效问题不能误配。
- 旧 checkpoint 或待答问题不能吞掉无关的新问题。输入绑定到当前 run、旧工作的续跑还是独立请求，由同一个输入解释/绑定边界处理；既不强行恢复，也不把每次输入都建成新 run。跨轮/重启的有效问题和答案关联见第 9.1 节，不用临时内存 ID 假装持久绑定。
- 用户贴回启动/测试报错时，输入 owner 结合当前上下文区分“只解释”与“继续修复原交付”，绑定相关项目、产物版本和原交付要求。覆盖 analysis 与 Change 入口之间的交接，不能把一次只读分流等同于抹掉原工作。已终结 run 不强行复活，可建立有来源关系的新 run；仍有效的授权策略按现行规则适用，已随旧 run 终结的 task grant 不自动继承。纯解释请求不擅自改代码，修复请求不困在只解释路径。
- 压缩从当前合同、权限、已知结果与未知副作用装配必要上下文；摘要不生成授权、不覆盖 revision，压缩成功不代表恢复通过。
- 完成覆盖提案对应具体要求与 EvidenceRef。宿主验证真实存在、来源、资源对象、run/task 及版本适用性、确定性执行义务；不能自动把整包 refs 复制成每条要求都已证明。
- 跨 run 的证据复用必须有显式继承与适用性关系；同 run 的旧测试也可能因文件已变而失效，不能仅按归属或最后一次成功选取。
- 语义覆盖仍由模型提出且可审查；确定性 host 不“理解并证明所有业务”。无法建立关键覆盖时不批准完成，说明具体缺口，不要求模型输出 Satisfied 就生效。
- 取消默认终稿触发的重复全目标 generic completion review，改为一次当前要求的语义覆盖提案及宿主硬条件核验；拒绝反馈只说明具体缺口。风险策略、用户要求或证据冲突触发的必要独立审查保留。此删减与覆盖关联一并实现，不能只删 review 就绕过完成资格。
- 执行义务从 owner 提交的已解析要求产生，不继续增加自然语言动词表。指定命令、cwd、观察退出码或要求成功的差别进入真实注册入口，不只存在于测试夹具。
- 核对 ToolResponse → 持久化/摘要 → 上下文装配 → 下一次 provider 请求的实际输入：调用身份、cwd、退出码、错误原因等语义不得丢失；截断时有标识及可取回原文的引用。允许适配成模型可读形式，不强求字段原样呈现，也不新建 observation store。导出后 agentVisible 或一份结构化回执的存在，均不能独自证明当次模型确实看见了它。
- 项目记忆对“保存记忆”任务可有效，对“开发系统”不能冒充实现；N01 无需写入，N03 非零退出码可完成诊断；独立候补 demo 不能替代现有系统集成。
- **产物已写、验证未执行的交付：** 仅要求生成代码或明确禁止运行时，可按该委托交付并标明未验证；要求可运行或修复成功时，缺少证明相应要求的真实运行证据，不能把这些要求记为满足。可以交付已完成部分、列出拒绝/缺依赖等实际缺口，并通过既有暂停/受阻路径收口，不另增 Partial 状态，不无限复核。只有用户有效修订才能撤回其验证要求；模型不得因执行受阻而自行缩减目标/删义务。此规则由当前要求关系驱动，不按“可运行”等字面词新增判定表，也不强制所有代码生成任务运行测试。

**出门条件：** EDU 继续/撤回/选项答复有结构化继承；X01 目标切换不串证据；不匹配对象与过期验证被拒；真实记忆任务、N01、N03 正常完成；拒绝路径同时满足 S1 的合法退出条件。

### S3：正常开发能力、审批、委派与 outcome 收口

**范围：** 现有工具/执行合同、Authorization Policy、审批响应、Delegate 权限与结果接收。

- 将环境探查、项目本地执行、验证证据分类、依赖安装/网络与外部副作用分清；不能由“是不是允许的测试字符串”承担整个开发执行能力判断。
- 优先复用现有受控执行器与审批合同：规范化 executable/argv/cwd，确定资源范围和宿主策略；不因命令叫 test 就断言只读，也不因为是 python 就一律失去正常环境探查能力。
- 验证分类器不支持的命令，不自动获得执行权限，也不因此自动禁止通用执行。复合命令由现有通用执行策略与执行能力判断；不能只因出现 `&&` 就长期一律拒绝，也不能拆出允许的子命令便声称整条命令安全。对本批不能可靠处理的语法，返回具体能力限制和可行替代，单次拒绝不连坐。暂不承诺任意 shell 语法支持；若需要新增解析器或扩大执行权限，按第 11 节送审。
- 不能用普通测试代替进程隔离；脚本可有任意行为。策略或现有隔离能力不足时明确能力缺口，不能扩大允许范围；需要新权限类别/边界时先提修订审批。
- 关键环境前提在大量实现前验证；探查受阻时说明真实结果并由模型调整路线，必要业务选择才问用户。缺依赖不自动安装、不虚报可启动。
- 资源授权不因 staged、恢复、改用主 Agent 或任务拆分丢失。“本任务允许”复用的是获批范围，不是每个文件重问，也不是一次文件授权变全目录授权。
- 获批资源范围内的普通创建包括新文件及必要的多级新目录。审批身份与执行路径守卫应使用一致的安全路径解释，覆盖不存在的后缀、路径别名、`..`、符号链接及 Windows junction 等跳转；仅直接父目录不存在不应再要求用户批准相同范围。执行前仍核对实际目标，不能只做字符串前缀校验或依赖事后删除来保证边界；无法安全解析时报告具体限制，不假装授权不足。重启后继续创建同样验收。
- 审批检查真实 option_id、session/run/task/resource 绑定和有效期。当前已确认的实现仅为精确文件的进程内批准缓存；多文件任务范围批准及重启恢复依赖第 9.2 节的有限合同扩展，不再写成现成功能。续跑仅复用仍有效的批准，撤销/切换对象按该节失效规则处理。
- ask_user 只收集缺失需求或有意义的用户取舍，不代办权限审批，不要求用户选择 shell/修宿主/write_scope。执行批准走正式审批，回答自身不修改 CapabilitySet。
- 子权限严格受父当前权限和委托范围约束；只读子任务不写，主 Agent 保留实现责任的要求有效时不能由可写子任务代替。
- 区分未注册、已注册未启动、执行中、结果到达、超时/取消未对账。父任务接收唯一 outcome 并关联子任务证据，未结束子任务成为带 ID 的 blocker，不能只报空 gap。
- 超时不是回滚证明。找实际重复 response 的生产源；边界去重保护审计和失败统计，operation identity 忽略 timeout/trace/request ID，但保留有语义的 argv 大小写。
- 项目需要启动验证时，复用现有执行器的进程追踪：关联本任务启动的实例，观察就绪/失败，验证后按合同保留或停止；不碰无关服务。结构化 executable/argv/cwd 只改善解析，不等于沙箱隔离或可靠停止。需要新的核心进程管理机制时停下送审，不默认建设新 ProcessManager。

**出门条件：** M02 范围内连续修改验证；选择本任务允许后同范围同任务不重复审批；D01 只读审查+主 Agent 实现可收口；越界和委派扩权被拒；超时写入有明确对账结果；普通开发探查与启动不再误走测试专用门槛。

### S4：贯通真实开发入口的过程展示

**范围：** 工具事实/公开说明生产端 → ACP → 持久化和历史适配 → 消息列表与活动组件。不更改后端完成权威。

- 先固定一段真实 Change 输入轨迹，再同时覆盖主 Agent、实际启用的委派、实时通知与历史加载；不能只测合成的理想 ActivityEvent。
- 复用现有 request/action 身份，把普通工具消息与活动关联为一次展示；缺失身份的历史记录保留来源和未知标记，不按相似文案擅自去重。
- 分离公开阶段文字、当前进度槽、工具事实、计划清单、审批和最终交付。阶段正文讲发现与下一步；没有实际公开说明时只显示事实，不公开隐藏思考或待审核终稿。
- 阶段说明不仅要“传得过来”，也要实际产生：在新发现、方案调整或阶段结果等有意义节点，由 Main Agent 输出简短公开说明，经真实 provider → ACP → UI 显示并保留到历史。宿主不以工具名拼接业务结论，不强制每 N 次调用播报。连续工具执行与长命令期间，即使没有新的模型说明，也显示真实动作及运行/等待状态；没有底层依据就不编造百分比或“深入分析”。
- 不机械每 N 次调用总结，不新建总结 Agent；现有模型输出/宿主消息边界若缺公开阶段标识，先比较内部适配与兼容扩展，再按第 9 节决定。
- 普通操作用紧凑无边框行，文件/命令可识别，详情可展开。按工作上下文与公开说明分段；活动区限高滚动，全部记录可访问，键盘可操作，焦点和展开状态稳定。
- 执行中当前操作可见；用户上滚查看时不强制抢回底部。长命令合理截断并能查看全文；百条活动不能撑满整个对话或丢记录。
- 失败、待审批、阻塞保持可见；审批处理后折叠成选择/范围记录。重复失败次数仍可辨，不能折叠成“完成”。
- 编辑证据区仅列真实确认的文件效果；纯编码阶段进度不得增加编辑计数；真实 diff 才展示 +/- 与审查内容，未知改动不显示伪撤销。
- todo 标为“模型计划”，不作为权威任务完成。公开总结与现有报告区协调，最后列交付物、实际验证/退出码、限制和启动方式，避免反复展示大段复核。

**源码/自动验证出门条件：** 真实 Change 消息轨迹与重载回放都到达轻量展示；同动作无双份卡片；公开文字未被吞掉且无私有思考泄漏；运行/失败/审批/编辑各有准确语义。包括已有真实 provider 轨迹的阶段文本回放及长命令状态链检查，不能只有手工拼造的 UI 事件。此门槛允许进入集中 candidate 构建，不证明候选模型必然主动汇报。

**产品验收条件：** candidate 启动后，在实际窗口检查阶段说明、折叠、限高滚动、异常显露与修改证据。使用真实模型产生的一段连续工具操作与一个长命令场景，核对有意义节点实际出现公开说明、运行中能辨认在做什么/等待什么；不能仅证明“如果发了就能显示”。此项由后续人工 E2E 完成；未做视觉验收不阻止准备 candidate，也不能因此将 S4 宣称产品通过。类型检查和组件测试不能替代该项。

## 6. 方案选择：采用和拒绝

| 问题 | 不采用 | 本批选择及代价 |
| --- | --- | --- |
| 状态脱节 | 每轮加一个本地 if 或再建状态机 | 现有准入与权威提交有序衔接；需验证并发/在途路径，不能只改循环开头 |
| 假完成 | 禁用记忆工具、所有任务强制写文件/测试绿 | 当前要求与实际效果关联；承认语义判断仍有局限，保留模型提案和可审查证据 |
| 恢复失联 | 识别“继续”等固定短语后换 UUID/直接启动 | 输入 owner 绑定当前工作和修订，对账后恢复；历史信息不足时明确缺口 |
| 开发命令受阻 | 不断扩字符串白名单，或放开任意 shell | 复用现有权限/执行边界，区分执行能力和验证分类；隔离不足不虚报安全 |
| 授权太碎 | 删除审批、ask_user 充当授权器 | 有边界的任务级批准与正确复用；越界、外部副作用仍正式审批 |
| UI 无变化 | 只调 CSS、直接开放 analysis tracker | 真回执入口、统一身份适配和来源分层；需要端到端数据与实际窗口验证 |

成熟框架的公开对照依据沿用审查报告第 7 节：借鉴工具 observation、消息/审批/状态分层和显式恢复，不照搬 done/FINISHED 业务语义，不推测 Codex 桌面私有实现。

## 7. 必须保护的验收矩阵

测试断言来自用户目标和真实故障，不照抄实现。以下是行为义务，不要求一行一个测试；可以用少量贯穿测试覆盖多个断言。

| 场景 | 必须成立 | 必须拒绝/区分 |
| --- | --- | --- |
| N01：测试原本全过 | 指定调用真实执行、零改动可完成 | 为凑证据写文件；只看“pass”文案猜退出码 |
| N03：配置错误、仅准改实现 | 诊断可完成，项目仍失败，零写入 | 强迫修配置、把项目健康记为通过 |
| M02：明确一文件修复 | 基线失败→授权内修复→指定复验→当前效果覆盖 | 丢授权、同范围重复审批、写后失败仍宣称修复完成 |
| D01：只读审查+主 Agent 实现 | 子任务真实启动、只读证据、主实现、唯一 outcome | 超时子任务代写、父无权限子却可写、空 blocker |
| X01：开发目标/切换/记忆/压缩 | 有效要求修订可追溯；恢复取权威事实 | 仅记忆写入/空目录 Completed；旧目标证据覆盖新目标 |
| 真实记忆任务 | 记忆效果确实完成相应委托 | 因全局禁记忆完成而错误受阻 |
| EDU 集成对象不在工作区 | 明确定位差异；保持集成目标，合法受阻或获准切换 | 独立 demo 自测通过冒充集成；复制项目视为默认授权 |
| EDU 暂停、继续、撤销委派、选项答复 | 不再新派发；当前合同绑定；撤回仅影响对应义务 | Paused 下仍写；数字成为新目标；旧批准被套给新对象 |
| 取消/崩溃/超时竞态 | 在途结果可对账；未知不重放；取消原因保留来源 | 把取消当失败，把 token 或 timeout 当停止/无副作用证明 |
| 完成拒绝 | 非空具体 gap，变化后可推进，无变化不复核循环 | 用“还有 Running”加空数组反复要求模型继续 |
| 工具隔离与身份 | 在策略确实拒绝某个 action 的反例中仅该 action 被拒、同轮 read 继续；重复回执计一次；验证分类和执行准入分别检查 | compound 一律拒绝当作产品目标；验证分类失败就禁止通用执行；timeout 改变就绕重复识别；argv 大小写被不当合并 |
| 证据适用性 | 资源、要求、实际版本匹配；缓存/跳过明确标识 | 另目录/旧版本测试、脚本 exit 非零、SKIPPED 当 PASS |
| UI 真入口 | Change/委派/live/reload 一致；公开说明与原回执可见 | 只有 analysis 可折叠；纯进度当编辑；隐藏审批/阻塞 |
| UI 长会话 | 百条活动限高可滚动、详情完整、失败突出、定位稳定 | 截掉证据、重复展示、强制滚到底或伪造阶段总结 |
| 低负担澄清/明确小任务对照 | 模糊交付仅澄清关键形态与范围，选项易懂有推荐；明确小任务直接推进；真实必要的自由输入可用 | 强制问卷、重复问已知信息、把内部故障交给用户填空；把推荐或问答当授权 |
| 一次/任务范围/重启审批对照 | 一次只批准绑定调用；展示并批准的多文件任务范围可连续使用，同 run 重启后经对账恢复 | 精确文件批准扩成全目录；拒绝/撤销/过期被恢复；旧缓存伪装持久批准 |
| 旧 checkpoint + 新的独立问题 | 新问题被正确处理，旧工作不会因此被误恢复或删除；有效晚答有明确绑定 | 旧 checkpoint 吞新输入、晚答误套新问题、单个数字成为新开发目标 |
| 下一次模型输入 | 新鲜工具结果的关键语义可见，截断可识别可取回；压缩后事实仍准确 | 根据导出标记猜可见性、成功退出码只存在宿主中、重复读制造进展 |
| 正常开发正例及静态审查反例 | 隔离项目真实探查→实现→运行测试→根据失败修复→复验；需要时启动、观察并停止自己的服务 | 只生成测试不执行，静态反复核对代替真实验证，跳过/缓存当新鲜通过 |
| 空项目创建与路径边界 | 一次批准明确多文件范围后创建多级新目录和文件；等价路径身份一致；同 run 重启后继续创建 | 父目录不存在就丢授权；`..` 或链接/junction 跳出范围；重复审批代替安全解析 |
| 写完但运行被拒/不可用 | 代码生成委托可如实完成并标未验证；可运行/修复成功委托保留缺口、交付已做部分并正确受阻 | 无验证比验证失败更容易 Completed；模型自行删验收义务；永久复核 |
| 原交付报错反馈/只求解释对照 | 贴启动错误后正确绑定原项目/产物与上下文；修复请求能读改测并收口，解释请求只解释；终态后新 run 有来源关联 | analysis 分流丢合同；强行复活终态；纯报错一律自动获得写入权；旧 task grant 跨 run 复用 |
| 用户离开、非关键问题未答 | 有可逆默认时不发非必要阻塞提问；未答后推进不依赖答案的合法工作，无工作才等待；真实等待时序可核对 | 超时当批准/已选推荐；重复问同一问题；同步等待存在却宣称后台仍在工作 |
| 连续工具与长命令的可理解性 | 新发现/变更方案/阶段结果有实际公开说明；无新说明时显示真实动作与等待；live/reload 一致 | 只有一串操作却称阶段汇报完成；猜测“深入分析”；将 UI 模拟数据当实际模型输出 |

至少有一组自动化贯穿 **ACP 输入绑定 → requirement/权限事实 → 实际工具回执 → Evidence → Convergence → Reducer → Projection**；另有实际 ACP 消息进入 UI 的实时/重载回放检查。不能只有各组件的局部 mock。

测试文件/目标名称在 S0 映射到现有套件后登记，不预先杜撰不存在的测试入口。隔离 fixture 不调用真实用户项目的写数据库脚本。

**联合里程碑的最小证据包：** 一个隔离开发正例、一组暂停/受阻反例和 N01/N03/记忆三种不同完成语义；随后增加目标切换、审批重启、委派超时及真实 UI 轨迹。可以复用同一条轨迹覆盖多个断言，不强制新增大量长 E2E。对照审查报告中的历史 S2 教务产物（不是本计划的 S2 切片）存在 seed/test 归属矛盾，可作真实执行反馈的补充夹具；目前仅静态确认，不标成已执行失败，也不升格成新增架构 P0。

**体验验收单独记录：** 用户能否说清当前在做什么、为何需要自己回答、已批准的范围、最后改了哪些文件及哪些验证未做。用同一 candidate 检查普通主路径、失败恢复与历史重载；不要求相同文案或像素复刻，不以总工具数/子 Agent 数评优。审批范围内无新风险或失效时不重复询问；单纯新 audit ID 不重置复核抑制。自然语言澄清与阶段说明最终由人工 E2E 验收，不能只靠 mock 宣称体验通过。

## 8. 验证节奏、构建及 E2E 交接

1. 开发中 Rust 修改后 `cargo fmt`，使用必要 `cargo check -p goose --lib` 等受影响最小检查；前端用现有 typecheck/lint 入口。不开多份 Rust 编译，不与桌面构建争抢产物。
2. 各切片核心回归准备齐后集中运行相关目标；失败修复仅重跑受影响项。集成后跑跨层相关门禁和适用的 Clippy，不默认全仓测试。
3. 命令以根 README 与组件规则为准：根目录 Cargo package/target/filter；`ui/desktop` 下 `corepack pnpm run typecheck`、`test:run` 的相关文件过滤、`lint:check` 的适用范围。执行前确认脚本参数支持，不发明入口或改变构建环境。
4. 每次验证记录 cwd、源码 manifest、完整命令、退出码、通过/失败/跳过数量。历史失败只在有当前基线证据时标为既有；本批引入的失败是交付阻塞，不静默排除。
5. 自动验证完成且独立审查无未解决 P0/P1 后，集中构建一个 candidate。按 README 的 `ui/desktop` → `node ./scripts/prepare-platform-binaries.js` → `corepack pnpm run start-gui` 入口及现有条件构建。先检查已有依赖与产物；出现未授权下载/安装则停止相关步骤报告，不自行补环境。
6. 此交付是源码桌面 candidate，不是安装包/发布。脚本所需后端构建不能称打包；纯前端迭代不无故重建后端。第一次集中构建失败可以修正本批问题后重建，不能为“一次”口号保留失败产物；重建后重新标识 candidate。
7. 使用既有 worktree 和干净 fixture 副本。candidate 独立 `CODEBUDDY_HOME` / `CODEBUDDY_USER_DATA_DIR` 的用法先核对现有启动支持；不借隔离切 profile/features/target，不用默认旧 profile 冒充本批验收。
8. 用户指定自己 E2E：交接启动窗口、后端哈希、前端构建来源、fixture/seed 哈希、提示词、数据根和导出位置后停在 **E2E_READY / PRODUCT_E2E_NOT_RUN**。未另获授权不代用户执行长 E2E。
9. 人工顺序：N01 → N03 → 干净 M02 → D01 → X01/EDU 互补续跑与受阻场景 → 一段正常开发和展示。前置核心失败先记录停止相关放行，不在污染 fixture 上继续凑成功。

E2E 同时看真实文件、ToolAudit、账本/Projection 和窗口，不仅看回复。必须有一次重载/重启后的恢复与展示检查。性能只设防回归指标：重复请求、重复审批、重复复核和等待来源可解释；不规定比 WorkBuddy 少几次调用，不把人工吃饭等待计作执行耗时。

## 9. 兼容、迁移与回退

- 先复用既有结构。若需要增添字段，列明 producer、唯一 writer、消费者、持久化位置、旧记录默认语义和失效规则；内部适配优先于公共协议变更。
- 第 9.1、9.2 节是本次明确提出、等待用户一并批准的已知合同扩展。批准本计划不等于批准该清单之外尚未定义的协议/持久化语义变化；超出时先提交差异和兼容方案。若现有合同已能承载，只做实现修复，不重复审批。
- 旧记录缺 run/action/revision/退出码时标未知，不从文案补造权威事实。历史 UI 允许降级但应能查看原记录；旧未知授权不得静默提升，新已知授权也不得因无关展示字段缺失全部作废。
- 旧 Paused run 无 checkpoint 时不凭聊天摘要强行恢复；依据现有权威事实对账，能安全恢复则明确提交，不能则说明具体不可恢复边界及用户可选择的后续工作。
- 不原地重写历史账本或批量迁移用户会话。本批主要在隔离 candidate 数据验证；回退使用已记录源码/产物和相应数据备份，不让旧二进制继续消费不兼容的新 profile。
- 回退产品不自动撤销已发生的文件/外部效果；这些效果必须列明并单独处理。不得用覆盖整个 dirty 工作树作为回退。

### 9.1 一并送审：当前要求与证据覆盖的最小合同扩展

**必要性已由源码确认：** `protocol/events.rs` 的 `UserRequirement` 目前只有 `requirement_id`、`source_message_id`、`execution_obligations`；`CommitUserRequirements`/Reducer 已支持递增 revision。`CompletionProposal::for_main_agent` 仍把一组 refs 复制给全部 requirement。因此本批不能只改提示词而承诺目标修订和逐项覆盖。

比较三种做法：继续根级 run-goal 自动覆盖无法修复 EDU/X01；新建 requirement 服务或通用需求状态机超出范围；**选择在既有 requirement 提交、事件/Projection 与覆盖提案中补齐以下关系**，继续使用同一存储和 Reducer。

| 合同增量 | 来源、提交与消费 | 兼容/失效边界 |
| --- | --- | --- |
| 当前要求的可审查内容与明确目标对象引用 | 模型提交最小语义候选，宿主绑定真实消息；对象引用与实际工作区/资源核对后提交，Main Agent/Convergence 消费 | 不拆每句话、不预枚举全部实现；尚未定位对象可继续已授权探查，但不能声称对象交付完成 |
| 要求修订间的保留、替代、撤回关系 | 复用递增 revision 的提交入口，引用旧 requirement 与来源输入；Reducer 提交，恢复/完成消费 | 保留历史 goal 和事件；未被撤回的原要求继续有效；不以删除清单条目默默撤销 |
| 跨 run 延续的来源合同引用（仅确需新 run 时） | ACP 绑定既有 run/revision，宿主校验后提交；上下文/证据使用方消费 | 优先恢复原 run；不自动继承权限，不自动让旧 evidence 对新对象有效 |
| 待答需求问题及答复绑定 | 复用现有用户输入/恢复合同，宿主绑定 question ID、来源 run/task/requirement revision、选项身份和解决/失效事实，经现有事件提交链保存；输入绑定和上下文消费 | 问答不是授权；超时不伪造回答；重启后只接收仍有效问题的晚答。目标替换或问题失效后不得套用；不另建 pending store |
| 完成提案绑定当前 requirement revision，逐项关联既有 EvidenceRef 与适用资源版本 | 模型只提关系；宿主从真实审计/evidence 取调用、退出码、对象和版本核验，Convergence 判硬门槛，Reducer 提交终态 | 不接受模型 Satisfied 作权威；不新增 evidence store；改变实现或要求后重新核对适用性 |

具体字段名、复用引用类型与序列化版本由实现者比较后决定，但不得超出这五类关系。事件写入仍经过现有提交链，Projection 仍只重建；没有新的 registry 数据库、核心生命周期枚举或权限授予入口。权限关系单独由第 9.2 节定义，不塞进 UserRequirement 或问答结果。

迁移采用显式可识别的合同版本/能力边界：新版可读取缺新增关系的旧记录，缺失标为未知；历史终态保持历史，不重判成“已验证”。若要恢复旧未完成任务，先依现有原始输入与事实建立可审查的当前合同；不能由摘要补造，也不能把内部缺字段伪装成用户业务歧义。旧客户端/旧后端能否读取新版不能仅凭“字段可选”保证（当前存在 deny_unknown_fields），所以仅在隔离 candidate profile 写入新版，不让旧程序打开该 profile，回退用配套备份。实现前记录确切的读写版本组合及兼容测试。

**批准边界：** 用户批准本计划即批准上述有限关系扩展及隔离兼容策略，不批准新状态机、新存储、权限扩张或改事实 owner。若实际实现仍需这些额外变化，按第 11 节再次提出修订；不得以本节为泛化重构授权。

### 9.2 一并送审：任务范围审批与恢复的最小授权合同

**必要性：** 当前 `PermissionManager` 从持久配置加载后，任务范围缓存仍初始化为空；`permission_inspector` 的写入批准按规范化文件身份缓存。它不能证明“本任务多文件一次允许”或重启后的批准恢复。R1 的验收高于其已定义合同，R2 在此补齐，不暗中降为“只在同一进程同一文件有效”。

**比较：** 放开工具级 AlwaysAllow 会扩大权限，拒绝；仅保留精确文件内存缓存达不到产品目标；选择在现有 Authorization Policy 与控制面事件/Projection 中记录有限的审批事实，缓存仅为可重建加速视图。不新增权限数据库，不改变权限 owner，不把 Requirement/TaskContract 当授权器。

| 关系 | 唯一来源/提交/消费 | 边界 |
| --- | --- | --- |
| 批准来源 | 正式权限卡的 request/option ID、实际用户选择，或当前宿主已生效且可追溯的授权策略；Authorization Policy 校验，现有 Reducer/RunEngine 提交 | ask_user、模型候选、自主标签、推荐选项均不能直接产生批准；既有策略已允许则不额外索要一次重复批准 |
| 获批资源与动作 | 明示的工作区、规范化资源范围、操作种类、排除项；工具边界消费同一事实 | 单文件卡不能暗授目录。多文件任务需在审批时明确展示实际范围，不自动新增任意 shell、网络、安装、Git 或外部副作用权限；范围内 read/edit/write 的合法复用不依赖展示别名 |
| 身份与寿命 | 绑定原 session/run 的任务授权及 authorization revision；子任务引用后取父当前权限与委托范围的交集 | AllowOnce 仅绑定具体调用，不因失败/超时变成无限重试许可；本任务允许不因 staged、压缩、工具切换或实现任务拆分丢失，但仍受有效范围约束 |
| 恢复与失效 | 同一未终结 run 恢复时，从权威事件重建并核对当前策略、工作区身份、撤回及在途结果；Projection/执行准入消费 | 暂停保留批准记录但不准入普通动作；终结/撤销/到期不再复用。换项目/新 run 不自动继承；同 run 调整需求不扩大范围，原范围可继续使用，已撤回部分不可恢复 |

策略允许与用户批准必须保留不同来源：策略决定仅沿用其原有 scope 和寿命，不因为被记录就变成持久用户任务批准；一次动作的策略允许不得升级为 task grant，重启恢复时重新核对当前策略。用户任务批准也不能覆盖更严格的现行系统策略。

旧记录只有 `user_confirmed`、文本“允许”或内存缓存时，不补造 durable grant。无法恢复批准时明确解释缺失并通过正式审批确认，不告诉用户去修宿主。审批记录格式不兼容或损坏时，只阻断依赖该记录的授权动作；在运行状态允许时仍可完成安全只读工作。

获批的创建范围可以包含尚不存在的文件和目录；不能把“先有直接父目录”当授权必要条件。路径身份的安全解析和执行时复核沿用唯一工具/权限边界，不在审批与实际写入处各造一套有不同规则的路径判断。链接或目录在批准后变化不得把原批准转移给越界目标。

实现前登记 producer、唯一 writer、持久化事件、缓存重建与失效路径；审批 UI 若当前只展示单文件，必须同步展示真实任务范围和对应 option 语义，不能只改后端缓存。沿用第 9.1 节的隔离数据、版本兼容与配套回退；不得把授权副本分别存入要求、计划、权限配置并各自判定。

**批准边界：** 仅允许上述既有权威链内的审批来源、范围、寿命和恢复关系扩展，及对应审批内容修正；不批准更宽的实际资源权限或新授权 owner。若现有平台无法执行这个范围，报告能力缺口，不以事后文件检查代替执行前限制。

## 10. 协作、记录与交付

实行“实现者 + 独立审查者”：共享同一原始证据，实现者负责代码，审查者只读核查事实边界、反例与验收；主执行者汇总异议，用户审定冻结范围。普通反馈在切片边界汇总，不互相抢同一文件，不反复让用户转述。

阶段记录单独追加，不修改冻结内容假装原计划就包含新工作。每个切片交付：

- 根因/需求证据、真实调用链、事实 owner；采用/拒绝方案及兼容边界。
- 实际变更文件与完整 diff、本批与既有 dirty 的边界；新增与复用类型及必要性。
- I1–I8 不变量的实现位置、对应回归和结果；未验证路径、基线失败、阻塞。
- 实际命令、退出码、数量和源码身份；不得以测试数量替代业务覆盖。

最终 candidate 交接另附：后端 SHA-256、前端来源、精确启动方式、隔离数据根、fixture/seed、自然提示词、session/run/诊断导出位置、如何识别旧 profile、关闭与回退方式。旧 baseline 非必需，不为对照再新建代码 worktree。

状态分别报告：**源码已实现 / 自动验证结果 / 构建结果 / E2E-ready / 产品 E2E 结果**。产品 E2E 未执行、失败或部分通过都必须直说。源码/组件通过不替代用户可用性验收。

## 11. 停止条件与变更控制

遇到以下情形停止相关切片并提出选择，其他安全且独立的已批准工作可以继续：

1. 必须新增核心状态机/存储、改变冻结事实 owner，或超出已批准第 9.1、9.2 节的持久化/公共协议语义。
2. 必须扩大 shell、文件、网络权限或安装依赖；需接触生产/重要数据。
3. 直接证据与计划根因冲突；当前实现者与已有修改发生不可安全绕开的重叠。
4. 目标项目无法确定，用户输入确有会改变交付结果的业务歧义；不得用内部协议错误冒充这种歧义。
5. 现有执行器无法保证准入或在途收口，必须改变隔离/进程管理机制；不能用提示词代替安全事实。

普通实现选择、修本批回归、必要格式化与相关检查不要求逐项确认。同一失败没有新证据时停止机械重试，不扩测、不无限提高预算。P2 外观细节和无关架构债登记待办，不混入本批。
