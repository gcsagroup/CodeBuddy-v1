## 3. 方案比較與建議

| 方案 | 效益 | 代價與判斷 |
|---|---|---|
| 自訂 Harness profile + Host 相容外掛 + 獨立能力服務 | 保持既有介面契約，重用上游核心，重用現有成熟能力 | 需開發協定／狀態介接；建議採用 |
| 直接將後端換成 dsh ACP 或現成 SDK 程序 | 最快接通一般對話 | 完整控制、即時呈現和產品擴充存在缺口；不符合目前範圍 |
| 在 Harness 上重寫全部周邊服務 | 統一實作技術 | 重複遷移 Git、電腦控制、記憶等能力，迴歸影響範圍大；本輪不採用 |

建議使用受版本約束的外掛組合，避免長期修改上游核心。保留 Rust/Go/Swift 能力服務屬於實作重用；新任務的舊 Agent 迴圈、Planner、TaskScheduler、舊控制層及恢復執行入口必須退出執行鏈。

## 4. 目標結構與職責

```text
凍結的 CodeBuddy 介面
    ↓ 既有 ACP / goose 擴充契約
Electron 啟動與通訊橋
    ↓ 本機驗證連線
CodeBuddy Host 相容外掛
    ├─ Session Controller：歷史、即時串流、分叉、取消
    ├─ Harness agent-loop / subagent / jobs：唯一執行與排程核心
    ├─ CodeBuddy 產品策略外掛：角色設定、任務控制、權限與結果投影
    └─ 獨立能力服務：MCP、電腦控制、Git、記憶、模型／設定等
```

| 單元 | 唯一職責與邊界 |
|---|---|
| Electron 宿主 | 啟停、就緒、當機報告、連線身分驗證與封裝；不解讀使用者任務或排程 agent |
| Host 相容外掛 | 驗證既有請求，轉換事件、識別碼與錯誤；不自行執行第二套模型迴圈 |
| Harness 與產品策略外掛 | Harness 執行／子任務機制負責執行；產品策略在其擴充點實作現有角色、計畫、任務生命週期和完成條件 |
| 產品狀態 | 每項狀態僅一個寫入者；新執行事件進入 Harness 工作階段日誌，舊 UI 快照為可重建投影；不將 turn/end 等同於任務已完成 |
| 能力服務 | 完成具體工具、儲存或系統操作並回傳真實回執；不自行建立舊 Agent |
| 歷史介接器 | 讀取遷入的舊格式歷史，支援既有查詢／匯出／管理；不恢復舊檢查點或執行權限 |

自訂 codebuddy profile 經上游啟動機制組裝外掛；優先呼叫 ctx.sessionController 及已公開服務，重用跟隨串流／重新連線邏輯。避免另外複製一套 Harness 啟動器或完整 Web UI。

相容層保留既有請求欄位、能力協商、錯誤結構、訊息／工具識別碼、任務序號和權限選項。長 prompt 與控制操作保持獨立通道，避免停止／快照查詢遭到阻塞。串流增量、持久事件和最終提交分開處理，重新連線時去除重複事件；公開思考僅轉送供應商實際提供的內容。

## 5. 介面凍結方式

- 凍結範圍包括 App／路由、components、樣式、國際化資源、互動 hooks/store、訊息／任務呈現轉換及其公開型別。
- 通訊例外僅限 main/preload/gooseServe、連線傳輸實作，以及必要的建置／封裝／相依套件接線；同一檔案中的視窗、選單、快捷鍵等行為仍保持原樣。
- ACP 業務介接器與 SDK 的對外型別契約保持不變。每個例外檔案在變更清單中說明理由，不擴大為整個目錄皆可修改。
- 實作前儲存目前來源檔案清單、雜湊和 dirty 狀態；複製納入基準的原始碼、文件和未提交新檔案。排除 .git、相依套件、建置產物、快取及私人資料；已忽略但必要的原始碼／資源另行列明後納入。
- 此時凍結的是複製時的完整工作樹；原專案之後的修改透過明確的增量合併納入，不自動覆寫新版。
- 驗收同時檢查凍結檔案零差異與真實功能。零差異只是原始碼約束證據，不等於功能通過。

## 7. 資料遷移設計

1. 新版使用獨立應用程式資料根目錄、Electron userData 與憑證命名空間；P0 同時固定安裝目錄、安裝程式身分、Bundle ID、單一執行個體識別、協定／檔案關聯歸屬及更新通道。候選版本不接管舊版註冊，正式切換另列精確交接操作；可見介面文案保持不變。舊目錄始終保留，遷移操作只寫入新版。
2. 舊 SQLite 使用一致性快照或資料庫備份介面，處理 WAL/SHM；日誌／附件記錄清單、來源和校驗摘要。重複匯入具冪等性，局部失敗可重試。
3. 舊聊天、工具回執和任務歷史保留原狀態。歷史視窗續聊維持原互動，後端建立新 Harness run，關聯唯讀歷史上下文；不繼承舊檢查點、活動程序控制代碼、授權或待執行工具。
4. 既有新增／分叉入口保持不變。舊歷史刪除、重新命名等操作僅作用於新版檔案副本，不修改來源應用程式。
5. 遷移模型／MCP、技能、配方和偏好；憑證參照另外對應。系統 keyring、OAuth 與 GitHub 登入逐項處理，不在報告或日誌寫出金鑰；遷移失敗沿現有介面重新登入。
6. 專案記憶保留啟用狀態、來源、審核資訊、TTL 與專案身分；路徑變化明確對應。Hindsight 等衍生索引按本機權威記錄重建，不恢復已停用或已刪除的內容。
7. 已確認：匯入排程為暫停且待驗證，沿現有「立即執行」流程驗證。「立即執行」會真實執行，驗收使用受控任務。啟用前核對舊版同來源排程已停用，並記錄原排程 ID 與交接狀態，確保單一觸發方；結束舊應用程式本身不構成永久停用證據。遷移器不擅自修改舊排程，來源排程仍啟用或狀態未知時保持新版暫停，沿現有錯誤回饋呈現交接缺口。舊執行個體不遷移為活動任務。
8. 保留佇列恢復後暫停的現有語意；待傳送、傳送結果不明及草稿分別處理，避免重播。外部後端連線設定須驗證，避免新版意外連回舊核心。

新舊並存用於回復應用程式版本；執行中的任務不在兩個核心間熱切換。新事件不會寫回舊格式，也不要求舊版能繼續執行新版任務。

## 9. 驗收、風險與交付邊界

- 後端必須涵蓋狀態機、協定驗證、事件去重、並行控制、取消、持久化及遷移邊界；輸入使用原專案真實格式的去識別化樣本。
- 沿用前端元件測試；在真實瀏覽器／Electron 中驗證現有互動。跨模組流程涵蓋需求輸入、計畫、實際檔案變更、測試、結果呈現、停止／恢復和歷史。
- 模型驗收涵蓋現有使用方式中的雲端、自訂相容端點、本機模型及視覺路徑；使用真實設定時另記錄憑證可用性與呼叫成本，目前不讀取使用者憑證。
- 採集首個可見增量、工具耗時、取消完成、重新連線恢復、token 與費用，與原版在相同條件下比較；尚無基準時不承諾固定效能收益。
