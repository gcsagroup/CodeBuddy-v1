# SecVibe 与 CodeBuddy 代码安全审查能力技术对接需求

日期：2026-10-23｜阶段：能力确认与接入评估

## 1. 合作目标

希望复用 SecVibe 已有的代码安全审查能力，让 CodeBuddy Agent 能审查生成或修改的代码，获得问题位置、风险说明和修复建议，并在授权范围内修复、测试及复检。本次先研究如何接入已有能力，不预设 SecVibe 新建服务或重构现有系统。

**目前尚未取得正式接口文档，也未完成真实联调；接入可行性、检测覆盖及效果均待验证。**

## 2. 希望接入的能力与使用模式

核心需求是代码安全问题检测及可供 Agent 理解的审查结果。希望了解是否支持文件定位、风险分级、证据、修复建议及修复后再次检查；依赖漏洞、敏感信息泄露等检查按现有能力评估，不预设全部支持。

考虑两种模式，首版范围需双方确认：

- **主动审查**：用户要求 Agent 审查指定代码或当前改动。明确此次范围和授权，按次评估耗时及费用。
- **自动审查**：Agent 生成或修改代码后，在约定节点触发。需另确认触发频率、持续授权、响应延迟与费用预算，以及服务不可用或发现问题时的处理方式。

自动审查不等于自动修改，也不等于强制阻止任务完成。自动修复权限及是否设置完成门槛需明确约定；两种模式均未预先确定为全部交付范围或首版必做项。

## 3. 请 SecVibe 确认的现有条件

1. 安全审查能力是否支持脱离网页/人工操作独立调用？是否已有 MCP、REST/HTTP API 或 SDK？哪些属于正式支持的接口？
2. 支持哪些语言、项目类型和安全检测类别？有哪些已知覆盖限制？
3. 接收文件、代码片段、差异、项目包还是仓库引用？输入大小及运行限制是什么？
4. 返回什么格式？是否包含问题位置、风险等级、证据和建议？如何表示未完成、失败或部分检查？
5. 能否提供接口文档、脱敏输入/结果样例、测试环境、鉴权方式及技术联系人？
6. 请说明现有部署和网络条件、典型耗时、并发/配额/费用，以及源码处理、留存删除和使用限制。

## 4. 对接方式建议

- **已有兼容 MCP**：优先评估复用 CodeBuddy 现有 MCP 接入机制。
- **仅有成熟 HTTP API**：比较直接适配与封装 MCP 的开发、部署、维护及复用成本，选择总成本更低的方式；不预先指定封装责任或要求新增 MCP Server。
- **已有 SDK**：评估语言、运行环境、授权及分发兼容性。
- **暂无独立调用入口**：先由双方确认可开放能力及所需资源，再决定是否进入开发，不直接制定新服务架构。

最终方式以现有接口资料和小规模验证结果为依据。

## 5. 职责与下一步

**SecVibe**：说明并提供可开放的既有能力、接口资料、测试条件和技术支持，确认能力与数据边界。

**CodeBuddy**：开展接入评估；在范围确认后负责必要适配、代码授权范围、结果展示、Agent 修复流程及产品侧验证，不重建审查引擎。

**双方负责人**：协调联系人、资料与测试资源，确认使用模式、首版范围及后续安排。

建议先指定技术联系人并交换上述资料，再开展一次接口说明与需求确认。随后共同选择一个小型脱敏项目，验证“提交代码 → 返回审查结果 → 修复 → 复检”，记录实际耗时、检测结果及接入缺口。完成验证后再确定技术路线、工作量和交付计划。
