# SecVibe 與 CodeBuddy 程式碼安全審查能力技術對接需求

日期：2026-10-23｜階段：能力確認與接入評估

## 1. 合作目標

希望重用 SecVibe 既有的程式碼安全審查能力，讓 CodeBuddy Agent 審查生成或修改的程式碼，取得位置、風險說明及修復建議，並於授權範圍內修復、測試與複檢。本次先研究如何接入已有能力，不預設 SecVibe 新建服務或重構系統。

**目前尚未取得正式介面文件，也未完成真實聯調；接入可行性、檢測覆蓋及效果均待驗證。**

## 2. 希望接入的能力與使用模式

核心需求為程式碼安全問題檢測及 Agent 可理解的結果。希望了解檔案定位、風險分級、證據、修復建議及再次檢查；相依漏洞、敏感資訊洩漏等按已有能力評估，不預設全部支援。

考慮兩種模式，首版範圍待雙方確認：

- **主動審查**：使用者要求審查指定程式碼或目前改動，確認當次範圍和授權，按次評估耗時及費用。
- **自動審查**：Agent 生成或修改程式碼後於約定節點觸發；另確認頻率、持續授權、延遲及預算，以及服務不可用或發現問題時的處理。

自動審查不等於自動修改，也不等於強制阻止完成。修復權限及完成門檻需另行約定；兩種模式均未預定為全部交付範圍或首版必做項。

## 3. 請 SecVibe 確認的現有條件

1. 能力是否可脫離網頁/人工操作獨立呼叫？是否已有正式支援的 MCP、REST/HTTP API 或 SDK？
2. 支援哪些語言、專案及安全檢測類型？有哪些覆蓋限制？
3. 接受檔案、片段、差異、專案包或儲存庫引用？大小及執行限制為何？
4. 回傳格式為何？是否有位置、等級、證據與建議？如何表示未完成、失敗或部分檢查？
5. 能否提供文件、脫敏輸入/結果範例、測試環境、鑑權方式及技術聯絡人？
6. 請說明現有部署與網路、典型耗時、並發/配額/費用，以及程式碼處理、留存刪除及使用限制。

## 4. 對接方式建議

- **已有兼容 MCP**：優先評估重用 CodeBuddy 的既有 MCP 機制。
- **僅有成熟 HTTP API**：比較直接適配與封裝 MCP 的開發、部署、維護及重用成本；不預定封裝責任或要求新增 MCP Server。
- **已有 SDK**：評估語言、執行環境、授權及分發兼容性。
- **沒有獨立入口**：先確認可開放能力及資源，再決定是否開發，不直接制定新服務架構。

最終方式以正式資料及小規模驗證為依據。

## 5. 職責與下一步

**SecVibe**：說明可開放的既有能力、提供文件及測試條件，支援技術說明，確認能力與資料邊界。

**CodeBuddy**：評估接入；範圍確認後負責必要適配、授權範圍、結果展示、Agent 修復流程及產品驗證，不重建審查引擎。

**雙方負責人**：協調聯絡人、資料及測試資源，確認模式、首版範圍與後續安排。

先交換資料並安排介面說明與需求確認，再選一個小型脫敏專案，驗證「提交 → 結果 → 修復 → 複檢」，記錄耗時、檢測結果與缺口。完成後再確認技術路線、工作量及交付計畫。
