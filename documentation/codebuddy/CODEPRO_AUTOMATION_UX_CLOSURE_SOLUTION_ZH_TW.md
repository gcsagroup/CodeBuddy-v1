# CodePro 自動化執行與使用者體驗閉環方案

[繁體中文（預設）](CODEPRO_AUTOMATION_UX_CLOSURE_SOLUTION_ZH_TW.md) · [简体中文](CODEPRO_AUTOMATION_UX_CLOSURE_SOLUTION_ZH_CN.md) · [English](CODEPRO_AUTOMATION_UX_CLOSURE_SOLUTION_EN.md)

## 一句話結論

目前看到的「停止、失敗、根目錄報錯、設定稍後才出現、只有部分步驟有進度、報告格式不一致」不是幾個互不相關的小問題，而是執行狀態、恢復動作、公開進度和最終報告尚未使用同一份資料合同。解法不是隱藏錯誤文字，而是建立一條可持久化、可恢復、可觀察且由後端事實驅動的完整執行鏈。

## 範圍與邊界

本方案解決四類問題：

1. 普通驗證失敗、缺少工具或權限不足時，任務過早顯示「失敗／停止」。
2. 使用者在磁碟根目錄建立對話或要求建立新專案時，系統沒有自動建立並綁定專案子目錄。
3. 開啟「高級模型路由」時，選項先不完整，稍後才突然出現。
4. Planner、Coder、Tester、Reviewer 的公開工作進度和最終報告格式不一致。

本方案不承諾「永遠沒有錯誤」。真正不可恢復的程式崩潰、資料損壞或重試預算耗盡仍必須如實告知使用者。要消除的是把可恢復情況錯標成終止性失敗，以及讓使用者長時間看不到進度。

## 已核對的目前事實

- `task_scheduler.rs` 已能產生 `VerificationFailed`、`WaitingForUser`、`InfrastructureFailed` 等結果，但仍有路徑把基礎設施問題收斂為一般 `Failed`，或把無進展轉成不可恢復人工審查。
- `worker_activity_callback` 轉發原始 Agent 訊息時只保留確認與詢問內容；工具活動能另外產生摘要，但並非每個角色、每個階段都有一致的公開進度事件。
- `codeProActivityModel.ts` 仍保留依靠「已停止／stopped」等文字猜測狀態的舊路徑，UI 可能與後端真實狀態不一致。
- 根目錄目前被視為專案分組與預設工作目錄，允許繼續執行；但新專案子目錄的建立與綁定只在部分 `NeedsWorkspace` 流程中完成，合同不一致。
- `CodeProModelModal.tsx` 先載入 Provider、設定和預設值，再等待多個 Provider 的模型發現；慢 Provider 會延後完整選項的呈現。
- 分析、簡單修復、DAG 聚合、終態和 Report Writer 仍有多個報告入口，雖然部分已共享結構化事實，但使用者可見版式尚未完全統一。

## 目標架構

每次執行只保留一份權威狀態，其他畫面都從它投影：

```text
使用者請求
  -> Intent + WorkspaceDecision
  -> RunState + RecoveryAction
  -> PublicProgressEvent
  -> UserReport
```

### 1. 統一執行狀態與恢復動作

狀態回答「現在發生了什麼」，恢復動作回答「系統接下來做什麼」，兩者不可混在一個 `Failed` 裡。

建議權威狀態：

- `Running`：正在分析、修改或測試。
- `VerificationFailed`：專案驗證未通過，但仍可進入修復。
- `Repairing`：Coder 正在根據結構化失敗證據修改。
- `Retesting`：Tester 正在重跑原命令。
- `WaitingForUser`：需要權限、登入、下載、路徑或高影響確認，進度已保存。
- `WaitingForEnvironment`：缺少 Node、PATH、執行階段或暫時資源，正在診斷或等待可恢復條件。
- `Succeeded`：權威驗證通過。
- `Cancelled`：使用者明確取消。
- `Exhausted`：修復或重試預算已用完。
- `Fatal`：進程或資料發生無法安全恢復的故障。

建議恢復動作：`RetrySameStep`、`RepairThenRetest`、`AskUserThenResume`、`DiagnoseEnvironment`、`Replan`、`Finish`。

硬性規則：

- `node -v` 啟動失敗不能直接等於專案測試失敗；先診斷命令是否存在、PATH、執行階段和權限。
- 測試退出碼非零時保存命令、cwd、stdout/stderr 引用和失敗測試，轉入 Coder，然後重跑完全相同的命令。
- 權限不足或範圍擴大時建立檢查點並詢問使用者；批准後恢復原步驟，不建立新任務、不丟失上下文。
- 只有使用者取消、明確預算耗盡或不可安全恢復時，才顯示終止狀態。

### 2. 根目錄與新專案採用原子工作區配置

根目錄（例如 `D:\`）是專案容器，不應直接當成新專案的寫入根，也不應報成「沒有可信工作區」。

當使用者說「建立教務管理系統」且目前位於根容器時：

1. 從需求產生可讀、無衝突的子目錄名稱，例如 `D:\academic-management-system`。
2. 在同一事務中建立目錄、取得 workspace lease、保存綁定和檢查點。
3. 成功後在該目錄續跑原始訊息，不再要求第二次工作區確認。
4. 名稱衝突時選擇安全後綴；只有多個候選會造成實質不同結果時才詢問使用者。
5. 建立目錄或取得權限失敗時進入 `WaitingForUser`，顯示需要的路徑和操作，不顯示專案失敗。

對現有專案的分析請求必須保持唯讀；「給我優化方向」不得被分類為修改意圖。

### 3. 每個角色都發布公開工作進度

使用者需要看到「系統在做什麼」，但不應顯示私有思維鏈、系統提示詞、密鑰或未經整理的模型草稿。

每個 Planner、Coder、Tester、Reviewer 都發布同一格式的 `PublicProgressEvent`：

- `role`、`phase`、`task_id`、`attempt_id`
- 一句可公開摘要，例如「正在定位失敗測試的原因」
- 目前工具、命令或檔案（經安全過濾）
- 開始時間、最近活動時間、已耗時
- 已完成數／總數（能確定時）
- 下一步與等待原因
- 結構化狀態，不使用文字反推狀態

UI 行為：

- 活動卡預設顯示一句摘要、耗時和最近心跳。
- 展開後顯示公開步驟、命令進度、增量輸出和可理解的等待原因。
- 10 秒無新輸出時顯示「仍在執行，最近活動於……」，不能自行判定卡死。
- 只有心跳超時且後端確認進程已退出時，才顯示需要恢復或診斷。
- 舊文字事件只作相容顯示，不能再影響權威狀態。

OpenAI 官方文件把 preamble 定義為工具呼叫前簡短、使用者可見的用途說明，也支援 reasoning summary。CodePro 採用這種「公開摘要＋工具進度」方向，但拒絕直接暴露隱藏思維鏈。參考：[OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model#preambles)。

### 4. 高級模型設定改為漸進式載入

設定彈窗不應等待所有 Provider 才顯示可用內容。

改造方式：

- 開啟時立即用持久化快照顯示四個角色及上次選擇。
- Provider 清單、預設設定和每個 Provider 的模型清單分開載入。
- 每個 Provider 完成後立即更新自己的下拉框，不等待最慢 Provider。
- 每個下拉框有獨立的 `loading / ready / unavailable / retrying` 狀態。
- Provider 清單完成前可先顯示已保存組合；完成後若 Provider、連線或模型已失效，立即清空整組舊覆蓋並回到目前模型。
- 切換 Provider 使用 generation id 取消舊結果，防止過期回應覆蓋新選擇。
- 新建但尚未保存的高級組合可按 Provider 個別重試；已持久化組合只要有一個角色失效，就不再宣稱該組合有效。

### 5. 單一模型權威與切換事務

- 預設畫面只顯示一個「目前模型」，普通切換會關閉高級路由，使所有角色跟隨同一 provider/model。
- 高級模式必須明確開啟；每個角色只顯示「實際模型」和「獨立設定」，不再並列預設、推薦或另一個目前值。
- 普通切換由單調修訂號串行化；過期提交標記為 superseded，最新提交決定最終設定。若會話已切換但預設設定保存失敗，會補償回滾會話與高級路由。
- 每次 CodePro 任務開始時建立路由快照，因此執行中的任務不換模型；新設定從下一個任務生效。
- `ActivityEvent.effective_model` 是執行審計權威，活動詳情直接顯示該值。
- Provider 刪除或模型清單更新會在後端清除引用失效項的高級路由；UI 發現失效連線時執行同一回退。

### 6. 所有任務使用同一報告合同

建立唯一的 `UserReportV1`。分析、修改、測試和審查只提供結構化事實，由同一渲染器生成使用者報告。

預設報告固定為：

1. **一句話結果**：完成了、等待你確認，或尚未完成。
2. **做了什麼**：最多五條，使用自然語言。
3. **驗證結果**：哪些通過、哪些未通過、是否已修復重測。
4. **需要你做什麼**：沒有就不顯示。
5. **技術詳情（可展開）**：命令、cwd、退出碼、證據引用、run/task/attempt id。

禁止事項：

- 不把測試失败、缺少工具或等待權限寫成「限制」。
- 不把 `task_failure`、`repair_branch_unavailable` 等內部代碼放在正文。
- 不用 Agent 自述覆蓋宿主驗證結果。
- 不在沒有跑測試時寫「已通過」。
- 不因任務種類不同而改變核心段落順序和狀態用詞。

## 分階段實施順序

### P0：先打通自動修復主鏈

- 將所有退出路徑接入統一 `RunState + RecoveryAction`。
- 驗證真實鏈路：首次測試退出 1 → 保存證據 → Coder 修改 → Tester 原命令退出 0。
- 缺少命令、權限和使用者取消分別進入不同狀態。

### P1：移除 UI 文字猜狀態

- ACP/SDK/UI 共用結構化狀態與進度事件。
- `legacyStatus` 只作舊記錄展示，不能驅動新任務狀態。
- 活動卡增加心跳、耗時、增量輸出和恢復提示。

### P2：完成根目錄原子建專案

- 統一 RootContainer、NeedsWorkspace、lease 和子目錄配置合同。
- 確保分析請求唯讀，建立請求自動配置子目錄，真實歧義才詢問。

### P3：漸進式模型發現

- Provider 級別獨立載入、重試、快取和取消過期請求。
- 驗證首次開啟、慢 Provider、失敗 Provider、切換與重新開啟。

### P4：收斂報告入口

- 以 `UserReportV1` 為唯一使用者可見渲染合同。
- 舊生成器轉為事實提供者或相容轉接器，禁止直接輸出另一套正文。

## 必須通過的驗收場景

1. `node tests.js` 首次退出 1，UI 顯示「測試未通過，正在修復」，Coder 修改後原命令退出 0，任務完成。
2. `node` 不存在時顯示「缺少 Node.js 或 PATH 未配置」，提供修復／授權入口，不標成專案 Bug。
3. 需要讀取工作區外檔案時保存檢查點並詢問；批准後原步驟續跑。
4. 在 `D:\` 新對話要求建立專案，自動建立安全子目錄並完成綁定，不出現第二次工作區確認。
5. 「分析並給優化方向」全程不寫檔案；若模型嘗試寫入，策略層攔截並回到唯讀分析，而不是終止任務。
6. Planner、Coder、Tester、Reviewer 每一步都有可展開公開進度；長命令持續顯示心跳與最近輸出。
7. 一個 Provider 回應慢或失敗時，其他角色的模型選項仍能立即使用。
8. 分析、修復、測試三類任務的報告使用相同順序和直白狀態詞；技術代碼只在展開區。
9. 連續修復失敗只在明確預算耗盡後顯示「未能自動修好」，並保留所有證據和續跑入口。
10. API、持久化事件、SDK、UI 和最終報告對同一 run 的狀態解釋完全一致。

## 完成標準

只有同時滿足以下條件，才能稱為閉環完成：

- 後端聚焦測試和狀態機整合測試通過。
- ACP Schema 與 SDK 重新生成並通過相容性檢查。
- UI 組件測試覆蓋進度、等待、模型載入和報告。
- 真實 Windows 桌面完成上述十個使用者場景。
- 關閉重啟後仍能恢復 `WaitingForUser`、修復輪次、模型選擇和公開進度。
- 任一畫面都不再以本地化文字推測權威狀態。
