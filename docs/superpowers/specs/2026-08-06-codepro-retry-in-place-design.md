# CodePro 原会话重试设计

日期：2026-08-06

## 问题

普通助手消息没有结构化任务终态时，桌面端把“重试”解析为 `fork`，并调用 ACP 会话分叉接口。每次点击都会创建一个名称带 `(copy)` 的新会话。这混淆了“重试”和用户明确要求的“复制/分叉会话”，还会制造重复历史。

## 决策

“重试”永远在当前会话执行：

- 普通助手消息：找到对应的上一条可见用户请求，将其作为一条具有新消息 ID 的用户消息追加到当前会话，然后向当前 `sessionId` 再次提交。
- `continue_checkpoint`：继续使用当前会话中的保存检查点。
- `retry_failed_validation`：继续在当前会话中只重跑失败验证。
- `replay_user_request`：继续在当前会话中创建关联重跑。
- 找不到有效原始用户请求时不显示重试操作。

只有用户明确点击“复制会话”或用户消息上的“从此处分叉”时，才允许调用会话分叉接口。

## 数据流

1. 消息操作策略把没有结构化终态的助手消息解析为 `resubmit`，不再解析为 `fork`。
2. 消息组件向会话控制器发送新的 `retry` 编辑类型和原用户消息。
3. 控制器验证消息属于当前会话且包含文本或图片。
4. 控制器创建新的用户消息，追加到当前消息列表，并调用当前会话的提交接口。
5. 控制器不得调用 `acpForkSession`，不得导航到新会话。

## 错误处理

- 当前会话正在执行、取消或等待不可兼容的操作时，沿用现有提交门禁。
- 原消息不存在、角色不是用户或没有可重试内容时，拒绝操作并保留当前会话。
- 提交失败作为当前会话内的可恢复运行错误展示；该错误分类的完整修复属于相邻的会话错误恢复工作。

## 验收标准

- 普通助手消息的重试策略为 `resubmit`。
- 点击普通“重试”向同一个 `sessionId` 提交请求。
- 重试保留原请求中的图片并生成新的消息 ID。
- 重试不调用 `acpForkSession`，不创建 `(copy)` 会话，不触发会话导航。
- 明确的复制会话和用户消息分叉行为保持不变。
- 结构化检查点继续、关联重跑和失败验证重跑行为保持不变。
