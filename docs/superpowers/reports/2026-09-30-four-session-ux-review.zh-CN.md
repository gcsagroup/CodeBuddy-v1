# CodePro 三题测试与 WorkBuddy 用户体验对照复盘

日期：2026-09-30。性质：证据回顾与改进依据，不是实施完成报告。

本报告分别回顾三次 CodePro 测试和一次 WorkBuddy 对照，再整合用户体验问题。核心结论是：CodePro 三题均有实际交付，但用户难以稳定判断正在做什么、为何仍在等待、哪些结果已经验证，以及怎样开始使用成品。WorkBuddy 本次的连续生成反馈和直接预览更自然。比较重点是这些用户可感知的体验，不是以生成品的一次性缺陷给模型或产品排名。

**改进方向是借鉴 WorkBuddy 更人性化的地方，而不是全面照搬。** 保留 CodePro 的事实归属、权限和完成边界，优化从提出需求、等待执行、理解结果到使用交付物的完整过程。不把对照产品的外观当成内部架构证据，也不因界面简洁而删除必要检查。

**用户补充的评估边界：** 初次生成存在缺陷、需要多轮修复是正常现象。同一模型每次输出也会不同，本次没有进行重复采样和多轮修复对照，不能据某个缺陷判断 Kimi-K3 能力不足，也不能据检查较少判断 WorkBuddy 阻碍了模型复盘。两种归因目前都缺少控制变量证据。稳定性值得后续单独评估，但不扩大本次体验复盘的范围。

交付物缺陷保留为当次可回查观察，不作为否定体验优势或要求 Agent 一次写对全部代码的依据。宿主这一轮应重点接受审查的是：模型能否获得可靠工具和反馈，用户能否理解过程，失败后能否继续检查和修复，以及报告是否如实表达已经做过的验证。

## 阅读方式与证据边界

- **原执行事实**：来自用户提供的会话、录屏和对应日志。
- **源码事实**：来自当前 checkout 或生成文件的静态阅读；不自动等于运行时行为已验证。
- **补充检查**：审查者随后在隔离浏览器或临时输入上做的检查，不是原 Agent 当时完成的验证。
- **审查意见**：对用户影响和改进方向的判断，不是已经实施的功能。
- **未知**：证据不足的部分保留未知，不用推测补齐。

录屏采用全程约每 20 秒抽帧，再对关键时段加密查看；不是逐帧观看，也未分析音轨。耗时是本次样本，不是性能基准。共享链接提供静态会话，实时行为主要由录屏支持。

产品源码参考：`C:\Users\admin\CodeBuddy`，分支 `work/codebuddy-next`，HEAD `68423420ee28fcfaa4b3c4d3f2a7d70da9aaf1c5`，带既有未提交改动。三份 CodePro 会话记录的 build provenance 同为该 revision 且 `source_dirty=true`；这不能证明每个当前未提交文件都与运行二进制逐字一致。本文将运行证据与当前源码解释分别列出。

本次只新增报告。没有修改产品代码、原始会话、录屏或交付物；未构建、未启动新的 CodePro、未提交或推送。补充检查使用临时浏览器上下文或隔离输入，不使用用户现有浏览器数据。

## 题目一 宠物店预约管理

### 原始目标与交付

### 分项审查

**Q1 UX01 等待提示没有反映真实更新。** 录屏约 100 秒处显示“深度思考 正在更新”和“正在接收思考内容”。日志表明，该阶段最后思考分片与下一工具事件之间约有 69 秒空档。当前 `BaseChat.tsx` 根据最新消息是否含非空 thinking 选择接收思考文案，没有以新分片是否仍在到达为依据。源码解释与可见现象一致，但不能据此确定空档全部发生在模型服务、代理还是解析器。

用户影响：内容已不变化，文案却持续声称接收，用户难以判断是在生成、卡住还是已经完成思考。

**Q1 UX02 计划样式是三题中的异例。** 本题计划使用不带列表前缀的 `[x]`、`[-]`；另外两题使用 `- [x]`、`- [-]`。当前 `CodeProPlan` 仅识别带 `-` 或 `*` 前缀的行，本题回退到普通 Markdown，其他两题使用图标和计数列表。不是窗口大小或用户设置差异。

**Q1 QUALITY01 基本功能存在真实价值，但边界未完整覆盖。** 补充的隔离浏览器检查确认：新增后刷新仍保留、同日同美容师冲突被拒绝、电话号码前导零保留。另复现：

1. 当天 23:30 开始且持续 60 分钟的预约，与次日 00:00 的同美容师预约都可保存。`findConflict` 先跳过不同日期，漏掉跨日重叠。
2. 取消旧预约、在原时段新建预约后，旧记录仍可直接标记为完成。没有状态转换核对，容易形成矛盾记录。这不同于证明两笔待服务预约同时存在，不夸大其后果。

这是审查者补充发现，不是录屏中已发生的客户事故。跨午夜属于边界；状态误改更接近日常操作风险。

**Q1 REPORT01 验证范围交代不足。** 原执行中的“7 项通过”来自模拟浏览器环境的脚本，不是完整真实页面验收。第一次失败是测试环境未正确绑定 `window` 的问题，不能算成已证明的产品缺陷。命令尝试打开页面也不等于工具观察到了页面。最终报告应区分逻辑检查、页面操作和日常可靠性，不将它们合并成“全部验证通过”。

**本题审查意见：** 保留低门槛单文件方案。优先修真实进度和稳定计划展示；生成工具的质量问题另列验证缺口，不在宿主里硬编码宠物店业务流程。

**本题审查意见：** 保留清楚的业务解释和报表层级。补齐通用异常处理和证据诚实性，同时让生成、检查、交付之间的反馈连续。

## WorkBuddy 宠物店预约对照

### 样本身份与可比范围

使用与 CodePro 题目一相同的原始需求，目录为 `C:\test\0930\01_booking_workbuddy`，录屏显示 WorkBuddy 5.6.2、Kimi-K3、允许完全访问。两个分享链接属于同一会话，不计作第五次测试。两份分享中的 HTML 与本地 `宠物店预约管理.html` 字符内容一致，后附指纹。

分享记录包含开发过程及后续导出聊天记录的问题。本文只将开发预约工具的一轮作为对照；不把导出问题的追加时间计入任务耗时。

### 可见体验与时间线

以下是视频内偏移，不是网络分片到达时间：

| 视频偏移 | 可见行为 |
| --- | --- |
| 约 20 至 75 秒 | 思考区域展开，文本随时间变化，主要为英文 |
| 约 80 秒 | 出现中文需求确认和实现说明 |
| 约 100 秒 | 文件项显示“生成中”，增加行数约为 +29 |
| 约 200 秒 | 同一文件生成进展达到约 +257 |
| 约 310 秒 | 文件创建项显示文件名及 +597，底部转为等待模型响应 |
| 约 320 至 360 秒 | 说明语法检查、执行检查并写工作日志 |
| 约 370 至 385 秒 | 右侧打开真实产物预览，左侧使用说明逐步出现 |
| 约 390 秒 | 最终答复完成，产物卡片、预览和使用说明同时可见 |

**WB UX01 生成过程更容易理解。** 写文件前的长生成期有持续更新的行数，而不是一直静止后突然出现已写入。它证明前端持续展示了生成进展，不能证明磁盘逐行写入，更不能从行数计算可靠完成百分比。

**WB UX02 思考呈现较连贯。** 录屏中的主思考区域在生成期展开更新，进入后续工作后收起，未见 CodePro 样本中的重复历史块。但英文长篇思考对中文店主仍不友好，且开头并非立即出现中文进度。值得借鉴的是生命周期和阅读秩序，不是原样展示长篇英文内容。

**WB UX03 没有独立任务计划卡片。** 本轮以中文功能说明建立预期后直接执行，没有创建可勾选计划。不能据此评价其复杂任务计划关联、跨轮继续或插话机制；也不能得出 CodePro 应删除所有计划的结论。

**WB UX04 交付接近实际使用。** 文件卡片可点击，右侧直接预览，左侧按打开、记一单、防排重、防漏单、日程、备份解释。用户不用先在日志和路径中寻找入口。最终正文逐步出现，而不是整段突现。不过录屏未完成新增、冲突、刷新保留的完整功能验收，预览成功不能算业务验证通过。

### 交付物补充观察与归因限制

原会话只记录了 JavaScript 语法检查，输出 `JS OK`、退出码 0，没有记录业务功能测试。语法检查通过的表述本身准确，但本次验证范围有限。没有证据表明模型曾尝试更深入检查却被 WorkBuddy 阻止；不能把未执行功能测试归因为宿主妨碍检查，也不能据此给模型能力定性。

审查者使用隔离浏览器实际填写表单并点击页面，确认基本保存、刷新保留、同日冲突提示有效；又复现两个问题：

1. 取消旧预约，在原时间新建预约，再通过“恢复为待服务”恢复旧预约，会产生同美容师同时间的两笔待服务预约。`setStatus` 直接改状态而不检查冲突。日程块还会相互覆盖，顶部显示两单，时段内却看起来只有一个块。
2. 跨午夜的重叠预约仍可同时保存。与 CodePro 类似，冲突筛选只比较同日期。

这是补充检查，不是原录屏中已发生的事故。测试脚本首次因默认“待服务”筛选隐藏已取消记录而定位超时；改为通过界面选择“全部”后完成检查，退出码 0。该定位失败不计作产品缺陷。

**对照审查意见：** WorkBuddy 的优势是连续反馈、自然的信息层级和可直接使用的产物入口。补充发现的代码缺陷不抵消这些体验优势；模型能否在后续反馈后修好，本轮未测试。它也会等待模型响应；差距在等待前后是否有足够事实让用户理解，而不是是否出现过某句等待文案。

## 跨记录问题与职责

以下整合在四次独立审查之后进行，不将所有症状归成一个根因。源码位置是阅读入口，应结合函数和当前 diff 查找，后续行号变化不改变证据性质。

### 计划展示与归属

**格式差异已确认。** [CodeProToolContent.tsx](../../../ui/desktop/src/components/codepro/CodeProToolContent.tsx) 中 `CodeProPlan` 的正则仅接受带列表符号的复选行，导致题目一与另外两题样式不同。修复属于已有计划展示合同，不需要新计划状态机，也不能从未完成项顺序猜测当前动作。

**同任务旧版本被叫作上次任务已确认。** 三题内部需求合同更新后，选中版本分别高于原计划版本；[CodeProPlanDock.tsx](../../../ui/desktop/src/components/codepro/CodeProPlanDock.tsx) 将同运行旧版本计划作为历史展示并标记“上次任务列表”。用户没有发起新目标，这一文案容易误导。保留旧计划历史是必要边界，不能为消除文案问题直接把旧勾选迁移成新版当前计划。

职责：宿主保持 run 与 requirement revision 的归属；Todo 保存模型清单；UI 消费绑定并准确解释“同任务旧版本”和“当前计划”。本轮没有验证换目标、跨任务污染、执行中插话或恢复的行为。

### 思考内容与实时状态

**重复传递与逐条显示已有源码依据。** [agent.rs](../../../crates/goose/src/agents/agent.rs) 拆分工具请求时向每条请求复制 `response_thinking`；[GooseMessage.tsx](../../../ui/desktop/src/components/GooseMessage.tsx) 对各消息中的思考分别渲染。模型上下文保留需求不等于用户必须重复阅读。不能只因 UI 重复就断言模型重复推理。

**活跃判断过宽已有源码依据。** [BaseChat.tsx](../../../ui/desktop/src/components/BaseChat.tsx) 的 `receivingReasoning` 看最新消息是否含思考，不代表现在仍有分片。[ThinkingContent.tsx](../../../ui/desktop/src/components/ThinkingContent.tsx) 有独立滚动区域和手动展开偏好，但组件自身未实现内容更新时跟随底部。不同调用入口的默认展开方式也不同。

职责：流式通道提供实际更新和结束事实；消息投影维护展示身份；UI 管理展开及阅读位置。只消费公开返回的思考内容，不额外索取、伪造或生成所谓完整思维链。用户手动回看时，不应强制抢回底部。

### 生成预览和阶段标题

当前源码已经有 `tool_input_preview`：Provider 生成显示用快照，ACP 转成带 `__inputPreview` 的 Pending 调用，桌面适配器和工具标题消费它。入口见 [formats.rs](../../../crates/goose-provider-types/src/formats.rs)、[OpenAI 流解析](../../../crates/goose-provider-types/src/formats/openai.rs)、[ACP server](../../../crates/goose/src/acp/server.rs)、[tools.ts](../../../ui/desktop/src/acp/adapter/tools.ts) 和 [toolActionPresentation.ts](../../../ui/desktop/src/components/toolActionPresentation.ts)。

**未知：** 本轮长等待里为什么没有及时体现这一预览，尚不能仅凭当前源码指定责任层。不能先宣称完全没有预览机制，再新建重复通路；也不能以代码存在宣称已修好。

[currentWorkStage.ts](../../../ui/desktop/src/components/codepro/currentWorkStage.ts) 读取成功发布的结构化 stage。题目二两次使用公开进度工具，题目一、三没有，普通说明不会自动成为该标题。最近阶段可以作为上下文，但不能冒充当前真实执行动作。改进不应通过解析自然语言或强制模型持续调用某工具来维持假实时感。

职责：模型决定工作策略并可发布语义进度；Provider 和传输链提供生成活动；Runtime 提供派发与回执；UI 区分生成内容、实际执行、等待响应及检查结果，不替任一 owner 创造事实。

### 最终答复集中释放与尾部等待

UI 日志中三题最终正文各为一个 `agent_message_chunk`。宿主发送时间到 UI 接收时间分别约 67、89、62 毫秒。这仅度量该段通知传递，不等于总响应延迟。

[agent.rs](../../../crates/goose/src/agents/agent.rs) 的 `agent_text_buffered`、`pending_final_output` 和 `agent_final_released` 路径显示，主 Agent 正文会先缓冲，再经相关条件和检查后释放。Host 集中释放确实参与了“最后整段出现”，不能只归责模型服务或前端。

**未知：** 网络、解析、正文生成和完成检查各占多少等待时间。本次 UI 探针有记录，但后端对应日志文件为空，轮转请求日志只保留题目一尾部，四段时间证据不齐。不得为模拟打字效果在已经收到整段正文后人为延迟播放，并称为真实流式。

职责：完成层消费权威事实；正文是否可以提前展示应明确其性质，不能提前宣布通过检查。保留门槛并不意味着普通过程说明也必须一直缓冲，具体落点需按现有消息合同核对，不在本报告里擅自变更冻结边界。

### 内部诊断与用户解释

三题中的内部合同拒绝不等同于三份业务均失败。用户真正需要知道的是：影响了什么、是否已恢复、还要不要自己做什么。版本号、工具 JSON、审计 ID 等可留给按需诊断，不宜占据主阅读路径。

但不能仅把所有失败隐藏：若确实影响交付、授权或需要用户选择，应明确说明。完成检查也不应把宿主已掌握的机械事实无限转交给模型复述。对合同减负的具体修改另行追踪调用链，不借体验优化改变权限或完成事实 owner。

## 借鉴范围与不照搬事项

| WorkBuddy 的可见做法 | 借鉴的人性化价值 | CodePro 的改进边界 |
| --- | --- | --- |
| 文件生成行数变化 | 长等待可感知，用户知道任务仍推进 | 使用真实生成事件，不把预览当落盘，不伪造百分比 |
| 思考更新后自然收起 | 保持阅读秩序，减少旧内容占位 | 同一内容只呈现一次，尊重手动展开与回看，不照搬英文长篇 |
| 最终正文逐步出现 | 交付过程连续 | 不绕过完成门槛，不用打字动画伪装上游流式 |
| 卡片和直接预览 | 从收到结果自然进入使用 | 入口对应真实文件或服务，打开失败明确反馈；预览执行边界单独核对 |
| 面向日常操作的说明 | 用户知道下一步做什么 | 不把技术日志当说明，也不把简短说明当功能验证 |
| 本轮没有独立计划卡 | 简单任务不增加额外负担 | 不强制所有任务建计划，也不删除复杂任务需要的计划能力 |

这次对照不意味着要把所有任务的验证缩成语法检查，也不意味着一律增加固定功能测试流程。模型仍决定合理的检查和修复策略，宿主提供合法可用的能力、真实结果及必要边界。不得隐藏未解决问题、自动放宽生成内容的运行权限，或为仿制外观重建平行状态系统。成品质量受模型、任务、上下文、工具和环境共同影响，本次不分配各因素的责任比例；体验改进与交付物业务缺陷分别管理。

## 后续改进顺序与用户验收

以下是审查建议，不是已实施方案或自动批准的协议变更。

**第一批聚焦过程。** 核对已有生成预览的运行传播，修正思考重复、活跃提示和计划格式一致性。保留同任务旧版本的真实归属，用准确说明代替“上次任务”的误导。需要改变持久化、协议或 owner 时单独提出方案，不能借 UI 修复偷偷迁移计划。

**第二批聚焦交付。** 复用现有文件查看、打开入口，让用户找到并使用交付物。内嵌预览需考虑生成脚本执行、权限及本地存储位置，不能假定预览与用户外部浏览器数据互通。最终正文流式与完成门槛的关系单独核对，不全面照搬对照产品。

**贯穿两批的原则。** 少增加模型负担和额外请求；不硬编码业务流程、不增加平行状态机、不通过关键词猜授权和终态。诊断折叠不是删证据，显示流畅不是假装成功。

验收沿一个连续用户过程，而不是只截几个组件成功画面：

1. 发送原始自然语言需求。收到什么活动证据就展示什么，没有证据时如实等待，不立刻编造“正在设计某模块”。
2. 长生成期间能看到可验证的进展；断流时不持续宣称接收新内容；生成完后及时转入真实工具或等待状态。
3. 同一思考在实时、折叠、切会话再返回时不重复；用户向上阅读不被抢滚动，返回最新位置有明确入口。
4. 三题已有计划格式得到稳定展示；同任务版本变化不冒充新任务，也不自动继承失效勾选。无需计划的任务不强行加计划。
5. 检查和恢复只展示真实影响；可展开查看诊断；停止或失败后不残留正在写某文件的提示。
6. 最终有真实交付入口和面向使用的说明；打开失败可见；明确哪些检查做过、哪些没做，不把预览当业务验收。

优先复用本次三题作为互补样本：预约题观察普通用户的端到端使用，库存题观察修复与验证后的收尾，对账题观察数据异常及报告证据。WorkBuddy 只作为本次体验对照，不要求所有交互一比一相同，也不据单次样本断言整体产品优劣。

## 回顾结论与后续记录规则

本报告确认的是四次具体样本和有限补充检查，不是产品成熟度认证，也不是模型或生成代码质量排行榜。计划、思考、等待、收尾和产物入口需要分别修复，再以连续用户过程验收。没有证据的网络延迟归因、跨轮计划行为、WorkBuddy 内部机制继续保留未知。

后续若评估稳定性，应另立范围，采用重复任务和多轮修复过程，区分模型输出差异与宿主是否稳定提供工具、上下文、执行反馈和恢复能力。本轮不追加这类测试，也不以一次初稿有缺陷替代稳定性判断。

后续实施记录应引用本文问题标识，分别填写修改来源、真实验证、剩余限制与 E2E 结果；不要把本报告改写成“当时已经修好”。成品业务缺陷与宿主体验缺陷分开跟踪，避免为了一个生成样例把业务规则写入宿主。

最终目标不是让 CodePro 长得像 WorkBuddy，而是让用户在等待时理解进展、回看时不迷失、交付时能上手，并且信任这些表现背后的事实。
