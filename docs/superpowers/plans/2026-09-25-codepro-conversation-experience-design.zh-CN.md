# CodeBuddy 对话体验重设计：先让用户看懂工作

状态：设计提案，供用户检查；不替换或擅自修改已冻结 R3，不代表产品已经实现。

## 1. 目标与边界

用户目标是接近桌面 Codex / WorkBuddy 的使用体验，不追求特立独行。默认界面是一段能读懂的协作过程，而不是调试控制台。用户不打开任何工具详情，也应知道：正在做什么、有什么进展、是否需要自己介入、最后得到什么。

本轮先确定信息结构、交互、内容来源和验收，再实现。不是再改一次边框，也不引入新的 Planner、Judge、状态系统或总结 Agent。后台真实错误不能由 UI 隐藏、豁免或改判。

## 3. 成熟案例：学什么，不照抄什么

## 4. 信息结构：正文是主线，操作是证据

从默认到深入共三层，不让用户连点多层通用参数表：

1. **默认阅读层**：简短公开说明、当前工作、必要的计划、重要异常、最终交接。
2. **操作记录层**：可折叠轻量列表，文件名/动作/状态，限高滚动。
3. **具体证据层**：命令输出、文件内容或真实 diff、验证结果；原始 JSON 放“诊断详情”。

公开说明是面向用户的计划、发现、取舍和下一步，不是隐藏推理。不能读取隐藏思考补成阶段总结，不能显示内部系统提示。

### 用户语言与自然表达（用户补充要求）

- 计划、当前工作、阶段总结、异常解释和最后交接都必须以面向用户的自然语言表达，不能用工具名、内部阶段代号、计数或参数表代替。清单可以保留，但每一项应是用户能理解的具体工作。
- 语言优先遵循用户当前明确要求，其次遵循已知的用户语言偏好；都没有时，根据当前 query 的主要交流语言表达。由模型理解语言意图，不用关键词表裁决；不要为普通语言选择增加一次提问。代码、路径、命令及必要原文保持原样，解释使用用户语言。
- 服务用户，而不是展示内部机制。例如“正在补齐学生选课和退课功能”，比“执行 write”更有用；“登录检查发现数据库初始化问题，接下来修复”，比“工具调用失败”更有用。这些说明必须有当前行动或观察支持，不能机械套用示例。
- 默认可见文案要回答“做什么、为什么现在做、有什么结果、接下来怎么办”中的相关问题，不要求每次凑齐四项。保持简短，不把用户拖进宿主协议、审计 ID 或技术自述。
- 原始工具标题可以保留在详情中，但不能因其是英文就覆盖面向用户的本地化说明。缺少语义说明时，按用户语言显示真实动作及对象；语言本地化不能扩大事实含义。

### 目标布局示意（示例文案，不是本次已验证成果）

```text
我先确认项目环境，再实现登录、基础资料和选课流程。

  ▾ 工作计划                         1 / 4
    ✓ 确认环境与范围

    ○ 验证角色权限与业务流程
    ○ 整理启动方式与交付说明

  ▸ 实现登录和学生管理 · 8 项操作

      修改  app/models.py             查看变更
      检查  登录测试                   未通过

  ▾ 修复并验证数据库初始化 · 3 项操作
```

阶段标题仅在有公开说明/计划关联时使用；无关联就保守显示“正在修改 app/models.py”或“执行记录”，不能用文件名和关键词猜测完成了“权限模块”。上面只示意层次，不强迫所有任务走四个固定阶段。

## 5. 六类交互必须一起设计

### A. 开始与计划

- 用户发出任务后立即反馈已接收；模型尚未返回时显示“正在分析任务”，不是虚构进展。
- 有重要范围歧义时只问用户能理解的产品问题，给推荐项；不让用户选宿主实现方式或填写内部协议。
- 普通小任务不强行列计划。复杂任务展示简短业务步骤，展开可看全部；计划来自现有计划内容，不增加调度器。
- todo 勾选是模型的工作进度，不是验收事实。保留首次计划及更新关系，历史位置不能被最后“全部勾选”倒灌。

### B. 执行与阶段说明

- 开工前说明接下来做什么；关键发现、方案调整、阶段切换、较长等待、最终停止时有可见反馈。
- 不要求每次工具调用前说一句话，不按“每 10 次调用”机械总结，不定时编造发现。
- Main Agent 负责公开说明；Host 负责实际执行状态；UI 负责组合呈现。缺模型说明时用有据的动作/等待状态降级，不能保持空白，也不能自动杜撰业务进展。
- 已完成普通操作默认收起；当前动作可在收起组标题中看见；失败/审批/结果未确认有外露提示，但不必把整屏堆栈强制展开。
- 内部合同检查仍保留诊断入口，不占主阅读流；若它阻塞任务，显示用户能理解的影响与责任方。

### C. 文件、命令及其他工具详情

- 文件行：动作 + 相对路径 + 状态；点开直接看代码/真实 diff，不先经过 `content` 参数表。
- 有前后版本才显示增删行和 diff；仅有写入回执则写“文件已写入”，可查看内容，不能伪造差异或撤销能力。
- 命令行：短说明/命令摘要 + 运行状态；点开显示实际命令、cwd、输出、退出码/超时、耗时。说明缺失不强行调用额外模型翻译；已知工具类别使用本地中文动作名。
- 原始参数、审计 ID、协议 JSON 放诊断详情；涉及凭据的内容展示和复制都要脱敏。
- 通用未知工具仍有安全降级，不因没有专用视图就消失。计划、审批、提问、委派、修改、命令分别适配，不给每个工具重造一套通用卡片。

### D. 异常、审批、子任务

- 普通命令失败且 Agent 正在处理：显示“某项检查未通过，正在处理”，不把任务直接标红终止。
- 需要用户时：突出具体问题、影响范围、可用选择；审批回答通过原审批通道，不转成普通聊天许可。
- 子任务可不用，但使用时显示在做什么、运行/等待/失败、结果入口；默认不复制其全部日志到主线。
- 未确认副作用与失败分开显示；不能因另一轮测试通过自动消除旧未知副作用。

### E. 停止与交付

完成、受阻、用户取消、连接中断均有对应收尾，不统一显示“已完成”，也不能只留“暂停”。

受阻时示例结构：

```text
本次开发已暂停，尚不能确认全部交付完成。
已完成的工作：〔由实际文件/工具事实支持的简述〕
已验证：〔命令、结果及对应版本；未验证则明说〕
当前阻塞：部分命令的后续影响尚未核对。
下一步：〔当前系统实际支持的恢复或诊断动作〕
查看文件变更   查看验证记录   展开技术详情
```

- 已确认的部分成果不应随整体暂停一起被抹掉。
- 不把被拒绝的完成草稿直接展示成事实；用报告事实来源提供已完成/未确认部分。
- 只有存在有效恢复绑定时才给“继续”按钮；不空口承诺可恢复。
- 不提供假的一键修复、打开服务、撤销按钮；能力不存在时说明限制。

### F. 滚动与历史

- 对话整体一条滚动轴；活动组展开区域上限约 240–320px，随窗口高度适配；这是一组设计初值，不是复刻其他产品参数。
- 组内命令输出再展开可以限高，但避免套三层滚动；窄窗口优先独立详情区。
- 用户正在上翻时不抢滚动位置；有新内容显示“回到最新”。跟随最新时只更新当前动作，不反复重建整组。
- 展开状态按稳定身份保存；实时、重载、加载更早消息，不能改变已存在分组的含义或丢失异常。
- 分页以呈现单元/稳定边界处理，不由“刚好剩 20 条消息”冒充阶段。

## 6. 视觉基线

- 单列对话、适度阅读宽度；正文清晰深色，活动次级灰色，但保持可读对比度；状态不只靠颜色区分。
- 普通操作无外边框、无大底色、无每条时间戳和重复“工具调用已完成”。边框只用于需要交互的提问/审批、代码详情或交付区域。
- 正文与活动有稳定留白；减少当前折叠后大片无意义空白。计划与产物无需常驻占半屏。
- 标题句子化、短而具体；路径可复制，过长省略但可展开全名。支持键盘展开、焦点可见、屏幕阅读器状态提示、浅深主题和常见缩放。
- 不照抄 WorkBuddy 的反复“深度思考”标签；它未必有利于用户理解。

## 7. 实现职责与有限后端依赖

| 内容 | 谁提供 | UI 做什么 | UI 不做什么 |
|---|---|---|---|
| 公开过程说明 | Main Agent，独立于最终完成提议 | 按顺序显示，作为自然阅读分隔 | 从隐藏推理抽取、猜测意图 |
| 业务计划 | 现有计划内容及更新 | 可读清单、当前项、历史版本 | 另建 TaskDAG、勾选即 Completed |
| 工具事实 | 真实请求/回执与现有审计 owner | 按 call ID 更新、按类别显示 | 解析自然语言改判权限/终态 |
| 当前运行/暂停 | 既有权威状态投影 | 状态提示和有效操作 | 自行恢复、豁免 blocker |
| 文件变化 | 实际写入/版本/diff 来源 | 文件入口、范围明确的变更 | 以模型草稿或仓库全部 dirty 冒充本轮修改 |
| 最后交接 | 现有报告事实构造路径 | 已做/验证/阻塞/下一步 | 原样展示失败完成草稿 |

优先修现有消息适配与公开进度路径，不复制第二套事实库。若现有消息合同无法可靠区分进度与最终提议，必须先提出有限字段/通道扩展及旧数据回退方案，经确认再实施；不能按“已完成”等中文关键词分类。新协议也不由工具数量暗推阶段。

## 8. 实施顺序与过关条件

1. **设计确认**：用本次会话说明六个状态：初始规划、连续写入、阶段过渡、可恢复失败、等待用户、结束/暂停。先做可交互原型，让用户看折叠前后和阅读节奏，不先接一堆新功能。
2. **呈现数据贯通**：建立或收敛现有呈现适配；稳定 ID、顺序、公开正文、计划、工具状态、最终报告贯通实时与历史。只增加视图模型，不新增业务裁决 owner。
3. **组件落实**：轻量活动组、计划专用视图、文件/命令详情、异常提示、交付摘要、滚动行为。复用已有编辑器/diff/确认组件。
4. **公开说明和终止交接补齐**：在同一批交付内修通必要的后端输出路径；如需超过冻结合同则单列授权。不能以“前端做完了，模型没说话”结束验收。
5. **真实资料回放 + 桌面验收**：相关验证稳定后集中构建一次，交付用户验收。后端未知结果分类及循环问题单列关联缺陷，不以 UI 改好了宣称运行时通过。

### 必须通过的体验验收

- 中文、英文及明确指定回复语言的请求，都应得到相应语言的计划、当前工作和总结；显式语言要求优先于 query 表面语言。代码路径不被翻译，未知语言偏好不触发无必要提问。
- 用户无需认识工具名即可理解计划和当前工作；“运行命令”“工具记录 20 项”不能独自承担过程说明。自然语言说明与真实行动相符，不以漂亮文案掩盖缺少证据。
- 不展开工具详情，用户能说出当前工作、上一个有效结果、是否需要自己操作。模型没给语义说明时明确显示可证实动作，不显示虚构阶段。
- 本次 130 调用长会话回放不会变成 130 张卡片，也不会折成一个没有意义的“20 项”；不丢工具、错误、部分成果。
- 两次 todo_write 呈现可读计划更新，不显示“Updated (457 chars)”作为主要结果；计划完成与任务暂停可同时正确表达。
- 普通文件修改最多一次展开进入有用文件内容/差异；命令一次展开可见实际命令和结果；原始 JSON 不占默认阅读层。
- 运行、失败、超时、结果未确认、暂停、取消具有不同解释；技术 ID 不出现在默认最终正文。
- 正文进度在执行期间可见，不等最终门禁放行；未经确认的完成声明不能借此绕过完成检查。
- 对话重载、加载早期记录、流式更新不会重复工具/打乱先后/重置用户展开与滚动位置。
- 用实际窗口检查窄宽两档、100%/125% 缩放、浅深主题和键盘导航；不能用组件测试取代观感验收。
- 新生成文案只解释有来源的事实；旧会话没有公开进度时不得补写历史故事。对旧记录的改进限于事实摘要和详情组织。

### 10.2 用户到底更喜欢什么：证据支持到哪里

**不是“文字越多越透明”。** [开发者观察研究](https://arxiv.org/html/2506.12347v1)观察了 19 位开发者处理 33 个问题。参与者核查代码时更常看 diff，而不是长解释；部分人明确抱怨冗长。研究样本来自同一家公司，主要反映早期使用，作者也提醒不能广泛外推。因此只能支持一个设计方向：短说明帮助理解，直接证据帮助核查，不能拿解释代替证据；不能宣称所有人都喜欢极简或都不需要文字。

**也不是“折得越深越好”。** [Cursor 用户反馈及回复](https://forum.cursor.com/t/new-version-hides-agent-tool-call-details-in-defiance-of-setting/165292)中，用户不满详细模式仍折叠探索记录；回复说明这是当前分组设计与用户预期不同，而非简单的设置失效。这证明存在真实的控制感问题，不证明所有用户都想默认展开全部日志。CodeBuddy 应尊重用户手动展开，并避免“详细”实际仍层层隐藏的命名误导。

**反复确认有注意力成本。** [Anthropic 工程说明](https://www.anthropic.com/engineering/claude-code-auto-mode)报告其用户批准了 93% 的权限提示，并将审批疲劳作为设计动机。这是厂商统计，不是 CodeBuddy 的测量，也不是取消安全边界的理由。采用方向是只在真正需要决策时打断，让提示具体可理解；本轮不因此扩张权限或增加新的审批分类器。

目前没有足够依据给“全市场用户最喜欢哪一种布局”排名。产品任务、用户技术水平和监督需要不同；本项目优先遵循用户已经明确的自然语言、简洁、可展开偏好，再用真实任务观察核验。

### 10.3 对本提案的具体补强

1. **简洁不等于隐藏控制权**：默认简洁；用户展开的组不被后续流式刷新自动收回。可提供本会话“展开操作记录”入口，不必新增复杂密度设置页；展开不包含隐藏推理、凭据或内部提示。
2. **公开说明有信息增量**：说发现、重要变化、下一步；不机械复述“已读文件 A、已读文件 B”，不为凑阶段持续输出长文。语言遵循第 4 节用户偏好。
3. **业务计划与后台活动分开**：计划写用户目标下的步骤；后台区写正在运行的检查、服务、子任务。不要让一个 shell 进程冒充业务阶段。
4. **打断和排队必须有回声**：用户补充要求后，UI 应明确当前是已接收、待处理还是已经应用；只消费现有真实事件。没有应用确认就不能写“已按你的要求调整”。
5. **离开后回来能接上**：优先利用最后公开说明、当前工作、待用户决定项和最新验证提供简短状态概览；不重新编造历史摘要，不额外建第二套事实。
6. **成果阅读优先**：最终区域将启动/查看产物、文件变化、验证、未解决问题放到可直接找到的位置。需要技术核查时可展开详情；不能只有一句成功口号或失败代码。

### 10.4 用小型体验检查选择设计，而不是凭喜好争论

原型用同一组事实比较“默认简洁”和“展开记录”，不能一版有丰富人话、另一版故意只有裸日志。至少覆盖连续执行、失败后恢复、等待用户、用户离开后返回、最终受阻五种状态。

让评审者直接完成：指出当前在做什么、找出最近结果、判断是否需要自己行动、打开一次文件差异、找出任务为何暂停。记录找寻时间、点击数、误解点和主观负担；本轮先作为设计比较，不设置没有基线依据的市场化分数。产品验收同时覆盖流式、重载及真实异常，避免原型表现良好而实际没有内容可显示。
