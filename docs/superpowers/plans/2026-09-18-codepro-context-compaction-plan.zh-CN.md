# CodePro 上下文压缩：统一触发、状态与预算计划

日期：2026-09-18  
实现记录：2026-09-18 起在 `fix/codepro-context-compaction` 的当前 worktree 实现；基线 `7f70938aa`。用户自行执行 E2E，本次不运行单元测试。  
状态：已完成只读诊断；未开始实现或验证。

## 目标

让 CodePro 与普通聊天在长会话下都能可靠地：

1. 在请求实际接近上下文容量前压缩，而非主要依赖网关超限后的补救。
2. 在手动压缩、自动压缩、恢复性压缩期间展示真实且持续的状态。
3. 用同一口径说明已用容量与下一次请求预算。
4. 压缩后继续原任务，不扩大授权、不丢失边界，也不重放结果未知的外部动作。

## 已确认事实

### 自动阈值没有覆盖 CodePro

普通聊天的 `Agent::reply` 会在调用执行循环前通过
`check_if_compaction_needed` 检查阈值。ACP 的 CodePro 请求则经
`reply_codepro_with_resume` 进入 `reply_internal_with_options`，绕过该入口。

CodePro 当前仍可在模型返回 `ContextLengthExceeded` 后进入恢复性压缩；这不是
达到配置阈值时的预防性压缩。因此不能承诺 CodePro 会在 UI 显示达到 80% 时自动压缩。

### CodePro 的手动 `/compact` 路由错误

桌面压缩按钮提交 `/compact`。普通聊天会将其交给
`execute_command` 的 `handle_compact_command`。

ACP 在 CodePro 会话中没有在分流前执行内置命令，而是把该消息送进
`reply_codepro_with_resume`。因此 `/compact` 可被规划器或模型当作普通对话请求处理，
而不是确定执行的本地压缩操作。2026-09-18 的现场记录中，该请求最终取消，且没有
可确认的压缩生命周期事件；不能将当时的等待归因于压缩。

### 状态传输没有压缩生命周期

后端目前把压缩开始表示为通用 `ProgressMessage`；ACP 将其转成通用
`StatusMessage::Progress`；桌面 ACP 状态仓库仅更新可覆盖的 `progressMessage` 字符串。

`ChatState.Compacting`、对应加载文案和 UI 测试已存在，但 ACP 路径没有将会话切换到该状态。
其后续消息、思考或工具事件也可以清除普通进度文本。右侧 CodePro 面板读取的是独立的
任务活动事件，压缩不在其中。

压缩成功时后端会产生 `AgentEvent::HistoryReplaced`，但 ACP 流处理没有专门转发该事件。
因此前端没有可靠的“上下文已替换／压缩完成”实时边界，刷新后的会话也无法从瞬时进度文本
恢复压缩过程。

### 显示用量不是下一请求的准确预算

后端阈值判断优先读取 `session.usage.total_tokens`，缺失时仅估算 agent-visible 消息；
前端容量上限则来自多级模型配置来源。两者都不等于下一次 rendered request，后者还包括
系统提示、项目规则、工具定义、新增消息以及输出预留。

因此截图中的用量变化不能单独证明压缩完成，也不能用 UI 百分比断言下一次请求一定安全或
一定会超限。

## 外部设计对照

[OpenAI 的 Compaction 文档](https://developers.openai.com/api/docs/guides/compaction) 展示了可观察的阈值语义：
渲染后的 token 数超过阈值时触发压缩，在同一响应流中发出压缩项，随后以压缩结果继续推理。

本项目采纳：阈值与压缩结果必须在调用链中可观察，压缩后继续原任务必须基于明确的压缩结果。

本项目不采纳：假定所有提供商支持 OpenAI 的服务器端接口或 opaque compaction item。对自定义
提供商保留本地压缩实现；提供商声明自行管理上下文时，不能伪称客户端已执行压缩。

## 实现边界

- 仅处理 CodePro 与普通聊天共用的压缩触发、结构化状态、预算投影和桌面展示链路。
- 不借此修改意图识别、任务 DAG、权限白名单、外部动作授权或测试结果聚合。
- 结果未知的外部发送、支付、发布、删除等动作必须保持为“未知”，压缩或恢复后不得自动重发。
- 不以伪造完成百分比掩盖无响应；界面仅展示实际开始时间、耗时、实际状态与明确标注的估算值。

## 分支与工作区规则

本计划的实现、测试、构建、桌面启动和验收全程只在**一个明确命名的分支及其现有 worktree**中进行。

1. 开始实现前，确认该分支基于当前主开发基线，并记录分支名与起点提交。
2. 不为单独测试、构建或桌面验收创建新 worktree 或新分支。
3. 所有针对本计划的修复与回归测试都在同一 worktree 进行；测试报告必须写明 HEAD 提交和工作区是否干净。
4. 验收通过后才将该分支合并回主开发分支；合并后再删除不再需要的 worktree。
5. 现有未追踪本地规则、旧报告和 E2E 夹具不属于本计划，不随本计划提交，除非另有明确授权。

## 实施顺序

### 阶段 1：命令入口与生命周期契约

1. 在 ACP 的 CodePro 分流之前识别内置 `/compact` 触发器，并调用本地压缩命令路径。
2. 定义版本化 `CompactionLifecycle` 事件，至少包含：
   - `session_id`、`run_id`、可选 `task_id`；
   - `trigger`：`manual`、`auto`、`recovery`；
   - `status`：`started`、`completed`、`failed`、`cancelled`；
   - 开始、结束时间，失败分类，以及实际或估算的前后用量；
   - 预算来源与精度：`provider_actual`、`local_estimate`、`unavailable`。
3. 将生命周期事件持久化到会话可回放的记录中；普通进度文本只可作为兼容性展示，不能再是唯一事实来源。

### 阶段 2：共用模型调用边界的预防性检查

1. 把“是否需要自动压缩”的判断放在普通聊天与 CodePro 共用的模型调用边界。
2. 每次即将调用模型时检查，包括初始请求以及工具结果追加后的下一次请求。
3. 排除压缩请求自身，避免递归触发；保留提供商自行管理上下文的例外。
4. 原有 `ContextLengthExceeded` 恢复路径继续保留，但统一发出同一生命周期事件并限制重复重试。

### 阶段 3：下一请求预算

1. 计算或估算下一次完整请求：可见会话、当前新增内容、系统与项目指令、工具定义、其他 provider 输入，以及输出安全余量。
2. 统一后端触发与前端展示使用的 context limit 来源；无法精确获得时，显示“估算”而不是把数值包装成实际用量。
3. 将当前窗口使用量、预估下一请求使用量、保留输出量分开存储和显示。

### 阶段 4：桌面状态投影

1. ACP 适配器接收生命周期事件，专门维护压缩状态，不通过 `progressMessage` 字符串推断。
2. 底部加载区、容量指示器和右侧 CodePro 面板读取同一状态源。
3. 展示“正在整理对话上下文 · 已用 N 秒”；成功、失败、取消后显示真实终态并恢复原任务阶段。
4. 会话刷新、重连与回放后恢复最后的持久化生命周期状态；普通工具/思考事件不得清除活动中的压缩状态。

### 阶段 5：安全连续性

在压缩摘要或保留状态中验证以下内容仍可恢复：当前用户目标、保护边界、待确认授权、任务与子任务状态、已完成工具结果、外部动作回执及结果未知标记。压缩后恢复只能从持久化的确定状态继续，不能根据模型文本推断外部动作已完成或重放该动作。

## 验收矩阵

1. 普通聊天和 CodePro 在阈值前均会触发预防性压缩，且不会先出现网关上下文超限。
2. CodePro 点击压缩按钮或提交 `/compact` 时，走本地压缩，不进入语义路由或任务规划。
3. 工具输出将下一请求推过阈值时，会在下一次模型调用前压缩。
4. `started → completed`、`started → failed`、`started → cancelled` 都有持久化、可回放的结构化证据。
5. 任务运行期间，底部和右侧始终显示同一压缩状态；刷新后状态正确恢复。
6. 前端显示数字与后端触发都标明实际/估算来源；系统提示、工具定义与输出保留被纳入投影预算。
7. 压缩完成后原任务继续；压缩失败或取消时原对话与任务状态保留，外部未知动作不重放。
8. 回归覆盖既有自动压缩、手动压缩、超限恢复、取消逻辑，以及 CodePro 的任务/权限/恢复路径。
9. 实现完成时按项目规则运行格式化、相关 Rust 与桌面测试、构建、clippy，并从改动源码启动桌面应用做真实交互验收；任何未通过项如实记录，不宣称完成。
