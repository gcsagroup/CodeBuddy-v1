# CodePro 核心 Agent 问题分析总结

**日期：** 2026-09-16  
**依据：** 2026-09-15、2026-09-16 两份产品测试记录，以及当前仓库源码  
**分析范围：** 意图识别、能力路由、Planner/DAG、长任务恢复、多 Agent 调度、工具调用、结果汇总与记忆  
**明确排除：** Git 提交/推送/回滚、Computer Use、纯前端展示问题

## 1. 结论先行

这批失败不是某一个模型突然“变笨”，也不是单独一个 Rust 函数写错。主要问题是核心 Agent 链路中的多份合同没有对齐：

```text
用户原始要求
  ↓
意图分类与硬约束提取
  ↓
工作流及能力选择
  ↓
Planner 生成任务和 DAG
  ↓
宿主编译任务合同、权限和证据要求
  ↓
Scheduler 分配角色与工具并执行
  ↓
结果聚合、完成判定和最终报告
```

上游只要丢掉一个关键信息，例如“必须实际运行”“不要修改”“只修改 app.js”“先运行 node --version”，下游就可能生成一个形式合法、实际上无法完成用户目标的任务图。更严重的是，最终报告目前还可能脱离真实执行证据，把零执行、跳过或部分完成描述成“已完成”。

因此，当前最核心的问题可以概括为五句话：

1. 用户的硬约束主要以自然语言在模块间传递，没有成为贯穿全链路的结构化不变量。
2. 意图分类选择的工作流，与该工作流实际获得的工具和权限并不总是一致。
3. Planner 认为可执行的 DAG，不一定能通过 Scheduler 的并发写入和任务合同规则。
4. 系统对“任务是否完成”的判断，没有逐项核对用户明确提出的验收条件。
5. 最终报告仍混入模型概括和角色模板，没有完全由宿主侧事实投影生成。

## 2. 主要问题与根因

### 2.1 测试意图被路由为只读分析，导致测试命令必然被拒绝

**对应案例：** D06、G02；A02 的部分现象也属于同一类能力错配。  
**把握程度：高。** 测试日志与当前源码能够互相印证。

用户说“运行现有测试，但不要修改文件”时，系统把“不要修改”理解成了“只读问题”。随后 Agent 虽然正确请求 `npm test` 或 `node --test`，只读 Shell 策略又会拒绝这些命令，因此测试进程根本没有启动。

这里不是单纯的 Shell 白名单太窄。测试命令可能写缓存、临时文件、覆盖率文件或启动子进程，本来就不应该被粗暴塞进普通只读白名单。真正的问题是系统缺少一种独立能力语义：

```text
允许执行测试及其受控运行时副作用
禁止修改项目源码和配置文件
```

当前实现把“读项目”和“运行但不改源码”混成一个 ReadOnly 路线。相关机制主要位于：

- `crates/goose/src/agents/codepro_intent.rs`：字面规则、简单对话和测试意图识别。
- `crates/goose/src/agents/agent.rs`：只读工具权限及 Shell 命令判定。

**责任判断：** 意图/能力建模是主因，Shell 拒绝是正确执行了一个错误选择的能力合同。

### 2.2 明确工具请求可能掉进“简单聊天”快速路径

**对应案例：** A02 的“运行 node --version”。  
**把握程度：中高。** 现象明确，当前规则能够解释，但仍应以自动化用例稳定复现具体分支。

短句、问句和缺少明显项目锚点的请求，可能被快速判成简单聊天。例如“能帮我运行 node --version，并原样告诉我结果吗？”在语气上像问题，但语义上包含不可省略的真实工具动作。

这说明当前规则对“句式”权重过高，对“可执行动作词 + 明确命令 + 要求原始结果”权重不足。简单聊天应当只有在确认不存在以下内容时才成立：

- 明确命令或工具动作；
- 文件、目录、项目或环境目标；
- 要求读取真实状态、版本、日志或运行结果；
- 写入、测试、构建、安装等副作用动词。

即使成功避开简单聊天，`node --version` 仍可能被只读 Shell 策略拒绝。这是第二层问题，不能把两层失败合并成“模型不会调用工具”。

### 2.3 语义分类器自身存在输入输出协议脆弱点

**对应案例：** A05 的无效 JSON 与错误工具链现象。  
**把握程度：高（协议缺陷）；中（它对历史每次失败的贡献比例）。**

语义分类 Prompt 中存在双花括号形式的 JSON 示例，而解析端要求标准 JSON。Prompt 协议和解析协议不一致，会把本可正常分类的请求推向解析失败或降级路径。

此外，语义分类阶段把普通解释、项目分析、动作执行压在少数粗粒度标签上，导致证据门禁也容易用错：普通知识解释可能被要求读取项目，而真正需要真实环境证据的动作请求又可能被当成聊天。

这类问题不能只靠继续增加中文关键词修复。更稳妥的分类输出至少应包含：

```text
primary_goal       主目标：解释 / 分析 / 测试 / 修改 / 环境探测
required_effects   必须发生的动作：读、执行、写、联网等
forbidden_effects  用户禁止的动作：不改文件、不安装等
targets            指定文件、目录、命令或项目
acceptance_items   必须逐项完成并留证的条件
```

### 2.4 Planner 生成的 DAG 与 Scheduler 的合法性规则不一致

**对应案例：** DurableQueue 多个 Tester 使用相同临时写入范围，全部零执行即暂停。  
**把握程度：高。** 持久化状态、零 Worker 动作及所有权校验源码形成闭环证据。

Planner 创建了多个可并行 Tester，并给它们相同的临时目录写权限。Planner/DAG 前段没有把它修正为串行任务，也没有给每个任务分配独立目录；直到调度阶段，`task_graph/ownership.rs::validate_write_ownership` 才发现并发写入所有权重叠并拒绝运行。

Scheduler 的 fail-closed 行为本身是合理的：不能为了“尽量执行”而放任并发任务写同一目录。缺陷在于同一套系统中存在两种不一致的“合法 DAG”定义：

- Planner/编译阶段认为合法；
- Scheduler/所有权阶段认为非法。

这类冲突应该在启动任何 Worker 之前，由统一的 DAG 编译器完成以下处理：

1. 检测兄弟任务的读写范围冲突；
2. 能安全串行化时自动补依赖边；
3. 能隔离目录时重写为任务独占临时目录；
4. 无法修正时，把具体冲突任务和路径返回 Planner 重规划；
5. 最终交给 Scheduler 的图必须已经满足 Scheduler 的全部不变量。

### 2.5 纯验证任务的降级路线会篡改用户目标

**对应案例：** Planner 失败后，纯验证请求被降级成 `Coder → Tester`。  
**把握程度：高。** 降级 DAG、角色状态、零命令和合同拒绝均有记录。

用户明确要求“只运行验证，失败时只报告，不修改代码”，但 Planner 输出无效后，通用 fallback 把任务变成：

```text
host-fallback-implement（Coder）
  ↓
host-fallback-verify（Tester）
```

Coder 没有 Shell，也没有修改文件，却被合同强制要求 `ChangedFiles` 和 `Patch`。结果 Coder 因无法提供补丁而暂停，真正拥有验证能力的 Tester 被跳过。

这不是 Planner 模型一次输出不好那么简单。安全降级必须保持用户语义边界：

- Test/Validate 请求只能降级为单一 Tester 或受控执行者；
- ReadOnly 请求不能降级成写入任务；
- Change 请求才可以要求补丁证据；
- fallback 不得新增用户没有要求的副作用。

换句话说，降级策略首先要“保真”，其次才是“保证有图可跑”。

### 2.6 角色任务与实际工具能力不匹配

**对应案例：** E05“先运行 node --version，然后修复 app.js”。  
**把握程度：高。** Coder 明确报告无 Shell，Tester 证据中也没有版本检查。

Planner 把“环境检查 + 修改代码”放在同一个 Coder 任务里，但 Coder 实际没有 Shell。代码修改成功，Tester 也运行了测试，然而 `node --version` 这个显式验收项从未执行。

当前系统把角色名、任务描述和能力分配当成三套相对独立的信息。正确做法应是先从任务步骤推导所需能力，再决定角色或拆任务。例如：

```text
环境探测（需要受控 Shell）
  ↓
代码修改（需要读写文件）
  ↓
验证（需要测试执行能力）
```

如果一个 Worker 缺少任何必需能力，任务在调度前就应被拆分或判为不可执行，而不是运行后再靠模型文字说明“我没有这个工具”。

### 2.7 “修改 + 验证”可能被末尾测试语句覆盖成纯测试

**对应案例：** G03 多轮用例。  
**把握程度：中高。** 错误工作流和只读合同已确认；具体由哪条当前规则触发，仍需干净夹具回归确认。

用户明确说“采用刚才的第一种方案，只修改 app.js，修改后运行测试”，最终却得到 `workflow=test`、空写入范围和单一 Tester。失败后恢复逻辑只会继续重跑相同测试，无法回到可写 Coder。

这里有两个连续缺陷：

1. 意图层没有把“修改 app.js”识别为不可丢失的主目标；
2. 路由后没有做目标—工作流一致性校验。

应增加一个宿主不变量：只要结构化目标含有明确写入目标，最终 DAG 就不能是 `write_scope=[]` 的纯测试图；只要用户声明“不修改”，DAG 也不能包含 Coder 写入任务。

连续验证失败且工作区没有任何变化时，也不应重复相同测试。恢复状态机需要识别“无进展”：相同失败条件 + 无新证据 + 无状态变化，应回到路由/规划阶段或明确停止，而不是只提高 plan revision。

### 2.8 简单修改状态机没有正确合并“修改事实、验证事实和策略拒绝”

**对应案例：** G03 最新两轮。  
**把握程度：高。** 工具回执与 `codepro_simple_change_run.rs` 的状态更新顺序直接对应。

已确认两个具体问题：

1. 文件编辑成功后，某个验证命令被拒绝，最终 `outcome()` 会优先把整轮标成 BLOCKED，掩盖“修改已经成功”这一事实。
2. 如果文件在本轮开始时已经满足目标，本轮没有再次写入，那么随后成功执行的 `npm test` 不会被登记为有效验证，最终报告反而声称验证未运行。

这说明状态机仍在用一个总状态表达多个彼此独立的事实。更合理的结果结构应分别记录：

```text
change_status       changed / already_satisfied / not_changed / failed
validation_status   passed / failed / not_run / policy_denied
policy_events       哪个命令被哪条策略拒绝
overall_status      根据用户验收项计算，而不是覆盖前述事实
```

策略拒绝可以让某个验收项未完成，但不能抹掉此前已经发生的成功编辑或另一条成功测试。

### 2.9 最终完成判定和报告不可信

**对应案例：** 多 Tester 零执行、验证 fallback、E05、G03、检查点暂停。  
**把握程度：高。** 多个案例中最终文字与持久化事实直接矛盾。

目前最影响用户信任的问题，是系统可能出现以下说法：

- Worker `turns_consumed = 0`，却称“按照计划完成了项目修改”；
- Tester 为 `skipped`，却称“实际执行了验证”；
- 明确的 `node --version` 没有证据，仍报告整个任务 completed；
- `npm test` 已返回退出码 0，却报告“验证未运行”。

这不是文案润色问题，而是完成判定架构问题。最终报告应由宿主侧事实生成，模型只能改善表达，不能创造事实。至少需要满足：

- 没有成功工具回执，不能写“已执行”；
- 没有变更证据，不能写“已修改”；
- `skipped`、`paused`、`turns_consumed=0` 必须忠实展示；
- 每个 `acceptance_item` 都要关联证据或 limitation；
- 任一强制验收项缺证，整体不得输出无条件 completed；
- 报告重写失败时，必须退回确定性的宿主模板，而不是猜测性总结。

相关实现集中在 `codepro_run_result.rs`、`result_aggregator.rs` 和 `codepro_terminal_report.rs`。当前工作区已经出现 `validation_not_run` 等未提交改动，但在完成针对上述案例的端到端回归前，不能视为已修复。

### 2.10 长任务检查点把不同概念混在了一起

**对应案例：** DurableQueue 动作额度暂停。  
**把握程度：中。** 已确认状态和界面语义矛盾，但“所有 PUBLISHED 检查点都必须可直接恢复”尚不能仅凭现有证据断言。

当前链路中至少有三种不同对象：

- 文件级事务检查点：用于保存/回滚文件状态；
- 执行续跑检查点：包含足够任务状态，可恢复 Scheduler；
- 用户审批或问答：等待用户授权某个明确动作或补充信息。

测试中磁盘存在已提交、已发布的文件检查点，但终止状态没有有效 checkpoint，界面又显示“需要你确认 · 0 个工具动作”。这说明存储、运行终态和交互语义没有使用同一状态模型。

修复前应先把三种对象拆开命名和建模。若只是达到动作上限且没有待审批动作，应显示“已暂停，可继续”或“无法自动继续，需要人工检查”，不能伪装成审批请求。

## 3. 记忆模块目前怎么看

在排除 Git/Computer Use 后，这两份测试里没有足够证据证明“记忆模块本身”是主要根因。相反，G02 的第二轮“继续”保留了原工作目录、`npm test` 目标和“不修改文件”约束，说明短期会话续接至少部分有效。

当前更像是：系统记住了用户要做什么，但恢复决策仍选择了同一个被策略拒绝的动作。也就是说：

```text
上下文记住了  ≠  下一步决策正确  ≠  工具能力可执行
```

因此不建议现在优先重写记忆。应先给记忆的输出建立可观察边界：恢复时明确记录继承了哪些目标、约束、目录和未完成验收项，再判断错误发生在“没记住”还是“记住后用错了”。否则调度、权限和恢复策略的问题会继续被误归因成记忆问题。

## 4. 按严重性和耦合度建议的修复顺序

### P0：先修事实层与完成判定

先让系统不再谎报完成。统一工具回执、任务状态、文件变更和验证证据，最终报告只消费宿主事实。即使执行仍失败，用户至少能得到可信结果，也便于后续定位。

### P0：建立结构化用户合同

在意图阶段生成并贯穿整个运行的 `UserTaskContract`，至少包含主目标、必须动作、禁止动作、目标范围和逐项验收条件。Planner、fallback、Scheduler、恢复与报告都不得改变这些硬约束。

### P0：统一“意图 → 能力 → 工具”矩阵

不要只决定 `chat/read/test/change` 名称，要同时验证该路线是否确实拥有完成任务需要的工具。优先覆盖四类回归：环境探测、只测试不修改、修改后测试、只修改不验证。

### P1：把 DAG 编译器变成 Scheduler 的唯一合法性入口

在派发前统一完成角色能力校验、写入所有权校验、验收证据要求和安全串行化。Scheduler 保留 fail-closed，但不再负责发现本可在编译期修正的普通图错误。

### P1：按用户合同设计保真的 fallback 与恢复

每种工作流拥有自己的降级图；纯验证不得降级成修改。恢复逻辑加入“是否产生新证据/状态变化”的判断，阻止相同失败的无进展循环。

### P1：拆分简单修改的多维状态

分别保存修改、验证和策略事件，支持“修改成功但验证受阻”“目标原本已满足且测试通过”等真实组合，不再用单一 BLOCKED 覆盖全部事实。

### P2：再评估长任务检查点与记忆

先区分文件检查点、续跑检查点和审批请求，再修复 UI/终态传递。记忆模块则在核心合同稳定后补充跨轮约束继承测试，不宜现在大改。

## 5. 推荐的最小回归集

每次修复后至少用全新目录、全新会话运行以下用例，并同时核对工具回执、持久化状态和最终报告：

| 用例 | 必须满足 |
|---|---|
| `node --version` | 实际执行；原样返回；无虚构版本 |
| 只运行 `npm test`，不要修改 | 测试真实启动；项目源码哈希不变；报告真实退出码 |
| 只修改 `app.js` | 只改目标文件；未运行验证时明确写 `not_run` |
| 修改 `app.js` 后运行测试 | 修改和验证分别留证；任一失败不得覆盖另一项事实 |
| 先运行版本检查，再修改并测试 | 三个验收项都有独立证据；缺一项不得 completed |
| Planner 输出非法 DAG | fallback 保持原读写边界；不得把验证变成修改 |
| 两个 Tester 需要临时目录 | 自动隔离或串行化；不得零执行后谎报完成 |
| 相同测试连续失败且无文件变化 | 不重复无进展动作；回到重规划或明确停止 |
| 动作额度耗尽 | 明确区分“可继续”“待审批”“不可恢复人工检查” |
| 第二轮只说“继续” | 继承目标、禁止项和未完成验收；不重复不可重试的拒绝动作 |

## 6. 最终判断

排除 Git、Computer Use 和纯前端问题后，当前最值得修的不是某个模型 Prompt，而是核心 Agent 的协议层。Scheduler 多数时候是在正确拒绝不安全或不满足合同的任务图；真正的问题通常更早发生：意图层选择了错误能力，Planner/编译器生成了不可执行的合同，fallback 改写了用户目标，最后结果层又没有忠实表达事实。

如果只修关键词或扩大 Shell 白名单，短期可能让几个用例通过，但会把风险转移到别的路线。更稳妥的主线是：

```text
结构化用户合同
  → 能力可满足性检查
  → 统一 DAG 编译与合法性校验
  → 证据驱动执行状态
  → 确定性完成判定与报告
```

这条主线同时覆盖你负责的意图识别、长任务、多 Agent 调度和工具调用；记忆则先作为“合同跨轮传递”来验证，而不是独立重写。
