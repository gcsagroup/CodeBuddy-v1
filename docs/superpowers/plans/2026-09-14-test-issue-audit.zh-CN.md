## 1. 连续需求的租约不一致

**事实：** `workspace_lease.rs` 校验持久化工作区绑定的租约 ID 与当前进程注册的权威租约 ID，不一致即返回文档中的错误。`server.rs` 在执行工具前也进行校验。因此错误不是凭空产生的通用文案。

**实测：** 在隔离会话 `20260914_2` 中，连续 3 次 `session/load` 均成功，没有重新提交租约确认；重启后端后再次加载也成功。随后真实 `read_document` 读到了测试 README 内容，`computer_observe` 也成功通过执行前校验。初始测试程序默认拒绝了若干读取审批，这些记录是测试端拒绝，不能记成工作区缺陷。

**未确认：** 未能复现“成功完成模型需求后再提交”的原始时序。现有证据不能断定偶发错误已经修复，也不能将会话记忆模块直接认定为根因。

**待验证的推测：** 已加载会话的租约与持久化状态若分别更新，旧对象再次保存可能覆盖新租约；前端同会话加载合并也应检查是否吞掉不同的恢复参数。这些需要并发/故障注入测试，尚非已证明根因。

**方案：** 为同一会话的 acquire、resume、persist、dispatch 建立一致的状态更新边界；使用版本号或条件更新阻止旧状态覆盖；记录不含凭据的会话、租约代次和调用关联信息。遇到不一致时，只在路径、目录身份和权限仍一致的情况下进行一次受控恢复，保留输入草稿。不要删除租约检查或无条件自动授权新目录。

**验收：** 连续完成 10 轮真实模型任务；覆盖双窗口恢复、后端重启、旧响应晚到、取消后继续、重命名/删除工作区。合法续接不重选目录，跨目录和失效绑定仍必须正确阻止。

## 2. 重复选择目录

**事实与实测：** 当前 `load_session.rs` 已有恢复有效工作区租约的分支；本次正常连续加载和重启恢复没有要求重新选择目录。原生打开已有验收对话也直接显示历史内容和输入框，没有出现目录选择卡。

**范围限制：** 打开会话成功不等于连续发送任务成功。原文的“每次发送”仍需在服务恢复后复测，并与问题 1 一起检查，避免重复设计两套恢复机制。

**方案：** 会话保留已确认目录，普通恢复验证目录身份后直接沿用；新建独立项目、显式切换目录、目录不存在或越界时再确认。区分“恢复既有绑定”与“建立新的写权限”，不要每轮重新走新建会话流程。

**验收：** 同目录多轮聊天不弹选择器；切换聊天和重启后保持正确目录；显式换项目确实换目录，原目录删除后提供可理解的恢复操作。

## 3. 历史记录与搜索

**事实：** 原生界面已存在 Ctrl+F 搜索、导入、重命名、导出、删除等入口；这些入口不等同于侧栏直接进入聊天。归档和批量管理本次未作功能验收。

**新复现：** 列表中有 `Model connection check`，实际在搜索框输入 `Model connection` 后显示“未找到匹配的会话”。`session_manager.rs::message_keyword_clause` 只对 `messages.content_json` 中的 text 字段匹配，没有查询会话标题。不能只因存在搜索框就宣布搜索完整可用。

**方案：** 搜索至少覆盖会话名称和正文；用明确的字段/相关性规则避免不透明匹配。搜索框常驻或增加明显按钮；历史页负责跨项目管理，侧栏负责快速切换。项目、日期筛选、归档和批量管理可分阶段补充，没有必要先删除历史入口。

**验收：** 标题独有词、正文独有词、中文、大小写、空白、`%`/`_` 字面量、分页及快速改变关键词都得到正确结果；空结果与请求失败分开展示。

## 4. 自主模式与权限说明

**事实：** 原生“行为与回答”页面仍写着“完整文件修改能力，可自由编辑、创建和删除文件”。后端权限并非无条件放行：工作区写入按配置/作用域处理；工作区外写入和高风险操作仍可能要求审批；用户拒绝规则必须保留。当前代码还对已注册的本机电脑动作设有自主模式处理，不能简单描述成“所有启动应用都一定审批”。

**证据边界：** 44 项权限检查测试通过。直接 ACP 工具调用与模型会话的审批路径并不完全相同；本次测试端收到的单次审批不能直接证明所有自主聊天都会异常审批。真实模型中的各类文件操作审批矩阵尚未完成。

**方案：** 文案改为“在当前已授权范围内自动执行；超出范围、受限制或需要额外确认的操作会说明原因”。同时显示实际目录范围、当前会话模式、默认新会话模式及审批规则来源。若普通已授权工作区修改仍重复审批，再修策略传递；不要仅为消除弹窗移除风险和拒绝规则。

**验收：** 对工作区读/写、工作区外写入、本机程序操作、外部发送、用户已拒绝动作分别核对实际决策；新会话和既有会话的模式变化符合界面说明，重启后不悄悄改变。

## 5. 电脑控制、鼠标约束和循环重试

**已经证明可用：** 真实调用 `computer_observe`、`computer_focus`、`computer_screenshot`、`computer_click`。最终点击本次隔离 CodeBuddy 窗口的“历史记录”，返回 `outcome: worked`、`isError: false`，原生窗口确实从新任务页切到历史页。这证明底层鼠标可用，不证明主 Agent 已能独立完成微信任务。

**新确认的契约问题：** `computer_click` 声明中的 `screenshot_id` 可省略，但运行时即使使用屏幕坐标也要求该字段。实际省略时返回“坐标动作必须绑定当前截图状态 screenshot_id”。另外观察有效期为 30 秒，过期后拒绝动作；本次也实际收到对应错误。获取新观察和截图、补齐参数后点击成功。

**策略与重试核查：** 当前脚本使用 PowerShell `-File`，本机策略为 LocalMachine `RemoteSigned`，本次没有被执行策略拦截。已有单次 PowerShell 20 秒超时；`tool_task.rs` 对同工具同参数失败在第二次提示检查、第三次识别为重复失败。指纹仅排除少量请求字段，改变截图 ID 或命令文本可能落入不同指纹。因此“完全没有重试机制”不符合当前代码，但跨参数变化的同类失败仍值得补测。原文 32 次历史操作没有附原始日志，本次不能独立确认。

**方案：**

1. 让 schema、说明、示例和运行时一致；坐标操作明确要求新鲜截图标识。过期时先刷新观察，再依据新状态决定动作，不能复用陈旧坐标或简单删除时效检查。
2. 将“必须用鼠标”保存为当前任务约束；不允许把命令行启动应用冒充完成。确实无法用指定方式操作时，解释原因并保留未完成目标。
3. 增加按目标、错误类别、动作效果归一的失败计数；相同策略拒绝不因改命令文本而无限重试。用户拒绝的同类动作，在授权条件未变化时不再次自动申请。
4. 分开计算单动作超时、无进展重试、任务总预算和真实进展；可恢复等待保留会话。对发送等结果不确定的动作先观察核对，不能盲目重放。
5. 检测执行策略阻塞并给出明确诊断；不自动修改系统策略或加绕过参数。

**验收：** 服务恢复后用真实模型执行“仅用鼠标打开微信/另一个桌面程序”，核对每次调用和可见窗口；注入截图过期、同类错误但不同参数、用户拒绝、窗口失焦、操作超时。发送消息类验收另用明确联系人和正文，检查发出方向及重复发送风险，不能用点击成功代替发送成功。

## 6. 复制历史会话

**实测：** 对真实 CodePro 会话调用 `session/fork`，返回 `-32602`，数据中包含 `CodePro sessions cannot be forked; start a freshly confirmed session`。原生历史列表仍显示“复制会话”按钮，前端直接调用 fork。当前产品能力与界面入口不一致。本次没有可靠捕获点击后的错误 toast，结论依据真实协议错误和可见入口，不伪称 toast 验收完成。

**方案：** 短期由统一能力判断控制历史页、消息编辑等所有复制入口，隐藏或禁用并给中文说明。长期把“复制内容”实现为创建独立会话：新会话 ID、新工作区租约、明确选择保留的已完成消息，不复制活动任务、未决审批或一次性发送授权。

**验收：** CodePro/普通聊天分别验证入口；复制后原会话不变；新会话可以正常执行；无旧租约、运行状态和审批串用；失败提示可理解且保留当前页面。

## 7. 执行展示

**实测：** 打开已有验收会话，能看到 `Read Document path: notes.txt` 等技术标题；点击后可展开“工具详情”“输出”，审计详情也可折叠。设置中已存在“详细/精简”显示。已有任务报告包含“做了什么、结果、总结”。因此“完全没有总结和折叠”不成立，但技术标题、英文残留、重复报告结构确实影响自然阅读。

**方案：** 默认展示“正在读取项目说明”“已检查 3 个文件”等与真实工具证据对应的短句；命令、路径、完整输出保持可展开。完成报告突出实际结果与未完成项，减少机械栏目和重复句子。修正把读取文件说成“执行文件”的通用动作描述。这里改善的是可验证的进度解释，不要求展示模型私有推理过程。

**验收：** 原生界面检查流式到达、长路径、错误/取消、精简与详细切换、重载后的展示；文字不得早于执行证据宣称整个任务完成。新模型生成的自然程度待服务恢复后验收。

## 8. 干净构建

**实测方法：** 从本次远端 main 提取原样 `builtin.rs` 放入隔离目录，用现有 `include_dir` 编译依赖实际调用 rustc。没有 `src/skills/builtins` 时 exit 1，宏报 `is not a directory`；仅创建空目录后同一编译命令 exit 0。Git 树中确实没有该目录下的跟踪文件，而本地残留空目录存在。提交 `31a2e9e11` 确实删除了 `goose_doc_guide.md`。

**边界：** 这是针对远端原样源码和实际宏的隔离编译复现，不是整仓全新 clone 后全部依赖的完整构建。它足以确认此处阻塞根因，不能保证修好这一处后整个仓库必然零错误。

**方案：** 如果仍保留内置技能加载架构，提交 `.gitkeep` 等不被当作技能加载的占位文件，确保干净检出目录存在；如果产品已决定完全取消内置技能，改为明确的空注册表并移除不必要的编译目录依赖。当前最小改动建议是占位文件，避免把用户已要求删除的教程恢复回来。CI 必须从干净 Git 内容开始构建，不能依赖开发机残留目录。

**验收：** 从 git archive 或新 clone 开始 Windows 构建；再跑相关技能测试、Rust 格式/静态检查、桌面构建和启动。分别验证空技能集合、未来新增合法技能及教程仍不展示。

## 与公开 Codex 行为的比较

公开文档将技术可访问范围与是否需要审批分开，并说明自动模式通常允许工作目录内操作、越界操作另行处理。本方案采用这种“范围明确、原因可见”的表达，拒绝把“自主”解释为全局免审；具体规则以 CodeBuddy 的实现和用户授权为准。[OpenAI：Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)

当前可用 Codex 任务工具也明确区分继续既有任务和复制已完成历史；本方案借鉴会话隔离和完成历史边界，不推断其私有租约或内部状态机。租约条件更新、错误归一、搜索字段和 UI 排版是针对本项目代码提出的方案，尚未声称与 Codex 内部实现相同。
